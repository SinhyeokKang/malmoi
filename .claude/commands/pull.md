description: git pull 후 최근 변경 파악 + 문서 확인 + 작업 맥락 브리핑. 코드 안 고침.
---

원격 변경을 받아오고 **지금 어디까지 왔는지** 브리핑한다. 세션을 새로 시작할 때 쓴다.

> 이름이 겹치지만 이 프로젝트의 **pull 흐름(DB → PR)** 과는 무관하다. 그건 `/api/pull`이다.

## 절차

1. **상태 확인** — `git status`. 미커밋 변경이 있으면 pull 전에 알린다 (stash 여부는 사용자 판단).
2. **브랜치 확인 후 `git pull`** — 작업 브랜치는 `dev`다. `main`에 있으면 왜인지 확인하고 `dev`로 옮긴다(작업은 dev에서만 한다).
   - 충돌이면 중단하고 보고 — 다른 창구(웹 UI·Codex·다른 머신)에서 푸시가 있었다는 뜻이다.
   - **`git log origin/main..origin/dev`가 비어 있는데 dev가 뒤처져 보이면 `/merge`가 다른 곳에서 돌았다는 신호다** — squash 머지가 해시를 바꾸므로 `/sync`로 dev를 `origin/main`에 맞춘다. 이 상태를 모르고 작업하면 다음 PR diff에 이미 머지된 변경이 다시 나타난다.
3. **최근 변경 파악**
   - `git log --oneline -15`
   - `git diff HEAD@{1}..HEAD --stat` (pull로 들어온 것)
4. **문서 확인** — `docs/PRODUCT.md` §10(아직 안 정한 것), `docs/POSTMORTEM.md` 최근 항목을 읽는다.
5. **진행 중인 기능 확인** — `docs/features/`에 디렉터리가 남아 있으면 그 `tasks.md`의 미체크 항목이 곧 진행 중인 작업이다. **그 주장을 검증한다**: 미체크인데 파일이 이미 있거나 `[x]`인데 파일이 없으면 문서가 낡은 것이다. 어긋난 항목을 리포트에 적는다 (고치지는 않는다 — 이 스킬은 읽기 전용).
6. **브리핑.**

## 리포트

```
📥 pull: dev
브랜치 관계: dev == origin/main / dev가 <n>커밋 앞섬 / ⚠️ /sync 필요
받아온 커밋: <n>건 / 없음
   <oneline 목록>

진행 중인 기능 (docs/features/): <slug 또는 없음>
  미완 태스크: <n>건 — <핵심 2~3개>
  🔒 결정 필요: <항목 또는 없음>
  문서 정합: tasks.md 주장과 실제 파일 일치 / 어긋남 <목록>

미결 항목 (PRODUCT.md §10): <목록>
최근 POSTMORTEM: <최근 1~2건 또는 없음>
다음 할 일: <미완 태스크 또는 최근 커밋이 예고한 것>
```

## 금지 사항

- **코드 수정·커밋 금지.** 읽고 브리핑만.
- **충돌 자동 해소 금지** — 중단하고 보고.
