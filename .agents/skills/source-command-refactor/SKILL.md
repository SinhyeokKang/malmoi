# source-command-refactor

Use this skill when the user asks to run the migrated source command `refactor`.

## Command Template

`/code-review` 발견을 실제로 고친다. **버그성 발견은 회귀 테스트를 먼저 박는다.**

## 사용

- `/refactor` — 직전 `/code-review`의 🔴/🟡 전부.
- `/refactor <항목 번호|설명>` — 지정 항목만.

## 절차

### 1. 대상 확정

직전 리포트에서 항목을 추린다. **⚪만 남았으면 스킵하고 보고**한다 — 참고 항목을 고치려고 diff를 넓히지 않는다.

### 2. 분류

각 항목을 둘로 나눈다:

- **버그성** (잘못된 동작을 만든다) → **회귀 테스트 먼저.** `/tdd regression`의 규율을 그대로 적용해 red를 확인한 뒤 고친다. 이 순서를 건너뛰면 "고쳤다"의 근거가 없다.
- **품질성** (동작은 같고 구조·가독성만) → 테스트 없이 수정, 단 기존 테스트가 계속 green이어야 한다.

### 3. 수정

- **한 항목씩.** 여러 개를 한 번에 섞으면 무엇이 무엇을 깼는지 모른다.
- 코어 로직(`lib/export.ts`·`githash.ts`·`github.ts`·`scan/`)이면 **`docs/ARCHITECTURE.md` 해당 섹션을 먼저 읽는다.**

### 4. 회귀 위험 확인 지점 (중단 조건)

아래에 해당하면 **강행하지 않고 사용자에게 확인**한다:

- 기존 테스트의 **기대값을 바꿔야** 하는 수정 (테스트가 틀렸다는 주장이므로 근거가 필요하다)
- **export 출력이 바뀌는** 수정 — 다음 pull에서 전 로케일 파일이 재작성되고 PR diff가 전면 변경으로 뜬다. 의도된 것인지 확인
- **스키마 변경**을 요구하는 수정 — `/db`로 분리해야 한다
- 공개 API·라우트 계약 변경

### 5. 게이트

- `pnpm test` 전체 green
- `pnpm typecheck` 통과
- 버그성 항목마다 red → green 전이가 실제로 관측됨

### 6. 자체 검증

`/implement`의 4관점(불변식·원칙·타입경계·단순성)을 수정분에 적용. 새 🔴/🟡가 나오면 해소(최대 2회 루프).

## 리포트

```
🔧 refactor
수정: <n>건 (버그성 <a> / 품질성 <b>)
1. <항목> — <무엇을 어떻게>  [회귀 테스트: <파일> red→green]
...
스킵: <항목> — <이유>
확인 필요(중단): <항목> — <왜 강행하지 않았는지>
테스트: <n> passed / typecheck: OK
자체 검증: 🔴 0 / 🟡 0 / ⚪ <n>
```

## 금지 사항

- **커밋·빌드 금지.**
- **버그성 항목을 테스트 없이 고치기 금지.**
- **회귀 위험 지점 강행 금지** — 4단계에 걸리면 중단하고 확인받는다.
- **범위 확장 금지** — 지정된 항목만. 옆에 보이는 다른 문제는 리포트에 적고 넘어간다.
- **테스트 삭제·약화 금지.**
