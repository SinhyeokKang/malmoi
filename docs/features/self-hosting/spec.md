# Self-hosting — 스펙

작성: 2026-10-08 · 기준: v1.2.4 · 상태: 사전 초안, 구현 미착수

## 1. 목적과 사용자

개발자가 자신의 서버에서 말모이를 설치·업데이트·복구할 수 있는 공식 경로 하나를 제공한다. 번역 편집자는 기존 UI와 권한 모델을 그대로 사용한다. MIT 라이선스와 별개로, 실제 운영 가능한 배포물을 제공하려는 제품 결정이다.

이번 요청은 스펙 작성까지다. 구현 일정·배포·이미지 공개는 승인된 작업이 아니다. 구현 전 [확인 사항](#7-확인-사항)을 확정하고 현재 코드와 다시 대조한다.

## 2. 관측된 문제

- 앱은 Vercel, 업로드는 Vercel Blob, 야간 작업은 Vercel Cron을 사용한다. Dockerfile만 추가하면 업로드와 야간 작업은 여전히 해당 서비스에 의존한다.
- DB 런타임은 Postgres지만 자격증명 운영 명령은 두 Supabase 프로젝트를 허용 대상으로 고정한다.
- 로그인·GitHub 연결·MCP·생성 워크플로·메일·공개 메타데이터에 서비스 도메인 전제가 있다. 일부 경로는 알 수 없는 origin에서 호스팅 서비스 주소로 되돌아간다.
- 독립 설치를 위한 영속 저장소, 전체 마이그레이션, 암호화 키 보관, 백업 복원 절차를 함께 검증하는 배포 계약이 없다.

근거 파일과 변경 경계는 [설계](design.md)에 기록한다.

## 3. 1차 범위 — 제안

공식 지원 경로는 Linux 단일 서버의 Docker Compose다. 앱 한 인스턴스, 일반 Postgres, 파일 업로드 볼륨, 야간 스케줄러를 운영한다. HTTPS reverse proxy 뒤의 도메인 루트에 설치한다. 서브패스 배포는 지원하지 않는다.

GitHub.com 리포 연동과 GitHub·Google OAuth 로그인은 유지한다. 운영자는 자기 OAuth App·GitHub App을 등록한다. 초대 메일은 **Resend 유지안을 가정**한다. 따라서 외부 연결이 필요한 셀프 호스팅이며 폐쇄망 배포는 아니다. GitHub Actions에서 설치 주소에 접근할 수 있어야 한다.

배포물은 버전과 digest가 고정된 앱·운영 도구 이미지 및 Compose 설정을 제안한다. 최초 검증 아키텍처는 linux/amd64다. 레지스트리·Postgres major·최소 자원은 구현 착수 전 검증으로 확정하며, 지원한다고 선기재하지 않는다.

## 4. 완료 조건

| ID | 수용 기준 |
|---|---|
| SH-01 | 빈 서버에서 문서에 적힌 외부 앱 등록·환경 설정 후 Compose로 설치한다. Vercel·Supabase 계정과 자격증명이 없어도 로그인과 프로젝트 생성이 된다. |
| SH-02 | 빈 일반 Postgres에 기존 마이그레이션 전체가 적용된다. 실패하면 웹·스케줄러가 시작되지 않는다. 런타임 DB 계정은 superuser가 아니며 DB 포트는 외부에 공개하지 않는다. |
| SH-03 | GitHub·Google 로그인, 계정 연결·해제, 세션 폐기, GitHub App 설치·연결이 설치 도메인에서 왕복한다. 위조 Host/forwarded header는 신뢰 주소를 만들지 못한다. |
| SH-04 | 생성된 GitHub Actions 워크플로가 설치 주소로 push한다. 편집 후 Publish가 대상 리포 PR에 반영되고 재실행은 불필요한 커밋을 만들지 않는다. 미전달 편집·열린 PR 보호도 유지한다. |
| SH-05 | MCP 개인 토큰과 OAuth 발견·동의·교환이 설치 주소에서 동작한다. 토큰 issuer/resource가 호스팅 서비스 주소로 대체되지 않는다. |
| SH-06 | 프로필·프로젝트 이미지 업로드·표시·교체가 동작한다. 컨테이너 재생성 뒤에도 유지되며 traversal·symlink로 볼륨 밖 파일을 읽거나 쓰지 못한다. |
| SH-07 | 설정된 초대 메일이 설치 주소와 해당 인스턴스의 이미지를 사용한다. 설정 오류·발송 불명확 상태는 기존 실패 계약대로 보인다. 메일 미설정을 정상적인 팀 온보딩 완료로 간주하지 않는다. |
| SH-08 | 스케줄러가 기존 시각인 매일 18:00 UTC에 기존 `/api/pull`을 호출한다. 200 응답 안의 프로젝트 실패·미처리도 운영 로그에서 구분된다. |
| SH-09 | 동일한 앱 이미지 digest를 서로 다른 두 origin에서 실행해 각 인스턴스의 기능 URL을 확인한다. 비밀은 빌드에 필요하지 않으며 이미지·클라이언트 번들·로그에 포함되지 않는다. |
| SH-10 | DB·이미지·키를 백업해 빈 볼륨에 복원한 뒤 로그인, 번역 조회·편집, 이미지, 자격증명 복호화와 리포 왕복을 검증한다. 키 회전·검증 도구도 일반 Postgres에서 동작한다. |
| SH-11 | 이전 지원 릴리스에서 업그레이드하고 실패 시 복구한다. 역마이그레이션 없이도 가능한 복구 절차와 중단 시간이 문서에 명시된다. 첫 릴리스는 직전 스키마 fixture로 절차를 검증한다. |
| SH-12 | 셀프 호스팅은 검색 노출을 차단하는 robots/noindex를 제공하고 Vercel Analytics를 실행하지 않는다. 개인정보 안내는 실제 운영자가 제공한 정책으로 연결된다. 이는 접근 제어를 대신하지 않는다. |
| SH-13 | 기존 hosted production/preview의 origin 정책, Blob, Cron, SEO, Analytics, 메일 동작에 회귀가 없다. 전체 단위·DOM 테스트와 타입 검사 및 양쪽 배포 smoke가 통과한다. |

## 5. 비목표

- Kubernetes, 다중 인스턴스, 고가용성, 무중단 업데이트, 자동 업데이트, 여러 DB·저장소 provider를 위한 범용 플러그인.
- 폐쇄망, GitHub Enterprise·GitLab, 로컬 비밀번호·SAML·이메일 로그인, 초대 전용 가입 정책 추가.
- SMTP는 메일 범위 결정 전까지 포함하지 않는다. 메일 큐·자동 재시도·일반 알림도 추가하지 않는다.
- SaaS와 셀프 호스팅 사이 계정·프로젝트 이전, 서로 다른 인스턴스 병합, 기존 Blob 일괄 이관.
- 관리 콘솔·설치 마법사·화이트라벨·쿼터 변경. 기존 운영자 예외와 ProjectMember 인가를 유지한다.
- 번역·키·이력 보존 규칙, push/편집/pull 계약, export 알고리즘 변경.

## 6. 범위 게이트

[PRODUCT](../../PRODUCT.md) §4.2에 셀프 호스팅은 비범위로 지정되어 있지 않다. §4.3의 이메일 로그인·웹훅을 요구하지 않는다. [ARCHITECTURE](../../ARCHITECTURE.md) §0의 불변식 열하나를 유지하므로 초안 작성 범위 게이트를 통과한다.

신규 UI 표면이 없는 배포 기능이므로 `design-brief.md`는 만들지 않는다. 실제 구현에서는 PRODUCT의 배포 범위와 OPERATIONS의 설치·복구 안내를 함께 갱신한다.

## 7. 확인 사항

| 항목 | 초안의 제안 | 상태 |
|---|---|---|
| 메일 범위 | Vercel·Supabase 의존을 제거하고 초대 메일은 Resend 유지 | 사용자에게 질문함, 답변 미확정. SMTP를 선택하면 설계·태스크 재검토 후 구현 |
| 배포 지원 폭 | 단일 서버 Compose, linux/amd64, 버전 고정 이미지 | 초안 제안. 레지스트리 공개 권한·이미지 발행 경로는 착수 전 확정 |
| 배포 검증 값 | Postgres major 하나·최소 CPU/RAM·디스크 여유·복구 실측 시간 | 컨테이너 검증에서 기록. 임의 성능·가용성 보장 없음 |

후속 구현은 이 문서만으로 시작하지 않는다. 메일 범위를 확정하고 feature review 뒤 [태스크](tasks.md)를 진행한다.
