# pull — DB → `l10n/sync` PR

MVP §8 구현 순서 **6단계**. 스펙 원본은 [MVP.md §3.3](../../MVP.md), 불변식은 [ARCHITECTURE.md §1.4·§2·§3](../../ARCHITECTURE.md), 태스크 원본은 [TASKS.md §6](../../TASKS.md).

TASKS §7에 있던 왕복 검증 항목도 이 단계로 당긴다 — 수동 트리거만으로 가능하고, 7단계(Actions·Cron 배선)는 왕복이 검증된 뒤에 붙여야 배선 오류와 pull 오류를 구분할 수 있다.

## 사용자

**둘 다** — 이 흐름이 두 사람의 요구가 만나는 지점이다.

- **번역 편집자**: 자기가 고친 값이 실제 제품으로 돌아가는 것을 본다. 지금은 편집이 DB에만 쌓이고 나가는 길이 없어, 편집 UI가 무엇을 위한 것인지 증명되지 않은 상태다.
- **개발자(나)**: 번역을 손으로 옮겨 심는 일이 사라진다. 리뷰할 것은 PR 하나다.

## 문제

**세 흐름 중 마지막 하나가 비어 있고, 그래서 파이프라인이 아직 닫히지 않았다.**

관측된 사실:

- 실 DB에 사람이 편집한 번역이 6건 있고 그중 **bugshot-2 소속은 4건**이다 (`actionLog.empty` ko, `attachment.download` ko/en/fr). 나머지 2건(`auth.change` ko, `auth.accountInfo` ko=`""`)은 **skillflo** 소속이라 이 단계의 검증 대상이 아니다(비목표 6). 전부 `updatedBy = SinhyeokKang`.
- 그 값이 리포로 돌아갈 경로가 **없다.** `/api/pull`이 미구현이고 cron도 없다.
- 그래서 **편집 손실 창의 방어가 현재 0이다** (MVP §3.1의 ⚠️ 블록). 대상 리포에 push를 한 번 더 돌리면 위 편집이 리포 값으로 덮여 사라진다 — strict 정책의 대가인데 완화 수단이 아직 서 있지 않다.

## 완료 조건

**검증 가능한 문장으로.** 각 완료 조건은 `tasks.md`에 대응하는 검증 줄이 있다.

1. **`l10n/sync` 브랜치에 PR이 하나 열린다** — bugshot-2 대상, DB의 편집 4건이 반영된 상태로. **편집된 키가 걸치는 `ts-dict` 파일 전부가 갱신된다** — write는 파일당 1회 계약이라(§1.4) 호출부 루프가 빠지면 첫 파일만 갱신되고 조용히 통과한다.
2. **PR diff에 바뀐 줄만 뜬다** — `ts-dict`가 수술적 치환이므로 빈 줄·주석·키 순서가 보존된다. 파일 전체가 재정렬돼 나오면 실패다. 빈 문자열 보존은 4단계에서 bugshot-2 키 하나를 UI에서 지워 만든 편집으로 검증한다(실 DB의 빈 값 케이스는 skillflo 소속이라 이 왕복을 지나지 않는다).
3. **두 번째 pull이 no-op이다** — 1회차 성공이 `lastPulledAt`을 갱신하므로 2회차는 1층(DB 측 스킵)에서 끝난다. **결정성(2층) 검증은 따로 한다**: `lastPulledAt`을 과거로 되돌려 강제로 2층에 진입시키고, blob SHA 전부-동일로 종료되는지 확인한다. *(한 번 열리는 것은 결정성을 증명하지 않는다 — 이게 깨지면 야간 cron이 매일 무의미한 커밋을 만들고, 며칠 뒤에나 발견된다.)*
4. **편집이 없으면 GitHub API를 한 번도 부르지 않는다** — DB 측 스킵(1층)이 먼저 걸린다. **주입된 fake 클라이언트로 호출 0회를 세는 테스트**로 확인한다 (TASKS §6이 지정한 형태).
5. **첫 실행 경로가 동작한다** — `l10n/sync`가 없을 때 `POST /git/refs`, 있을 때 `PATCH` + force.
6. **`CRON_SECRET` 없이 호출하면 거부된다** (fail-closed).
7. **커밋이 base 트리를 보존한다** — 트리 요청에 `base_tree` 포함(빠지면 리포의 나머지 파일이 전부 삭제된 커밋이 된다), 커밋 메시지에 `[skip-l10n]`(없으면 7단계 배선 시 무한 루프). 둘 다 순수 테스트로 판정한다.
8. **왕복이 닫힌다** — PR 머지 → 대상 리포에서 push → DB가 리포 값과 일치. 편집이 리포에 반영된 뒤이므로 **이번엔 덮여도 값이 같다.** 이것이 손실 창이 닫히는 것의 의미다.

## 비목표

- **Actions 워크플로·Vercel Cron 배선** — 7단계다. 6단계에서는 수동 트리거(편집 UI 버튼 + 직접 호출)로 검증한다.
- **웹훅 즉시 반영** — MVP §7 비범위. 손실 창을 줄이는 유일한 수단이 pull 주기라는 사실은 그대로 남는다.
- **PR 본문 꾸미기** — 변경 요약·통계 같은 것. 사람이 읽을 최소한만 쓴다.
- **여러 프로젝트 동시 pull** — 운영 대상은 `ACTIVE_PROJECT_SLUG` 하나다.
- **충돌 처리** — 정의상 없다. `l10n/sync`는 force update되는 스냅샷이다 (ARCHITECTURE §3).
- **skillflo 대상 pull** — 그쪽은 `lastCommitSha`가 더미(`aaaa…`)이고 `repoName`(`skillflo-web`) 실재 여부도 확인되지 않았다. 6단계 검증 대상은 bugshot-2 하나다.
