# inbox-filter-search — spec

> 2026-10-18 착수(사용자). `/inbox` 페이지(inbox-page, 2026-10-09)에 좁히는 도구를 더한다. **UI는 프로젝트 Logs 페이지의 필터 줄 패턴을 재사용한다**(사용자). 프로젝트도 드롭다운 필터로 고른다(사용자). 코드 착수는 language-request-todo가 dev에 들어간 뒤다 — 그 기능이 Inbox 항목 종류(`language_unsent`)와 렌더(`lib/inbox/**`·`components/inbox/**`)를 바꾼다.

## 사용자

**둘 다다.** Inbox는 두 역할 모두의 할 일 목록이다(PRODUCT "Attention inbox"). 프로젝트가 여럿이고 할 일이 쌓인 사람이 "이 프로젝트의 것만", "검토 대기만"을 보려 한다.

## 문제 (관측된 사실)

- `/inbox`는 비보관 멤버 프로젝트의 현재 할 일을 **상한 없이** 프로젝트별 카드로 전부 보인다(`components/inbox/inbox-list.tsx`). 좁히는 도구가 없다 — 프로젝트·항목 종류로 거르거나 이름으로 찾을 수 없다.
- 같은 앱의 Logs 페이지는 필터 줄(`FieldTrigger` 드롭다운 + `SearchInput` + `Clear filters`, URL이 상태)을 갖는다. Inbox는 그 형이 없다.

## 완료 조건 (검증 가능한 문장)

1. **필터 줄** — `/inbox` 머리 아래에 Logs와 같은 형의 필터 줄이 선다: 드롭다운 필터 **둘**(종류 · 프로젝트) + `Clear filters`(좁힘이 있을 때만) + 끝에 `SearchInput`. DOM 테스트.
2. **종류 필터** — 단일 선택(`All` + 항목 종류). 고르면 그 종류의 항목만 남는다. 순수 함수 단위 테스트.
3. **프로젝트 필터** — 다중 선택(`DropdownMenuCheckboxItem`, Logs Source 축과 같은 형). 고른 프로젝트의 카드만 남는다. 선택지는 Inbox에 항목이 있는 프로젝트다. 순수 함수 단위 테스트 + DOM 테스트(`role="menuitemcheckbox"`).
4. **검색** — 질의가 항목의 보이는 글자(프로젝트 이름 · 보조줄의 소스 slug · 언어 이름·코드)에 대소문자 무시 부분 일치하면 남는다. 순수 함수 단위 테스트.
5. **URL이 상태다** — 좁히는 축은 전부 쿼리(`?kind=` · `?project=` · `?q=`)에 산다. [Apply]가 없고 고를 때마다 URL이 바뀌어 서버가 다시 그린다. 새로고침·뒤로 가기·공유가 그대로 된다. 알 수 없는 값은 무시한다(파서 단위 테스트).
6. **빈 결과** — 좁힌 결과가 0이면 Logs의 `NoMatch`와 같은 형의 "맞는 항목 없음" 상태가 선다(필터가 없을 때의 빈 상태 `All clear`와 구별된다). DOM 테스트.
7. **헤더 드롭다운·배지는 그대로다** — 필터는 페이지에만 있다. 배지 수·드롭다운 목록은 좁힘의 영향을 받지 않는다. 기존 테스트 green.
8. **필터 트리거는 한 벌이다** — Logs의 지역 `Filter` 조각을 `components/ui/`의 프리미티브로 옮기고 Logs·Inbox가 같이 쓴다(손 사본 0). Logs 동작은 그대로다(기존 Logs 테스트 green).

## 비목표

- **헤더 드롭다운의 필터·검색** — 360 폭 메뉴는 결과 목록 행이고, 거르는 도구는 페이지가 든다.
- **안 읽음 축** — 페이지를 열면 읽음이 기록되므로(`MarkSeen`) 새로고침 뒤 늘 비게 된다. 넣지 않는다.
- **기간 축** — 항목은 사건이 아니라 지금 상태다(검토 시각은 push가 덮는다 — inbox-list 머리 주석).
- **서버 쪽 좁힘** — 항목은 이미 한 번에 다 읽힌다(`loadAttentionInbox`). 조회를 바꾸지 않고 읽은 계획을 순수 함수로 거른다.
- **새 시각 디자인** — Logs 패턴 재사용이라 Claude Design 시안을 받지 않는다.
- **스키마·환경변수** — 없다.
