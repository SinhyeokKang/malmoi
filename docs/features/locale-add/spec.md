# Add and remove languages — 스펙

작성: 2026-10-13 · 개정: 2026-10-14(2차 검수 반영) · 상태: **추가·삭제 범위 합의 완료 · 구현 전 설계 검증·시안 대기**

slug는 `locale-add`를 유지한다. 범위는 웹 UI와 MCP에서 **소스별 언어 추가·제거·취소**다. 키 추가·삭제는 별개다. 이번 개정은 2026-10-14 사용자 승인에 따른 것으로, 옛 스펙의 “추가만 지원 · 취소는 수동 Sync” 결정을 대체한다.

## 1. 목적과 사용자

OWNER가 소스 상세에서 언어를 추가하면 번역자가 바로 편집하고, Publish가 새 파일을 PR/MR에 싣는다. 잘못 추가한 언어는 개별 취소하고, 더 이상 지원하지 않는 언어는 같은 화면에서 제거를 요청해 Publish로 파일 삭제를 전달한다.

1순위 사용자는 번역 편집자(비개발자 동료)다. 개발자에게 빈 파일 생성이나 파일 삭제를 따로 부탁하지 않고 언어 구성을 관리한다. 파일 집합을 바꾸는 결정은 OWNER(`project:settings`)만 한다. EDITOR는 활성 언어의 번역을 편집한다.

**제거는 DB 데이터를 보존하는 비파괴 동작이며, 리포 파일 삭제와 앱 비활성화를 뜻한다. 로케일 행·번역 값·활동 이력은 물리 삭제하지 않는다.** 언어 지원 중단에 필요한 애플리케이션 코드·라우팅·설정 파일 수정은 이 기능이 대신하지 않는다. 대신 제거 확인 Dialog와 PR/MR 본문이 그 정리가 필요하다고 경고한다(수락 기준 7).

## 2. 관측된 문제

- 언어를 추가·제거하려면 개발자에게 리포 파일 생성·삭제를 부탁해야 한다. 앱에는 요청할 길이 없다(PRODUCT §7.2).
- 옛 추가 스펙은 “추가는 여기서, 삭제는 리포에서”였고, 방금 추가한 제안 하나의 취소도 프로젝트 수동 Sync를 요구했다. 개별 변경을 되돌리는 범위보다 넓다.
- 요청 근거는 사용자 결정(2026-10-13 추가, 2026-10-14 삭제 포함)이다. 별도 이탈·이슈는 관측하지 않았다.

현재 코드의 공백(Publish 계약에 파일 삭제 없음, 보호 집계가 셀 토큰만 봄)은 design.md §0이 다룬다.

## 3. 범위와 원칙

**PRODUCT §7.2의 UI 로케일 추가·삭제 금지를 둘 다 해제하는 정본 개정을 구현 태스크 §0에 포함한다.** PRODUCT §4.2의 번역 생성·무제한 포맷 설정 UI는 범위에 들어오지 않는다.

| 항목 | 결정 |
|---|---|
| 지원 | `json-catalog`·`chrome-locales`, 소스별 단일 언어 추가·제거·취소 |
| 제외 | `ts-dict`·`yaml-catalog`·`code-dict`의 언어 구성 변경. 공유 파일 내부 객체 삭제도 제외 |
| 기준 언어 | 제거 불가. 리포에 있는 다른 활성 언어로 기준을 바꾼 뒤 제거 |
| 권한 | OWNER, 비보관 프로젝트. 웹과 MCP 같은 코어 |
| 저장 | 추가·제거 요청은 DB에서 확정. 리포 변경은 기존 Publish PR/MR 경로만 사용 |
| 보존 | 로케일·번역·사건 유지. 제거 후 같은 코드 재추가로 되살림 |
| 미전달 편집 | 제거·전달 전 추가 취소는 그 언어의 미전달 편집을 서버 지문 승인으로 폐기한 뒤 진행. 제거 중에는 편집 잠금 |
| 소유 | 제안된 파일 집합 변경은 DB의 명시적 의도. 의도가 만료되면 존재 여부는 다시 리포가 결정 |
| 병합 없음 | 추가·삭제 요청으로 목표 파일 집합을 계산. 리포 값과 DB 값을 비교해 승자를 고르지 않음 |
| 상한 | 추가 경로에 로케일 수 상한을 두지 않는다. 기존 `/api/push` 입력 상한(`MAX_LOCALES`)은 그대로 |

**전달과 리포 반영은 다르다.** PR/MR에 실린 제거 의도는 머지 전 재Publish에서도 유지한다. 머지 여부를 브랜치 부재나 HTTP 실패로 추측하지 않는다. 열린 PR/MR이 없음을 성공한 조회로 확인한 뒤 base 관측으로 실제 파일 집합을 확인한다(design §1).

## 4. 수락 기준

1. OWNER가 지원 소스에 언어 코드를 추가하면 목록과 번역 화면에서 즉시 편집 가능하다. 파일이 base에 확인되기 전에는 행에 `Adding` 배지가, 미전달이면 기존 `Unsent` 배지가 붙는다. Chrome은 지원 목록에서 선택한다.
2. 자동 적재는 페이로드에 없는 추가 제안을 orphan하지 않는다. 리포가 그 코드를 실제로 포함하면 기존 strict 적재로 일반 언어가 된다. 번역 편집 보호는 기존 규칙을 따른다.
3. 값이 하나 이상 있는 추가 제안을 Publish하면 새 파일을 만든다. 표현은 같은 소스의 base 파일에서 빌리되 구조는 빌리지 않는다. 같은 DB·같은 원본은 같은 바이트이고, 다음 Publish가 그 파일을 원본으로 읽어도 diff 0이다.
4. 번역 0개인 제안은 파일을 내지 않고 Publish 작업으로 세지 않는다. 미리보기는 파일이 아직 생기지 않는 이유를 표시한다. 빈 제안 하나로 자동 적재를 보류하지 않는다.
5. **전달 전 추가 취소**는 그 언어만 Inactive로 만든다. 그 언어에 미전달 편집이 있으면 미리보기가 그 수를 보여주고, 서버 지문을 승인해야 폐기된다. 다른 언어의 편집·제안은 바뀌지 않는다. 값과 사건은 남는다.
6. 기존 비기준 언어의 [Remove language]는 파일 경로·저장된 번역 수·미전달 편집 수를 보여주는 미리보기 뒤에 제거 예정으로 바꾼다. 미전달 편집이 있으면 승인 지문으로 폐기한다. 제거 예정 언어의 번역 저장·Revert는 서버가 거부한다.
7. 제거 확인 Dialog와 PR/MR 본문은 “앱 코드의 이 언어 참조(import·지원 언어 목록 등)를 정리해야 한다”를 표시한다.
8. **번역 편집 0건이어도 제거 요청만으로 Publish가 가능하다.** PR/MR에는 정확히 그 소스·언어의 파일 삭제가 들어가고, 미리보기·결과·Logs는 파일 추가(`New file`)·수정(`Updated`)·삭제(`Removed`)를 구분한다. 다른 파일·로케일 행·번역은 삭제하지 않는다.
9. 미전달 제거 요청이 있으면 CI·야간 적재는 전체 보류한다(새 deferred 사유). 전달 후에는 기존 열린 PR/MR 보호가 적재를 보류한다.
10. 제거 요청을 PR/MR에 전달한 뒤 다른 언어를 편집해 재Publish해도 삭제 diff가 남는다. 전달된 추가를 취소하면 다음 Publish의 PR/MR에서 새 파일이 빠진다.
11. **제거 취소**는 즉시 편집을 다시 허용한다. 이미 전달된 제거였으면 행에 `Unsent`가 붙고, 번역 편집 0건이어도 Publish가 이전 삭제 diff를 PR/MR에서 없앤다. 그 전까지 UI는 “취소 완료”라고 말하지 않는다.
12. 열린 PR/MR이 없다고 성공한 조회로 확인되고 현재 의도가 마지막 전달과 같으면 의도가 만료된다. 만료 때 base에 파일이 없으면 그 언어는 Inactive, 있으면 활성이다.
13. 머지 없이 닫혀 제거 대상 파일이 base에 남은 경우, 그 언어는 활성으로 돌아오고 제거 요청은 사라진다. 다시 제거하려면 새로 요청한다.
14. 의도 만료 판정은 같은 base SHA라 적재를 건너뛰는 야간 방문에서도 돈다. 만료된 요청은 새 PR/MR에 다시 실리지 않는다.
15. PR/MR 조회 실패·응답 유실·상태 불명은 만료로 접지 않고 의도를 유지한다.
16. 수동 Sync는 언어 변경과 미전달 편집을 함께 보여주고 서버 지문으로 승인받는다. 성공하면 리포 파일 집합대로 로케일 활성/Inactive가 정해지고 언어 변경 의도가 전부 사라진다. 다음 Publish는 폐기한 삭제를 다시 싣지 않는다. 다른 언어 하나를 취소하려고 Sync할 필요는 없다.
17. 제거 후 재추가는 같은 로케일 행과 값을 되살리고, 값 있는 활성 셀에 새 편집 토큰을 발급한다. 기준이 없는 셀의 Revert는 기존 규칙대로 비활성이다.
18. 기준 언어 제거·제거 예정/추가 중 언어의 기준 승격·비지원 포맷·잘못된 코드/경로·중복 코드·대소문자/구분자 충돌·보관·EDITOR·결과 미확정 Publish·오래된 승인 지문을 사유 코드로 거부하고 DB를 바꾸지 않는다.
19. 추가·제거·취소·만료는 `Project`→`TranslationSurface` 잠금과 같은 tx의 사건을 따른다. Publish는 스냅샷 때 캡처한 의도만 전달 확인한다. 실행 중 새 요청이나 취소가 과거 실행의 확인으로 사라지지 않는다.
20. 신규 제안 경로가 이미 base에 있으면 그 언어만 보류한다. 제거 대상 경로의 소유·형식·파일 상태가 확인 불가능하면 삭제를 수행하지 않는다. 같은 경로에 쓰기·삭제가 함께 계획되면 실패한다.
21. GitHub·GitLab에서 같은 시나리오(tasks §9의 roundtrip 매트릭스)가 같은 결과를 낸다. MCP도 추가·제거 미리보기·제거·제거 취소를 같은 코어로 제공한다.
22. en·ko·es 문구를 함께 반영하고, 화면 문구는 호스트별 어휘(pull request / merge request)를 쓴다. 제거 예정은 진행률·Keys 검색·Inbox의 작업 대상에서 제외하고 Sources에는 상태를 남긴다. 추가 제안은 활성 작업 대상이다.
23. 다른 세션의 제거가 도착하면 그 언어의 미저장 셀 입력은 읽기 전용으로 남고 저장에서 빠진다. 셀 단위 되돌리기로 버릴 수 있고, 제거 취소 뒤에는 그대로 편집할 수 있다. 이동 시에는 기존 이탈 확인이 그 입력도 센다.
24. orphan 상태는 기존 danger 톤으로 `Inactive`라고 표시하고, 원인(“리포에서 제거됨”)을 단정하지 않는다. 지원 포맷의 OWNER에게는 Add language로 같은 코드를 재추가하는 복구 경로를, 비지원 포맷에는 리포 복구 후 Sync 경로를 안내한다.

## 5. 비목표

- 키 추가·삭제, 번역·로케일·이력의 영구 삭제.
- 수술적 포맷의 언어 구성 변경, 기준 언어를 없애는 동작, 여러 소스·언어 일괄 변경.
- 앱 코드·언어 선택기·Chrome manifest 등 로케일 파일 외 설정 자동 변경.
- 로케일 이름·깃발 편집, 기계 번역, base 값 복사로 채우기.
- 새 파일 표현의 base 외 출처, 새로운 PR/MR 전략이나 3-way merge.
- webhook·실시간 PR/MR 상태 반영(PRODUCT §4.3 ②). 머지·종료 반영은 다음 야간 방문 또는 Publish까지 최대 하루 늦을 수 있다. Sources는 화면 진입 시 PR/MR을 조회하지 않는다.
- 앱에서 PR/MR을 닫거나 되돌리는 동작.
- 추가 경로의 로케일 수 상한.
