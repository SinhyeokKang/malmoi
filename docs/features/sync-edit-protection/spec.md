# spec — Sync 편집 보호와 PR 인계

상태: CPO·CDO·CTO·QA **4차 검수**로 범위를 다시 좁혔다 — 열린 PR 대비 파일 diff(옛 완료 조건 11)와 D2를 이 spec에서 뺐다. 구현은 T0만 완료다.

## 이 기능이 정본 다섯 자리를 뒤집는 근거

`ARCHITECTURE.md` §5.5.2와 `CLAUDE.md`·`AGENTS.md`의 코어 원칙 절은 편집 손실 창에 대해
**"이 위험을 코드에서 지우려 하면 곧 변경 감지·병합이 되어 코어 원칙을 깬다 — 완화는 pull 주기를 줄이는 쪽에서만 한다"**
고 단언한다. `.claude/commands/audit.md`와 그 Codex 미러는 "편집 손실 창(ARCHITECTURE §0 불변식 2)을 완화하려는 코드가 몰래 들어왔는지"를
상시 감사 항목으로 든다. **이 기능은 그 판정을 바꾼다. 근거는 다음 하나다.**

§5.5.2가 금지한 것은 **변경 감지와 병합**이다. 이번 설계는 둘 다 하지 않는다 —
**자동 Sync 판정은 리포를 보지 않는다.** 미전달 편집이 하나라도 있으면 그 프로젝트의 자동 적재를 통째로 보류하고,
편집이 0이면 기존 strict 적재를 한 줄도 바꾸지 않고 그대로 돈다. 리포 값과 DB 값을 견주는 코드가 없으므로
승자를 고르는 자리도, 3-way merge도, 충돌 해소 UI도 생기지 않는다.
**대가는 정확히 하나다: 미전달 편집이 남아 있는 동안 리포의 새 소스 키·삭제도 앱에 들어오지 않는다.**
즉 손실을 막는 값이 "적재가 늦어짐"이고, 병합이 아니다.

(Publish는 오늘도 base 트리를 읽는다 — `lib/publish/read.ts`의 미리보기와 `lib/pull/`의 2층 blob SHA 비교다. 그것은 이번에 바뀌지 않는다.
"리포를 보지 않는다"는 **자동 Sync 판정**의 성질이다.)

구현이 끝나면 위 다섯 자리를 이 근거로 갱신한다(T14). 갱신하지 않으면 다음 `/audit`이 이 기능을 회귀로 보고한다.

## 사용자와 목적

- 번역 편집자(EDITOR): 저장한 번역이 자동 적재 때문에 사라지지 않고 PR로 전달되기를 원한다.
- 개발자(OWNER): 코드를 정본으로 유지하고, 일반 코드 커밋 때문에 번역 작업이 막히지 않기를 원한다.
- **상충하면 편집 보존을 우선한다.** 거친 보류는 개발자의 요구("코드 커밋이 막히지 않기를")를 일부 희생한다 —
  미전달 편집이 있는 동안 코드 push는 성공하지만 그 커밋의 로케일·키 변경이 앱에 반영되지 않는다.
  되돌릴 수 있는 쪽(적재 지연)을 되돌릴 수 없는 쪽(편집 소실)보다 뒤에 둔다.
- **개발자가 보류를 아는 자리는 둘이다** — Actions 로그의 응답 본문(`"status":"deferred"`, 구 태그도 그대로 찍힌다)과
  Home `To send` 카드의 보조 줄(`repository updates paused`). 새 태그(T16)는 `::warning` 주석을 더한다.
- 앱의 책임은 저장한 편집의 보호와 PR 전달까지다. 머지·배포는 GitHub와 개발자가 맡는다.

## 범위 게이트

PRODUCT §4.2 비범위에 해당하지 않는다 — 승인 워크플로("To review"는 승인이 아니다, §4.2 `needsReview` 문장)·실시간 공동 편집·
범용 알림(이메일)을 만들지 않는다. ARCHITECTURE §0 불변식 2가 금지하는 값 병합·충돌 해소 UI도 만들지 않는다.
PRODUCT §4.3의 2차 항목(webhook 등)도 추가하지 않는다. 결정성(§0)은 유지한다.

**갱신 대상 정본은 다섯이다**(전부 T14): `docs/ARCHITECTURE.md` §5.5.2 · `CLAUDE.md` 코어 원칙 절 ·
`AGENTS.md` 미러 · `.claude/commands/audit.md` · `.agents/skills/source-command-audit/SKILL.md`.
여기에 PRODUCT §3·§4.1·§7.6, ARCHITECTURE §0 불변식 1(보류 중 유예)·§2·§3·§5.5.7, DESIGN(배너·카드 갈래·§6.2 Alert 표),
DIRECTORY(새 모듈 + "표시 전용"·"세 벌" 두 문장), ACTIONS(`deferred` 응답), OPERATIONS(A→backfill→B 절차)가 더해진다.

**launch-readiness와 겹치는 다섯(L3.10·L3.5·L7.2·L3.3·L2.9)은 이 spec이 소유한다.** 그쪽은 L1.5 포인터로 접는다 —
먼저 닫는 쪽이 다른 쪽 단언을 무효화하는 순서 문제라 한 문서가 순서를 쥔다(T14).

## 범위에서 제외 확정된 것

- **리포 기준본(blob SHA manifest)과 CI의 트리 조회.** (3차) 완료 조건 대부분이 이것 없이 만족되고,
  단독으로 요구하는 것은 "보류를 더 좁게 건다"는 개발자 편의뿐이었다. 손실 방지 보장은 거친 보류와 같다.
  따라서 `PushPayload`의 manifest 확장·새 CLI·새 action 태그 릴리스도 전부 제외다.
- **빈값·누락 셀의 strict 적재 보완.** (3차) 이것은 "편집을 보호한다"가 아니라 **"덮어쓰기가 덜 덮는다"는 반대 방향의 별건**이고,
  `lib/push/apply.ts`의 `t.value !== ""` 필터가 만드는 구멍은 오늘의 수동 Sync에도 이미 있다.
  더 중요하게 `lib/adapters/shared.ts`의 `.filter((e) => e.message !== "")`가 재생성 writer 전체에 걸려 있어
  **`value = ""`는 "빈 값 기록"이 아니라 그 키를 파일에서 제거하는 것**이다.
  **별도 spec으로 분리하며, 그쪽에서 "명시적 빈값"과 "미번역 빈값"을 export가 구별하는 수단을 먼저 정한다.**
- **운영 차단·drain.** (3차) 배포 A가 이미 dual-write하므로 drain의 유일한 목적("옛 writer가 토큰 없이 저장")은
  A의 롤아웃 완료로 해소된다. backfill을 멱등·수렴형으로 만들어 절차 자체를 없앤다(design §6).
- **열린 PR 대비 파일 diff·페이지네이션·전 페이지 열람 게이트·미리보기 승인 지문.** (4차) 이것만으로 Claude Design 핸드오프 선행·
  `components/ui/`에 없는 pagination 프리미티브·DESIGN §6.2 "초록·빨강을 넓히지 않는다" 개정·EDITOR의 열린 PR 인가 재판정
  (`checkOpenPullRequest`가 `project:settings`라 EDITOR는 열린 PR을 영영 모른다 — ARCHITECTURE §5.6.35)이 딸려온다.
  launch-readiness L3.3은 같은 모달에 "새 갈래를 그리지 않는다(결정됨)"를 닫아 뒀다. "편집 보호"와 "PR 인계 검토"는 문제도 사용자도 다르다.
  **별도 spec `publish-pr-handoff`로 분리한다.** 그 전까지 Publish 미리보기는 오늘처럼 base 대비 목록이고 실행 게이트가 아니다(§5.6.35 유지).
- **D2(열린 PR이 있으면 야간 Publish가 새 편집이 있어도 안 씀).** (4차 철회) 번역 PR은 개발자가 머지할 때까지 며칠 열려 있는 것이 보통이라
  D2는 야간 Publish를 사실상 끈다. cron은 오늘처럼 열린 PR도 갱신한다 — 그것은 "현재 DB 전체 스냅샷으로 PR 갱신"이지 병합이 아니다.

## 문제 — 현재 코드에서 확인한 사실

1. `lib/push/apply.ts`는 기존 번역 값을 덮고 `updatedBy`를 비운다. 편집부터 Publish까지의 짧은 구간에도 손실이 가능하다.
2. ~~자동 Publish의 스킵이 `max(updatedAt)`와 `lastPulledAt` 비교라 사람 편집 없이도 PR을 갱신할 수 있다~~ —
   **T0(2026-09-17)로 닫혔다.** `shouldSkipPull`이 `unpublishedWhere`(`updatedBy IS NOT NULL ∧ 활성 표면 ∧ updatedAt > lastPulledAt`) 건수로 판정한다.
3. ~~`changes.length === 0` 경로의 sync 브랜치 되돌림이 편집 없이도 닿는다~~ — 같은 T0로 1층 뒤에만 닿는다.
   **남는 것은 시각 술어의 한계다**: 같은 밀리초의 재저장(완료 조건 7)을 `DateTime`으로 구별할 수 없고, Publish가 캡처한 편집과
   그 뒤 들어온 편집을 정확히 가르려면 편집의 **식별자**가 필요하다.
4. 현재 미전달 술어는 저자·시각 기반이고 **손 사본 넷 + 공유 조각 하나**다 — `isUnpublished`(`lib/keys/view.ts`),
   목록 raw SQL ⑤(`lib/keys/query.ts`), **Publish 캡처의 `where`**(`lib/publish/read.ts`), 메모리 하네스(`app/(edit)/__tests__/harness.ts`),
   그리고 `countUnpublished`와 pull 1층이 공유하는 `unpublishedWhere`(`lib/keys/unpublished.ts`).
5. CI는 표면별로 요청하고, 수동 Sync는 프로젝트의 활성 표면을 순회하며, Publish는 모든 활성 표면의 PR 하나다.

**발생 빈도는 측정하지 않았다.** 사용자 데이터 손실 기록은 0건이다. 그러나 **손실 경로 1건은 실증됐다** — POSTMORTEM 2026-09-17:
번역 PR을 merge commit으로 머지하면 루프 마커가 사라져 push가 DB를 Publish 시점 값으로 덮었고, 그 사이 저장한 번역이 사라진다
(폐기용 리포에서 재현). 마커는 고쳤지만 **strict 적재가 열어 두는 창 자체**는 그대로이고, 이 spec의 거친 보류가 정확히 그 창(Publish→머지 사이 저장)을 막는다.
현재 대응은 `components/translations/edit-loss-banner.tsx`의 경고 배너와 EDITOR도 실행 가능한 수동 Publish다.
범위를 거친 보류로 줄인 이유가 이것이다 — 미측정 문제에 최대 규모를 걸지 않는다.

## 용어

- Sync: 리포 → 앱. CI 자동 적재와 OWNER의 수동 Sync를 포함한다. **구현 위치는 `lib/push/`·`lib/import/`다.**
- Publish: 앱 → PR. 수동 실행과 기존 야간 실행을 포함한다. **구현 위치는 `lib/sync/`·`lib/pull/`다**(디렉터리 이름이 방향과 반대다).
- 미전달 편집: 활성 표면·활성 키·활성 로케일에서 서버에 저장됐고 아직 전달 확인되지 않은 셀의 최신 수정.
  현재 사용자뿐 아니라 프로젝트 멤버 전체의 수정이다. orphan 번역 값은 보존하지만 미전달 집계·Publish 대상에 넣거나
  전달 성공으로 처리하지 않는다.
- 보류(deferred): 미전달 편집이 있어 자동 적재를 실행하지 않은 것. **저장되는 상태가 아니라 pending > 0에서 파생된다.**

## 동작 계약

### 자동 Sync (CI `/api/push`)

판정 범위는 **프로젝트 전체**다. 인가·보관·포맷·역행·실행권 검사를 먼저 통과해야 한다.
**리포를 조회하지 않는다** — GitHub 호출이 0회 늘어난다.

| 미전달 편집 | 동작 |
|---|---|
| 있음 (프로젝트 전체 어느 활성 표면이든) | **프로젝트 전체 자동 적재 보류.** 키·번역·저자·미전달 표시·Project·TranslationSurface 전부 불변(진행 표시 포함). 응답 `deferred` |
| 없음 | 기존 strict 적재를 실행. 리포가 정본이므로 이미 전달한 앱 값도 리포 값으로 덮을 수 있음. 적용 뒤 재집계에서 pending이 생겼으면(판정과 적용 사이에 커밋된 저장) 전체 롤백 → `deferred` |

- **응답 계약**: HTTP 200 본문에 닫힌 union `status: "applied" | "deferred"`. `deferred`는 `reason: "pending-edits"`와 `pendingCount`를 든다.
  기존 실제 오류는 4xx/5xx 유지 — `failed`는 상태 값이 아니라 HTTP 오류다. 보관 프로젝트는 pending과 무관하게 기존 409다(가드가 먼저다).
- **보류 중에는 리포의 새 소스 키·삭제·로케일 추가도 앱에 들어오지 않는다.** 편집자는 코드에 이미 있는 키를 못 보고,
  화면과 코드가 갈린다. 이것이 거친 보류의 대가이며 화면이 그 사실을 말해야 한다.
- CI는 표면별로 요청하더라도 같은 프로젝트 전체 게이트를 통과한다. pending이 없는 기존 표면별 적재를
  일괄 트랜잭션으로 바꾸는 것은 이번 범위가 아니다.
- 보류는 실패나 적재 성공이 아니다. 다음 CI 요청 또는 수동 Sync/Publish 시 다시 평가한다.
- 자동 폐기·대기열·타임아웃 폐기는 없다. 보류 후 새 이벤트가 없어도 UI가 파생 상태(pending > 0 ⇒ paused)와 수동 해소 경로를 보인다.
- **비파괴 출구가 둘이다**: ① 편집을 Publish해 PR로 보내면 pending이 0이 되어 적재가 재개된다.
  ② OWNER가 폐기를 승인하면 즉시 적재한다. 화면은 **①을 먼저** 제시한다.
- **저장 경로에 잠금을 넣지 않는다.** 사람이 타이핑하는 경로다. 보존은 적재 쪽이 책임진다 — strict upsert가 토큰 있는 셀을 건드리지 않고(`WHERE "pendingEditToken" IS NULL`),
  적용 뒤 재집계로 "판정 뒤 들어온 저장"을 잡아 롤백한다. 편집은 살고 적재만 다음 요청으로 미뤄진다.

### 수동 Sync

- OWNER 전용 유지. 미전달 편집이 있으면 확인 Dialog를 표시한다.
- **문장을 늘리지 않는다.** 기존 `repositorySync.unsent` 블록(`{N edits} that haven't been sent yet will be replaced.`)을 폐기 서술로
  **교체**한다: `Sync will discard N unsent translation changes and replace them with repository values.` Dialog 설명문의 기존 `replace`와
  같은 사실을 두 번 말하지 않게 한 문장만 남긴다. 줄 수가 안 늘어 360px Dialog 판정이 필요 없다.
- 버튼 라벨은 건수로 갈린다 — **N = 0이면 기존 `Sync from repository`, N > 0이면 `Discard changes and sync`.**
  트리거 `Sync`와 확정 버튼의 접근 이름이 달라야 한다는 기존 규칙(DESIGN §6.646)은 양쪽에서 유지한다.
- N은 키 × 로케일 셀 수이며 활성 표면 전체를 센다.
- 사용자가 명시적으로 승인하면 리포 값으로 덮는다. 자동 Sync의 보존 규칙을 우회하는 유일한 경로다.
- **덮는 범위는 현재 strict 적재와 동일하다** — 리포에 있는 값으로 교체하고 `updatedBy`·편집 토큰을 비운다.
  리포의 빈값·누락 셀 처리는 이 기능의 범위가 아니므로(위 제외 항목) 확인 문구를 `replace them with repository values`로 두고
  "모든 편집이 사라진다"고 주장하지 않는다.
- **승인은 서버가 발급한 불투명 지문이다.** 현재 pending 셀 집합·`importRevision`·표면 설정의 digest이고 클라이언트는 그것을 되돌려줄 뿐이다.
  실행 시 서버가 잠금 뒤 같은 지문을 재계산해 대조한다. Dialog 이후 새 편집이 생겼으면 지문이 달라져 재확인한다.
  단순 boolean 승인으로 이후의 모든 편집을 버릴 수 없다. 폐기 upsert는 **승인 집합의 토큰 또는 토큰 없음**인 셀만 덮는다 —
  지문 대조와 upsert 사이에 커밋된 저장은 새 토큰이라 살아남고 결과에 "승인 뒤 N건은 남았다"로 실린다.
- 확인 없는 호출·EDITOR 직접 호출·편집/설정이 달라진 옛 승인으로는 폐기할 수 없다. 별도 만료는 없다 — 상태가 바뀌면 지문이 바뀐다.
- 현재의 표면별 부분 성공 계약은 유지한다. 실제 적용한 셀만 폐기되며 실패/미적용 표면·파일의 편집은 남는다.
- 편집 백업·복원·수동 재적용 화면은 이번 범위에 없다. 사용자가 폐기를 취소하면 기존 편집이 그대로 남는다.
- `Send changes first`는 Publish 실행이 아니라 번역 화면 링크다. 편집이 보존돼 있고 번역 화면은 언제나 열리므로 숨기는 갈래가 없다.

### Publish

1. pending 0이면 모든 트리거에서 즉시 no-edits. **GitHub 쓰기·조회·브랜치 되돌림 0회.**
2. 최신 base 커밋을 하나 캡처하고, 검사한 커밋의 트리·원본·부모를 그대로 써서 PR을 생성/갱신한다.
   검사 후 최신 ref를 다시 읽어 다른 부모로 쓰지 않는다.
3. 성공 확인된 스냅샷의 편집만 전달 처리한다. 실행 중 추가 편집은 미전달로 남는다.
   렌더 결과가 base와 같아 `no-changes`로 끝나는 경우도 캡처 편집을 전달 처리한다 — 오늘 2층이 그 경우 `lastPulledAt`을 전진시키는 것과 같은 행동이다.
4. writer 경고가 있으면 GitHub 쓰기 전에 전체 중단한다. 셀별 부분 전달 추적은 만들지 않는다.
5. GitHub 쓰기 후 응답/DB 기록 실패는 전달 여부 불명이다. 편집을 해제하지 않고 기존 `delivery: unknown` 안내를 유지한다.
6. 완료는 `Sent to pull request`와 PR 링크다. 머지·배포 완료라고 말하지 않는다.
7. 미리보기는 오늘처럼 base 대비 목록이고 표시 전용이다(§5.6.35 유지). 미리보기와 실행 사이의 변화는 "매번 새 조회부터"로 흡수한다.

### PR 인계 뒤

- 미전달 편집이 없으면 수동·자동 Publish 모두 GitHub 쓰기를 하지 않는다. Sync와 cron이 기존 PR을 base로 되돌리지 않는다.
- 새 편집을 다시 보내는 경우에는 기존의 '현재 DB 전체 스냅샷으로 PR 갱신' 계약을 유지한다. 과거 PR 값을 합치지 않는다.
  cron도 같다 — 열린 PR이 있어도 새 편집이 있으면 오늘처럼 갱신한다.
- 따라서 PR 전달 → Sync → 새 편집 → 재Publish는 이전 PR 내용을 교체할 수 있다. 그 교체를 사람이 검토하는 화면(PR diff)은 `publish-pr-handoff` spec이다.
- PR 전달 후 base가 움직여 생기는 충돌, 사람이 PR 브랜치를 수정하는 경우의 검토·머지는 앱 책임 밖이다.
  앱은 자동 충돌 해결을 하지 않는다.

## 완료 조건

1. 편집 A 저장 뒤 코드 커밋 B를 자동 적재해도 A의 값·저자·미전달 상태가 유지된다. B가 로케일 파일을 바꿨는지와 무관하다.
2. 미전달 편집이 있는 동안 자동 적재는 전부 `deferred`이고 키·번역·`Project`·`TranslationSurface`(진행 표시·마지막 적재 성공 시각 포함)가 모두 불변이다.
   쓰기 SQL이 0회다(같은 픽스처의 pending 0 경로에서는 N > 0으로 대조한다).
3. 미전달 편집이 0이면 기존 strict 적재가 그대로 돈다. pending이 0이 된 뒤 첫 CI 요청이 `applied`이고 `paused` 표시가 사라진다.
4. OWNER가 승인한 수동 Sync만 편집을 폐기한다. 승인 뒤 추가 저장은 지문 불일치(재확인) 또는 토큰 조건부 upsert(남김)로 보존된다.
   실패 파일의 편집과 orphan 번역 값은 보존된다.
5. pending 0이면 Publish가 GitHub 쓰기·조회·브랜치 되돌림을 0회 한다. 1층 스킵은 시각이 아니라 토큰으로 판정한다.
6. PR 전달 후 Sync와 cron을 반복해도 미전달 편집이 없으면 기존 PR head가 변하지 않는다.
   **단 사용자가 승인한 수동 재Publish의 no-change 브랜치 정리는 제외한다** — 그 경로는 2026-09-09의 방어선이므로 유지된다.
7. Publish 스냅샷 뒤 같은 셀을 다시 저장하면 성공 처리 이후에도 새 수정이 미전달이다. 동일 밀리초 저장도 포함한다.
8. API·CLI가 `applied / deferred`를 구분하고 실제 오류는 HTTP 오류로 남는다. 화면은 보류를 파생 상태(pending > 0 ⇒ `paused`)로 보인다.
   보류에서 마지막 적재 성공 시각·진행 표시를 전진시키지 않는다.
9. orphan 키·로케일의 기존 편집은 backfill·집계·Publish 캡처에서 제외되고, 다른 셀을 보내도 값·저자·토큰이 전달 완료 처리로 바뀌지 않는다.
10. 부분 파싱·writer 경고·응답 유실을 전체 전달 성공으로 숨기지 않는다. 보낸 것으로 증명되지 않은 편집은 남는다.
11. 보호 상태에서 번역 화면 배너가 손실을 예고하지 않고(`can be lost`·`automatically` 없음) 닫기 없이 상시 `info`로 서며, pending 0이면 사라진다.
    **이것은 기존 배너의 반전이다** — 현재 배너는 닫기 키 `lastPulledAt`·`warning`이고 재오픈 트리거가 Publish뿐이다(`edit-loss-banner.tsx:15-16` 주석이 의도로 적음).
12. Home `To send` 카드가 pending > 0에서 `repository updates paused` 보조 줄을 낸다.

**검증 방법**(완료 조건이 아니라 tasks 소관): 두 프로젝트·두 표면 격리, CI/수동 Sync/저장/Publish 경합을 실제 PostgreSQL로 검증한다. 경합은 barrier 기반이며 sleep 타이밍에 기대지 않는다.

## 비목표

값 병합, rebase 엔진, 편집 이력/복구함, 이메일·webhook, 자동 배포 추적, 실시간 공동 편집,
표면별 PR, 의미 단위 파일 비교, 리포 경로 재설정 UI, 일반 목적의 작업 대기열.

**검수에서 명시적으로 추가한 비목표:**

- **리포 기준본과 파일 단위 변경 감지** — 위 "범위에서 제외 확정된 것".
- **빈값·누락 셀의 strict 적재 보완** — 별도 spec.
- **열린 PR 대비 파일 diff·페이지네이션·열람 게이트·미리보기 승인 지문** — 별도 spec `publish-pr-handoff`.
- **D2(열린 PR이면 cron이 안 씀)** — 철회.
- **운영 차단·drain 기능** — 앱 설정으로도, 배포로도 만들지 않는다. backfill 멱등성으로 대체한다.
- **보류의 자동 해소·대기열·타임아웃 폐기** — 사람이 Publish하거나 폐기를 승인할 때까지 보류가 유지된다.
- **보류 발생 기록 컬럼**(`lastDeferredAt` 류) — 보류는 pending > 0에서 파생되고 실제 발생은 Actions 로그가 든다.
- **저장 경로의 잠금·거부** — 보존은 적재 쪽 조건부 upsert + 재집계가 책임진다.
- **승인 HMAC·만료** — 서버가 잠금 뒤 재계산하는 지문으로 충분하다. 새 환경변수·`AUTH_SECRET` 배선 없음.

미전달 '순수 차이 0' 최적화도 제외한다. 값을 수정했다가 원복해도 전달/동등 확인 전에는 보수적으로 미전달로 센다.

## 확인 결과

- **범위 확정(4차)**: 토큰 축 + 거친 보류. 스키마 추가는 `Translation.pendingEditToken` **1필드** + 인덱스 하나다.
- D1 확정: 프로젝트 전체 보류. 표면별 CI 요청에도 서버가 프로젝트 전체 pending을 본다. 일반 적재의 전체 원자성을 새로 약속하지 않는다.
- D2 철회(4차): cron은 오늘처럼 새 편집이 있으면 열린 PR도 갱신한다.
- PR 파일 diff 미리보기는 별도 spec으로 분리(4차). 이 spec의 UI 변경은 배너 교체·Sync Dialog 문구/라벨·Home 카드 갈래 하나뿐이라 **Claude Design 핸드오프가 필요 없다.**
- 이미 합의한 사항: 코드 정본, 병합 없음, 수동 폐기 확인, PR 전달 이후 머지·배포 책임 제외.
