# spec — Sync 편집 보호와 PR 인계

상태: 스펙·기술 설계 초안 작성 완료. D1·D2 사용자 확인 반영. 다음 단계는 `/tdd interface`다.

## 사용자와 목적

- 번역 편집자: 저장한 번역이 자동 적재 때문에 사라지지 않고 PR로 전달되기를 원한다.
- 개발자(OWNER): 코드를 정본으로 유지하고, 일반 코드 커밋 때문에 번역 작업이 막히지 않기를 원한다.
- 앱의 책임은 저장한 편집의 보호와 PR 전달까지다. 머지·배포는 GitHub와 개발자가 맡는다.

## 범위 게이트

PRODUCT §4.2 비범위에 해당하지 않는다. 실시간 공동 편집·승인 워크플로·자동 병합·충돌 해소 UI를 만들지 않는다.
§4.3의 webhook·메일도 추가하지 않는다. ARCHITECTURE §0의 값 병합 금지와 결정성은 유지한다.
바뀌는 것은 **strict 적재를 허용하는 조건**이다. 적용을 허용하면 여전히 리포 값 전체로 덮는다.
PRODUCT §3·§4.1, ARCHITECTURE §2·3·5.5·5.6의 관련 정책 갱신은 구현 태스크에 포함한다.

## 문제 — 현재 코드에서 확인한 사실

1. `lib/push/apply.ts`는 기존 번역 값을 덮고 `updatedBy`를 비운다. 편집부터 Publish까지의 짧은 구간에도 손실이 가능하다.
2. `lib/pull/run.ts`는 DB 스냅샷과 실행 시점의 최신 base를 조합한다. 마지막 적재 이후 로케일 파일 변경을 막는 게이트가 없다.
3. 자동 Publish의 스킵은 `max(updatedAt)`와 `lastPulledAt` 비교다. 리포 적재도 시각을 올리므로 사용자 편집이 없어도 PR을 갱신할 수 있다.
4. `changes.length === 0` 경로도 sync 브랜치를 base로 옮긴다. PR 전달 뒤 DB가 리포 값으로 돌아오면 이전 PR 내용이 지워질 수 있다.
5. CI는 표면별 요청, 수동 Sync는 프로젝트의 활성 표면 순회, Publish는 모든 활성 표면의 PR 하나다.
6. 현재 미전달 집계는 저자·시각 기반이다. 전달 중 새 편집과 적재를 확실하게 구별하려면 편집의 식별이 필요하다.

stale이 오래 지속될 수 있다는 것은 우려이며, 발생 빈도를 측정한 결과는 아니다.

## 용어

- Sync: 리포 → 앱. CI 자동 적재와 OWNER의 수동 Sync를 포함한다.
- Publish: 앱 → PR. 수동 실행과 기존 야간 실행을 포함한다. 열린 PR 갱신은 수동만 허용한다(D2 확정).
- 미전달 편집: 서버에 저장됐고 아직 전달 확인되지 않은 셀의 최신 수정. 현재 사용자뿐 아니라 프로젝트 멤버 전체의 수정이다.
- 리포 기준본: 마지막 정상 적재의 로케일 파일 경로·blob SHA와 리포/브랜치/표면 설정. DB 번역 값을 해시한 것이 아니다.
- 동일/변경: 전체 대상 경로 집합과 각 파일 바이트 기준. 추가·삭제·이름 변경·주석·서식 변경도 변경이다.
- 확인 불가: 기준본 없음, 불완전 트리, 조회 실패 등. ‘동일’로 취급하지 않는다.

## 동작 계약

### 자동 Sync

판정 범위는 **프로젝트 전체**다(D1 확정). 인가·보관·포맷·역행·실행권 검사를 먼저 통과해야 한다.
미전달 편집은 모든 활성 표면에서 합산하고, 리포 비교도 모든 활성 표면의 대상 파일을 확인한다.
표면 A에 편집이 있고 리포의 표면 B가 바뀌어도 전체를 보류한다. 어느 표면이 막혔는지는 보조 설명으로만 제공한다.

| 리포 비교 | 미전달 편집 | 동작 |
|---|---|---|
| 동일 | 있음 | 번역·키·저자·미전달 표시를 보존. 최신 커밋 확인 사실만 갱신 |
| 변경 | 있음 | 프로젝트 전체 자동 적재 보류. 모든 표면의 마지막 적재 기준본과 편집 유지 |
| 확인 불가 | 있음 | 안전을 확인할 수 없어 보류. 변경으로 단정하지 않음 |
| 동일/변경 | 없음 | 기존 strict 적재. 리포가 정본이므로 이미 전달한 앱 값도 리포 값으로 덮을 수 있음 |
| 최초/구 클라이언트로 비교 불가 | 없음 | 기존 입력 검증을 통과한 적재는 허용. 근거 없는 기준본은 생성하지 않음 |

‘동일 + 편집 있음’에도 기존 `applyPush`를 실행하면 편집이 지워지므로 반드시 별도 무변경 경로다.
보류는 실패나 적재 성공이 아니다. 다음 CI 요청 또는 수동 Sync/Publish 시 다시 평가한다.
CI는 표면별로 요청하더라도 같은 프로젝트 전체 게이트를 통과한다. pending이 없는 기존 표면별 적재를 일괄 트랜잭션으로 바꾸는 것은 이번 범위가 아니다.
자동 폐기·대기열·타임아웃 폐기는 없다. 보류 후 새 이벤트가 없어도 UI에서 상태와 수동 해소 경로를 확인할 수 있다.

### 수동 Sync

- OWNER 전용 유지. 미전달 편집이 있으면 확인 Dialog를 표시한다.
- 문구: `Sync will discard N unsent translation changes and replace them with repository values.`
- 버튼: `Cancel` / `Discard changes and sync`. N은 키 × 로케일 셀 수이며 활성 표면 전체를 센다.
- 사용자가 명시적으로 승인하면 동일 파일이어도 리포 값으로 덮는다. 자동 Sync의 보존 규칙을 우회하는 유일한 경로다.
- Dialog 이후 새 편집이 생겼으면 재확인한다. 단순 boolean 승인으로 이후의 모든 편집을 버릴 수 없어야 한다.
- 확인 없는 호출·EDITOR 직접 호출·만료 승인·편집/설정이 달라진 옛 승인으로는 폐기할 수 없다.
- 현재의 표면별 부분 성공 계약은 유지한다. 적용된 표면만 폐기되며 실패/미적용 표면의 편집은 남는다. 결과에 이를 구별한다.
- 편집 백업·복원·수동 재적용 화면은 이번 범위에 없다. 사용자가 폐기를 취소하면 기존 편집이 그대로 남는다.

### Publish

1. 최신 base 커밋을 하나 캡처하고, 활성 표면 전체의 대상 경로 집합·blob을 각 기준본과 대조한다.
2. 일반 코드만 바뀌었으면 통과한다. 한 표면이라도 로케일 변경/확인 불가면 프로젝트 Publish 전체를 중단한다.
3. 변경된 리포를 Publish가 자동 Sync하지 않는다. 작성한 번역을 유지하고 OWNER에게 수동 Sync를 요청할 수 있게 안내한다.
4. 검사한 커밋의 트리·원본·부모를 그대로 써서 PR을 생성/갱신한다. 검사 후 최신 ref를 다시 읽어 다른 부모로 쓰지 않는다.
5. 성공 확인된 스냅샷의 편집만 전달 처리한다. 실행 중 추가 편집은 미전달로 남는다.
6. GitHub 쓰기 후 응답/DB 기록 실패는 전달 여부 불명이다. 편집을 해제하지 않고 기존 `delivery: unknown` 안내를 유지한다.
7. 완료는 `Sent to pull request`와 PR 링크다. 머지·배포 완료라고 말하지 않는다.

### PR 인계 뒤

- 미전달 편집이 없으면 수동·자동 Publish 모두 GitHub 쓰기를 하지 않는다. Sync와 cron이 기존 PR을 base로 되돌리지 않는다.
- 새 편집을 다시 보내는 경우에는 기존의 ‘현재 DB 전체 스냅샷으로 PR 갱신’ 계약을 유지한다. 과거 PR 값을 합치지 않는다.
- 따라서 PR 전달 → Sync → 새 편집 → 재Publish는 이전 PR 내용을 교체할 수 있다. 이 경우 수동 미리보기에서 **기존 PR 대비 제거·교체되는 내용까지** 보여주고 확인받는다.
- D2 확정: 열린 PR이 있는 자동 Publish는 새 편집이 있어도 보류하고 수동 Publish로 넘긴다. PR 조회 실패도 쓰지 않는다.
- PR 전달 후 base가 움직여 생기는 충돌, 사람이 PR 브랜치를 수정하는 경우의 검토·머지는 앱 책임 밖이다. 앱은 자동 충돌 해결을 하지 않는다.

## 완료 조건

1. 편집 A 저장 뒤 일반 코드 커밋 B를 자동 적재해도 A의 값·저자·미전달 상태가 유지된다.
2. B가 어느 활성 표면의 대상 로케일 파일을 변경하든 프로젝트 전체 자동 적재가 보류되고, Publish는 GitHub 쓰기 전에 중단된다.
3. 대상 파일 추가·삭제·이름 변경과 새 로케일 파일도 2와 동일하다. DB에 등록된 로케일만 비교해 누락하지 않는다.
4. 미전달 편집이 없으면 변경된 리포를 정상 적재한다. 보류 상태가 남아 최신 상태로 오인시키지 않는다.
5. OWNER가 승인한 수동 Sync만 편집을 폐기한다. 확인 뒤 추가 저장과 경합하면 재확인 또는 실행 중 거부로 보존한다.
6. PR 전달 후 Sync와 cron을 반복해도 미전달 편집이 없으면 기존 PR head가 변하지 않는다.
7. Publish 스냅샷 뒤 같은 셀을 다시 저장하면 성공 처리 이후에도 새 수정이 미전달이다. 동일 밀리초 저장도 포함한다.
8. 화면·API·CLI가 `applied / unchanged / deferred / failed`를 구분한다. 보류에서 마지막 적재 성공 시각을 전진시키지 않는다.
9. 일반 코드 변경 후 Publish가 만든 커밋의 부모는 검사한 B이고, 로케일 외 파일은 B와 동일하다.
10. 부분 파싱·writer 경고·응답 유실을 전체 전달 성공으로 숨기지 않는다. 보낸 것으로 증명되지 않은 편집은 남는다.
11. 두 프로젝트·두 표면 격리, CI/수동 Sync/저장/Publish 경합을 실제 PostgreSQL과 리포 왕복으로 검증한다.

## 비목표

값 병합, rebase 엔진, 편집 이력/복구함, 이메일·webhook, 자동 배포 추적, 실시간 공동 편집,
표면별 PR, 의미 단위 파일 비교, 리포 경로 재설정 UI, 일반 목적의 작업 대기열.
미전달 ‘순수 차이 0’ 최적화도 제외한다. 값을 수정했다가 원복해도 전달/동등 확인 전에는 보수적으로 미전달로 센다.

## 확인 결과

- D1 확정: 프로젝트 전체 보류. 표면별 CI 요청에도 서버가 전체 활성 표면을 검사한다. 일반 적재의 전체 원자성을 새로 약속하지 않는다.
- D2 확정: 새 편집 + 열린 PR 없음일 때만 야간 자동 Publish를 유지한다. 열린 PR 갱신은 미리보기 확인 뒤 수동 실행한다.
- 이미 합의한 사항: 코드 정본, 병합 없음, 동시 변경 때만 자동 적재 보류, 수동 폐기 확인, PR 전달 이후 머지·배포 책임 제외.
- 미결 제품 선택 없음. 스키마·원격 조회·확인 토큰의 구체 설계는 design.md의 제안이며 구현 전에 인터페이스 테스트로 검토한다.
