# MCP OAuth — Claude Design 작업 지시

Malmoi의 **OAuth 동의 화면을 새로 설계하고, 기존 `/mcp` 페이지에 연결된 앱 관리와 OAuth 연결 안내를 추가**해줘.
코드베이스를 알고 있다는 전제로 설명할게. 기능 소개보다 실제 화면·상태·인터랙션을 완성하고 구현자가 그대로 옮길 수 있는 핸드오프를 남겨줘.
이번 산출물은 디자인과 인터랙션 명세야. 인증 서버 구현이나 배포는 하지 않아도 돼.

## 먼저 볼 파일

- 이 디렉터리의 `spec.md`, `design.md`(특히 §4.2·§5·§6.1), `tasks.md`.
- `docs/DESIGN.md`, `app/globals.css`, `components/ui/` — 시각 규칙·토큰·기존 프리미티브.
- `app/(edit)/mcp/page.tsx`, `components/mcp/{token-card,token-modal,connect-card}.tsx` — 현재 `/mcp` 전체와 권한 폼·폐기 인터랙션.
- `components/signin/{auth-layout,auth-column,provider-button}.tsx`, `app/invite/[token]/page.tsx`,
  `app/signin/page.tsx`, `app/signin/link/[challenge]/page.tsx` — 셸 밖 화면과 로그인 왕복.
- `messages/en.tsx`의 `mcpConnector`, `lib/mcp/{grant,issue-plan,snippets}.ts` — 영어 라벨과 선택 규칙.

이미 구현된 화면은 현재 코드와 DESIGN이 기준이야. 옛 핸드오프와 다르면 현재 코드를 따라줘.
기능 계약은 이 디렉터리의 spec/design을 따르고, 화면 배치와 여백은 기존 패턴 안에서 판단해줘.

## 사용자와 이번 변화

개발자는 Claude Code·Codex에서, 비개발자인 번역 편집자는 claude.ai 커넥터에서 서버 URL을 등록해.
그 뒤 브라우저에서 Malmoi에 로그인하고 권한에 동의하면 클라이언트로 돌아가 연결이 끝나.
**OAuth 경로에서는 토큰을 보여주거나 복사시키지 않아.** 개인 토큰 방식은 그대로 병행해.

이번에 설계할 표면은 세 가지야.

1. `/oauth/authorize` — 로그인 전·후 동의, 예외, 재동의.
2. 기존 `/mcp` — 연결된 앱 목록과 연결별 끊기.
3. 기존 `/mcp`의 Connect 안내 — OAuth의 URL 등록 경로와 기존 개인 토큰 설정을 구별.

사이드바에 새 목적지를 만들거나 프로젝트 화면을 재설계하지 말아줘. `/mcp`는 기존 계정 단위 페이지야.

## 1. 새 동의 화면 `/oauth/authorize`

셸 밖 화면이야. 기존 초대·계정 연결 화면의 흰 폼 패널 단일 구성(우측 키비주얼 없음 — 2열 장식은 `/signin` 전용)을 이어가고, 낯선 OAuth 전용 테마를 만들지 말아줘.
무세션이어도 정상적으로 들어오는 페이지이며, 별도 `/signin`으로 먼저 보내는 흐름이 아니야.

### 로그인 전

- 어느 앱이 Malmoi 연결을 요청했는지 먼저 보여줘.
- 이 화면 자체에 기존 GitHub·Google 로그인 버튼을 둬. 공급자 클릭 뒤 로딩·중복 클릭 방지도 기존 패턴을 따라줘.
- 로그인하면 같은 요청의 동의 화면으로 돌아와. 공급자 취소·오류로 `/signin`에 착지한 경우에는 이 요청으로 돌아오는 링크를 보여줘.
- 같은 이메일에 새 공급자를 붙이는 기존 계정 연결 화면을 거쳐도 목적지는 이 동의 화면이야.
  기존 `/signin`·계정 연결 화면 전체를 다시 그리지 말고 필요한 복귀 문구·링크 변경만 보여줘.

### 로그인 후 동의

한 화면에서 **누가 / 어떤 앱에 / 무엇을 / 어느 프로젝트에서 / 언제까지** 허용하는지 읽히게 해줘.

- 현재 계정과 `Not you?` 계정 전환. 계정을 바꿔도 같은 요청을 유지해.
- 앱 이름과 식별 보조 정보. 앱 이름은 앱이 스스로 정한 문자열이므로 공식 앱 인증처럼 보이게 하지 마.
  CIMD이면 clientId URL, DCR이면 clientId와 검증된 콜백 주소를 보조 정보로 표시해.
  기술 용어를 주 설명으로 늘어놓지 말고, 사용자가 연결 대상을 구별할 정도로 배치해줘.
- 권한은 기존 개인 토큰 폼의 라벨·순서·설명을 재사용해. 새 권한이나 역할은 만들지 않아.
  권한을 체크하지 않은 읽기 전용 상태도 유효해. 현재 프로젝트 역할 때문에 체크박스를 막지 않아도 돼.
  **실제로 할 수 있는 일은 각 프로젝트에서의 내 역할과 선택한 권한의 교집합**이라는 설명이 필요해.
- 범위는 기존 `All my projects` / `Chosen projects`. 전체 범위에는 나중에 참여하는 프로젝트도 포함돼.
  고른 범위에는 현재 참여 중인 비보관 프로젝트만 나와. 프로젝트 0개면 기존 폼처럼 Chosen projects를 사유와 함께 비활성화하고,
  고른 범위에서 선택이 0개면 Authorize할 수 없어. 전체/선택 범위를 오갈 때 선택은 유지해.
  이 연결로 직접 만든 프로젝트는 선택 범위에 추가된다는 기존 예외도 설명에 반영해줘.
- 만료는 30/90/365일. **연결의 수명**이며 내부 access token의 1시간 만료는 화면에 노출하지 마.
  기본값·읽기 전용·프로젝트 선택 동작은 기존 토큰 폼을 기준으로 하고 다르게 제안하면 이유를 표시해줘.
- 주 행동은 `Authorize`, 보조 행동은 `Deny`. 성공하면 클라이언트로 돌아가므로 토큰 결과 모달·복사 단계·가짜 연결 완료 화면을 넣지 마.
  Malmoi가 code를 돌려준 것만으로 클라이언트의 최종 연결 성공을 단정할 수 없어.

### 같은 앱에 재동의

동일한 사용자·clientId의 연결은 하나야. **연결을 완료하면 기존 연결을 대체하고 다른 기기의 같은 앱도 끊길 수 있음**을 동의 전에 알려줘.
실제 교체는 클라이언트가 code를 교환하는 데 성공할 때야. 동의 화면을 열거나 Deny한 것만으로 기존 연결이 끊기지는 않아.
이름이 같아도 clientId가 다른 앱은 별도 연결이므로 이름으로 교체 경고를 판단하면 안 돼.

### 꼭 표현할 상태

| 상태 | 화면·행동 계약 |
|---|---|
| 요청 조회 중·조회 실패 | 진행과 오류를 구분. 장애를 없는 요청으로 표시하지 않고 재시도 제공 |
| 검증된 요청, 무세션 | 앱 식별 + GitHub·Google 로그인 |
| 로그인 중 | 누른 공급자의 진행 표시, 중복 제출 방지 |
| 로그인 완료 | 현재 계정 + 동의 폼 |
| 멤버십 0개 / 선택 프로젝트 0개 | 기존 폼의 범위 선택 제한·사유 |
| 재동의 | 기존 연결 대체·다른 기기 영향 안내 |
| 제출 중 | 입력과 행동 중복 실행 방지, 기존 Button 로딩 |
| 명시적 저장 실패 | 선택을 보존하고 인라인 오류·재시도 |
| 응답 유실·결과 미확인 | 완료로 단정하거나 자동 재제출하지 않음. 요청 상태를 다시 확인하는 복구 동작 |
| 없는·만료·이미 처리한 요청 | 원인을 구별하고 클라이언트에서 연결을 다시 시작하도록 안내 |
| 세션 만료·계정 전환 | 유효한 요청은 보존하며 로그인으로 복귀, 만료된 요청은 명시적으로 종료 |
| clientId·redirectUri 검증 실패 | Malmoi 안에서 종료. 신뢰할 수 없는 주소로 돌아가는 버튼 없음 |
| Deny | 검증된 콜백으로 거부 결과 반환. 기존 연결은 유지 |

요청은 10분 동안 유효해. PKCE·해시·DB 잠금·issuer 같은 구현 용어를 사용자 오류 문구에 넣지는 마.

## 2. 기존 `/mcp`에 연결된 앱 관리 추가

**`/mcp` 페이지도 변경 대상이야.** 동의 페이지만 만들고 끝내지 말아줘.
현재 페이지의 헤더·셸과 **fluid 1280** 폭을 유지해. 예전 896px 고정 폭 핸드오프로 되돌리지 마.
기존 개인 토큰 카드의 생성·재발급·폐기·한 번만 원문 표시 동작은 그대로 두고, 새 연결 목록과 Connect 안내를 함께 배치해줘.
권장 배치를 하나로 완성하되 기존 두 카드의 역할이 어떻게 이어지는지 핸드오프에 적어줘.

연결 행에는 다음 정보를 보여줘.

- 앱 이름 + 식별 보조 정보. 같은 이름의 별도 앱 두 개를 구별할 수 있어야 해.
- 허용 권한, 전체/고른 프로젝트 범위, 마지막 사용, 연결 만료.
- 연결별 `Disconnect`. 다른 OAuth 연결과 개인 토큰에는 영향이 없어.

기존 token-card의 사실 정보·날짜·마지막 사용 없음 패턴을 재사용해. 목록 없음, 마지막 사용 없음, 만료,
긴 앱 이름·URL, 동일 이름 두 연결, 여러 연결이 있는 상태를 포함해줘. 만료 행이 조회된 경우의 표현은 정하되 영구 이력 보관 화면처럼 약속하지 마.
최초 조회 중·조회 실패도 구분해줘. 조회 장애를 연결 없음으로 표시하지 말고 재시도를 제공해.

끊기는 기존 개인 토큰 폐기의 확인 Dialog를 따라줘.

- 어느 연결을 끊는지 이름과 보조 식별 정보로 명확하게 해줘. 확인 버튼은 기존 danger 변형을 사용해.
- 취소하면 원래 버튼으로 포커스가 돌아와.
- 제출 중 중복 실행을 막고, 명시적 실패면 행과 재시도 위치를 유지해.
- 응답 유실은 성공으로 말하지 않고 결과 미확인으로 표시해 재조회해.
- 성공하면 행을 제거하고 상태를 알려줘. 포커스는 다음 행의 Disconnect, 없으면 목록 제목으로 이동해.
- 같은 이름의 앱도 버튼 접근 이름에서 구별해줘.

권한·범위 변경은 클라이언트에서 다시 연결하고 동의하는 방식이야. 인라인 권한 편집·별도 앱 등록·전역 Disconnect all을 추가하지 마.

## 3. `/mcp` Connect 안내 확장

OAuth 연결은 **서버 URL 등록 → 브라우저 로그인·동의**가 주 경로야. URL은 현재 환경의 것을 보여줘.
OAuth 대상은 Claude Code·Codex·claude.ai 셋이고, claude.ai 사용자를 셸 환경변수나 설정 파일 안내로 보내면 안 돼.

- 서버 URL과 복사 행동은 기존 ConnectCard를 이어가.
- OAuth 경로에는 Authorization 헤더나 토큰 환경변수가 필요 없어.
- 개인 토큰 연결의 기존 클라이언트·설정 조각도 유지해. 기존 Cursor 개인 토큰 예시를 없애거나 Cursor OAuth 지원을 새로 약속하지 마.
- OAuth/개인 토큰 방식을 선택하는 정보 구조는 가장 단순한 형태 하나로 제안해줘.
  개인 토큰과 OAuth 설정을 한 조각에 섞지 마. 기존 헤더가 남으면 OAuth로 넘어가지 않는 클라이언트가 있으므로 전환 안내도 필요해.
- CLI 설정 조각은 기존 WorkflowBlock을 재사용하고, claude.ai는 URL 등록 흐름으로 안내해.
- 도구 목록을 새로 복제하지 말고 현재 가이드 링크를 유지해.

## 시각·접근성 기준

라이트 단일, 기존 neutral 토큰·Pretendard·타입 스케일·radius·컴포넌트를 써줘. 새 raw 색·테마·폰트는 만들지 마.
MCP 표시는 기존 공식 `McpIcon`, 공급자 버튼은 기존 브랜드 아이콘을 재사용해.
앱이 넘긴 이름·메타데이터를 이유로 임의 로고나 브랜드 색을 가져오지 마.

URL·clientId·계정·날짜는 sans야. mono는 실제 코드 블록에만 써.
포커스 링, 키보드 탭 순서, Dialog 초기/복귀 포커스, 로딩 중 버튼, 오류와 폼 필드의 연결을 핸드오프에 명시해줘.
기존 화면의 레이아웃 규칙을 따르되 긴 목록·작은 높이에서 주요 행동이 화면 밖으로 사라지지 않게 확인해줘.

## 아직 실측 전인 사항

등록 방식(CIMD/DCR), 클라이언트별 실제 버튼명·설정 형식·콜백 주소, refresh 경합 호환성, claude.ai의 preview 접근 방법은 T1이 확정해.
디자인에는 식별 정보의 두 데이터 형태를 보여줄 수 있지만, 임시 주소·클라이언트 절차는 **샘플/미확정**으로 표시해줘.
실측 없이 실제 서비스 UI나 인증 성공을 만들어 사실처럼 제시하지 마.
refresh 재사용으로 연결이 끊긴 사용자는 클라이언트에서 다시 동의해야 하지만, 삭제된 연결에 서버가 보관하지 않는 상세 사유를 목록에 표시하지 마.

## 필요한 산출물

1. 새 동의 화면과 기존 `/mcp` 변경안을 연결한 디자인. 대표 정상 상태뿐 아니라 위 상태표·끊기 예외 상태를 포함해줘.
2. 각 아트보드의 경로·진입 조건·주 행동·성공/실패 다음 화면을 적은 상태 맵.
3. 컴포넌트 대응, 치수·스크롤 경계·긴 텍스트 처리·포커스·로딩·오류·영어 UI 문구를 포함한 구현 핸드오프.
4. 기존 코드에서 바뀌는 부분과 유지할 부분, T1 결과를 기다리는 자리 목록.

화면 문구는 영어, 핸드오프 설명은 한국어로 써줘. 기존 문구는 먼저 재사용하고, 새 문구는 구현 시 `messages/en.tsx`에 들어갈 단위로 정리해줘.
