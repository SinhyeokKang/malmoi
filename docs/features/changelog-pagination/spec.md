# Changelog pagination — 스펙

작성: 2026-10-16 · 상태: **범위·미결 합의 완료 · `/feature-review` 반영(2026-10-16) · 구현 전**
합의: 페이지 상한 3 · 전체 3초 · 부분 실패는 읽은 데까지 · ⌘F 비목표 · **자동 드러내기 없이 버튼만**(`ghost` · `md` · 가운데) · 끝 문장은 다 드러난 뒤에만 · 해시는 진입 때만.

`/changelog`에 10개 단위 드러내기(`Show older releases` 버튼)를 붙이고, GitHub Releases 한 요청 상한(100건) 때문에 목록이 끊기는 문제를 함께 푼다.

## 1. 사용자

방문자 전체가 대상이다. 공개 페이지라 로그인 여부와 상관없다. 개발자와 번역 편집자 모두 "최근에 무엇이 바뀌었나"를 보러 온다. 대개 위쪽 몇 개만 읽는다고 **가정한다**(방문 집계는 페이지뷰만 세서 측정값이 없다 — `lib/seo/analytics.ts`). 오래된 판은 버전 주소(`/changelog#v1.0.1`)나 버튼으로 찾는다.

## 2. 관측된 문제

- 앱 릴리스가 2026-09-27 v1.0.0부터 2026-10-13 v1.4.2까지 31개 쌓였다(하루 약 1.9개). 지금은 전 항목을 한 번에 렌더하므로 최신 몇 개를 지나면 스크롤이 길다.
- 로더는 GitHub에 `per_page=100`으로 **한 번만** 요청한다(`lib/changelog/load.ts`). 원 배열이 100칸을 채우면 목록 끝에 "Older releases are on GitHub Releases." 문장만 남는다. 지금 속도면 2026-11월 말에 앱 릴리스가 100개를 넘고, 그 뒤로 옛 판은 앱 안에서 볼 수 없다. 액션 태그 릴리스도 같은 100칸을 쓸 수 있지만 **지금은 0건**이다(`malmoi-i18n-push-v*` 태그에 Release가 없다).

## 3. 범위 — PRODUCT 판정 개정

**PRODUCT.md `/changelog` 비범위의 "페이지네이션(100건 초과분은 GitHub 링크 한 문장)"을 범위로 옮긴다** (2026-10-16 사용자). 처음 출시 때 일부러 뺀 결정을 되돌리는 근거는 "2026-11월 말이면 100건 상한에 닿는다"다. 정본에는 **두 판정으로 나눠** 적는다(tasks §0).

- **수집**: GitHub Releases를 다음 페이지까지 따라 읽는다. 최대 3페이지(원 배열 300건)다.
- **표시**: 처음 10개만 보이고, 버튼으로 10개씩 더 드러낸다.

같은 줄의 나머지 비범위(버전별 하위 페이지·검색·필터·RSS·구독·새 버전 배지·앱 안 작성 UI·`/merge` 직후 즉시 반영)는 그대로다.

| 항목 | 결정 |
|---|---|
| 첫 화면 | 최신 10개가 보인다 |
| 더 보기 | 목록 끝의 `Show older releases` 버튼을 누르면 다음 10개가 드러난다. **스크롤만으로는 드러나지 않는다**(2026-10-16 사용자 — 자동 드러내기는 계속 내리는 사람에게 스크롤 길이를 줄이지 못한다) |
| 데이터 | 서버가 받은 전 목록을 렌더하고, 클라이언트는 숨김만 푼다. **추가 요청·새 진입점(Route Handler·Server Action)이 없다** |
| 버전 주소 | 숨겨진 항목의 주소로 들어와도 그 항목까지 펼치고 착지·포커스한다. 진입 때 한 번만 본다(`hashchange`는 듣지 않는다 — `PublicScroller`와 같다) |
| 수집 | 페이지 수 상한 3과 전체 시간 상한이 있다(design §2) |
| 상한 도달·부분 실패 | 읽은 데까지 보이고, **모든 항목이 드러난 뒤에** 목록 끝에 지금의 `Older releases are on GitHub Releases.` 문장이 선다 |

## 4. 완료 조건

1. 릴리스가 25개면 첫 렌더에 25개 항목이 전부 DOM에 있고, 1~10번째만 보이며 11~25번째는 `hidden`이다(서버 렌더와 첫 클라이언트 렌더가 같다).
2. `Show older releases`를 누르면 11~20번째가 보이고, 포커스가 11번째 버전 `h1`로 간다. 한 번 더 누르면 21~25번째가 보이고 포커스가 21번째 `h1`로 가며 버튼이 사라진다.
3. 스크롤만으로는 숨은 항목이 드러나지 않는다.
4. `/changelog#v1.0.3`처럼 숨겨진 판의 주소로 들어오면 그 판을 포함하는 묶음까지 보이고, 그 `h1`이 화면에 들어오며 포커스를 받는다. 이미 보이는 판의 주소는 지금과 똑같이 동작한다(`ReleaseList`가 착지를 다시 부르지 않는다).
5. 릴리스가 10개 이하면 버튼이 없다.
6. GitHub 원 배열이 100칸을 채우면 다음 페이지를 요청하고, 100칸 미만인 페이지에서 멈춘다. 같은 태그는 한 번만 나온다. 정렬은 모든 페이지를 합친 뒤 한 번 한다.
7. 첫 페이지가 실패하면 지금과 같은 실패 문장이다. 둘째 페이지부터 실패·타임아웃·형 오류가 나면 앞 페이지까지의 목록 + 끝의 `Older releases` 문장이다.
8. 페이지 수 상한(3)에 닿고 마지막 페이지가 100칸이면 끝에 `Older releases` 문장이 선다.
9. `Older releases` 문장은 숨은 항목이 남아 있는 동안 보이지 않는다. 마지막 묶음이 드러나면 버튼 대신 그 자리에 선다.
10. 콜드 캐시 첫 진입의 총 대기 상한이 지금처럼 3초다. 페이지가 여럿이어도 늘지 않는다.
11. `pnpm gate` green. `client-graph.test.ts`의 `CLIENT_LIB_FILES`에 잎 `lib/changelog/reveal.ts` **한 줄만** 더하고, 그 파일이 잎인지 검사하는 테스트가 함께 선다.

## 5. 비목표

- **서버 페이징(`?page=`)·커서·다음 묶음 요청.** 줄이는 것은 스크롤 길이다. 첫 HTML은 지금처럼 받은 릴리스 전부를 싣고 릴리스 수에 비례해 는다. 상한은 원 배열 300건이다(받아들인 비용 — 넘으면 그때 실측으로 다시 정한다).
- **스크롤로 자동 드러내기(무한 스크롤).** 계속 내리는 사람에게는 스크롤 길이가 지금과 같아 문제를 풀지 못한다.
- **찾기(⌘F)로 숨겨진 항목 찾기.** `hidden="until-found"`는 쓰지 않는다(design §5).
- **JS가 없는 환경에서 11번째 이후 보기.** 소개 문장이 이미 GitHub Releases로 보낸다.
- 페이지에 머문 채 주소창 해시만 바꿨을 때의 착지(`hashchange`).
- 스크롤 위치·펼친 개수 기억(뒤로 가기, 새로고침 뒤 복원). 버전 주소로 다시 들어오는 길이 있다.
- 총 개수·남은 개수 표시, 불러오는 중 표시(받아 올 것이 없다).
- 페이지 안에서 버전 주소를 복사하는 길(DESIGN §6.617의 기존 비범위).
