# user-menu-projects — spec

헤더 사용자 메뉴(아바타 메뉴)에 **내 프로젝트 그룹**을 둔다 — 계정 그룹(`navWorkItems`)과 공개 그룹(`Changelog · Docs · Privacy Policy`) 사이.
앱 셸·공개 셸 둘 다. 요청·결정: 2026-10-09 사용자 — 상한 5 · 공개 셸 포함 · 5개 초과 시 "더 보기" 없음(위 그룹 `Projects`가 대신) · 메뉴 폭 `w-60` 고정(feature-review).

## 사용자

**둘 다** — 특히 공개 셸(`/docs`·`/changelog`·`/privacy`)에 선 사람. 가이드를 읽다가 작업하던 프로젝트로 돌아가는 사람은 개발자·편집자 모두다.

## 문제 (관측된 사실)

- 공개 셸에는 사이드바가 없다. 로그인한 사용자가 `/docs`에서 프로젝트로 가는 길은 둘이다 —
  사용자 메뉴 `Projects` → `/projects` 목록 → 행, 또는 검색 캡슐(`⌘K`) → 빈 입력 미리보기의 Projects 앞 3개(`lib/search/rows.ts`의 `PREVIEW_LIMIT`) → 행.
  둘 다 두 번 이동이고, 두 번째 길은 검색 입구라 "프로젝트로 돌아가기"로 발견되지 않는다.
- 앱 셸에서는 LNB 프로젝트 스위처가 같은 일을 한다.
- **남는 가치**: 아바타 메뉴는 "내 것"을 찾는 사람이 먼저 여는 자리다 — 그 자리에서 입력·단축키 없이 한 번에 프로젝트 Home으로 간다(최대 5개).

## 범위 게이트

- PRODUCT §4.2 비범위에 걸리는 항목 없음 — 새 권한·데이터·조회·사전 키가 없다.
- ⚠️ **새 결정이다** — DESIGN §6.5 헤더 행의 "LNB와 겹치는 항목은 의도다"는 첫 묶음이 사이드바 **사용자 구역**과 같은 `navWorkItems`라는 뜻이었다.
  프로젝트 구역(스위처)과 겹치는 것은 이 기능이 새로 내리는 결정이고, PRODUCT:948("8-3은 스위처를 지워 옮기는 길을 목록 하나로 모았었다" — 이후 스위처가 돌아온 이력)과 같은 줄에 기록한다.
- IA 결정 1(PRODUCT — 프로젝트로 가는 자리는 전부 Home에 착지)을 따른다.
- 메뉴 길이가 9줄에서 최대 14줄로 는다 — 상한 5가 그 대가의 상한이다.
- **같은 파일을 만지는 진행 중 spec** — responsive-public P-01·P-06(공개 헤더·서랍, "메뉴 이동·폭 변경으로 중복 조회가 생기지 않는다"), responsive-app A-01(앱 헤더 배치).
  좁은 폭에서 사용자 메뉴가 서랍으로 옮겨 다시 마운트되면 지연 조회가 다시 돌 수 있다 — 이 기능이 먼저 들어가면 두 spec의 해당 행에 이 그룹을 등재한다(inbox-page가 A-07에 자신을 등재한 선례).

## 완료 조건 (검증 가능한 문장)

1. 로그인 사용자의 사용자 메뉴는 구분선으로 갈린 **다섯 구획**이다: 이름·이메일 머리 / 계정 그룹 / **프로젝트 그룹** / 공개 그룹 / Sign out. 프로젝트 그룹은 계정 그룹과 공개 그룹 사이이고 앞뒤를 같은 `DropdownMenuSeparator`가 가른다.
2. 프로젝트 그룹은 **보관 안 된** 멤버 프로젝트를 **최대 5개** 보인다. 순서는 LNB 프로젝트 스위처의 빈 질의 순서(`switcherProjects(rows, "")`)에서 보관을 뺀 앞 5개다.
3. 각 항목은 스위처 행과 같은 형이다 — `ProjectThumbnail xs`(16) + 이름 — 이고 누르면 그 프로젝트 Home(`routes.project(slug)`)으로 간다. 메뉴 Content는 **`w-60` 고정**이라 긴 이름·긴 이메일이 truncate되고 응답 전후로 메뉴 폭이 변하지 않는다.
4. 앱 셸에서 지금 보고 있는 프로젝트(`UserMenu`가 `usePathname()` + `activeProject(pathname, memberships)`로 구한다)가 목록에 있으면 그 항목이 스위처와 같은 `selected`(`menuitemradio` + `aria-checked` + `Check`)다.
   지금 프로젝트가 없으면(공개 셸 · 앱 셸의 `/projects`·`/inbox`·`/account` 등) 프로젝트 행은 전부 일반 `menuitem`이다(`menuitemradio` 0개).
5. 보관 안 된 멤버 프로젝트가 0이면 그룹과 그 구분선이 서지 않는다(빈 문구 없음).
6. 앱 셸은 **새 조회가 없다** — 헤더가 이미 받는 `memberships`를 쓴다.
7. 공개 셸은 페이지 렌더에 조회를 싣지 않는다 — 로그인한 공개 셸이 렌더·마운트만으로는 Action 호출 0이고, 메뉴가 기존 `loadSearchMemberships`(→ `loadSearchMembershipsAction`)로 읽는다(회차 규칙은 design D2). 비로그인이면 메뉴 자체가 없다.
   응답 전에도 다른 그룹은 누를 수 있다. 응답이 오면 프로젝트 행이 늘어 아래 그룹이 밀린다 — **대가로 수용**한다(design D2).
8. 새 사전 키가 없다 — 스켈레톤 sr은 기존 `projects.loading`이다(design D4).
9. 정본 문서(DESIGN §6.5·§6.615·§6.8 · ARCHITECTURE §6.37·경계 표 · PRODUCT:250·:948 · CLAUDE.md 데이터 경로 표 · DIRECTORY)가 새 소비자·새 결정을 반영한다(tasks T6).
10. `pnpm gate` green — 커밋 경계마다.

## 비목표

- **"더 보기"·전체 수 표시** — 위 그룹 `Projects`가 목록으로 간다(2026-10-09 사용자).
- **보관 프로젝트** — 스위처·`/projects`가 든다. 메뉴는 지금 일하는 곳으로 가는 지름길이다.
- **검색 입력** — 스위처·`⌘K`의 일이다. 메뉴는 5개 고정 목록이다.
- **최근 방문 순서·고정(pin)** — 기록할 상태가 없다.
- **⌘K 미리보기 순서(지금 먼저)** — 메뉴는 추천이 아니라 목록이다. 열 때마다 자리가 바뀌지 않아야 손이 기억한다. 스위처 순서를 그대로 쓴다(feature-review 2026-10-09).
- **지금 프로젝트를 상한 밖에서 끌어올리기** — 앱 셸에서는 LNB 머리가 이미 지금 프로젝트를 보인다. 상한 밖이면 체크 없이 둔다.
- **그룹 라벨(`role="group"` + `aria-label`)** — 다른 그룹도 라벨이 없고 `DropdownMenuGroup` export가 없다. 프리미티브를 늘리는 비용이 이득보다 크다(feature-review 2026-10-09).
- **실패 문구·Retry** — 위 그룹 `Projects`가 같은 목적지로 간다(design D2).
- **디자인 시안** — 기존 메뉴에 기존 스위처 행 형을 조립한다.
