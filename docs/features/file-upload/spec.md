# spec — file-upload

## 사용자

**개발자(나)**다. 이것은 화면이 아니라 **능력**이고, 첫 소비자가 계정 사진(`account-settings`)이다.
비개발자 동료는 이 기능을 "사진 바꾸기"로만 만난다.

## 문제

리포에 **파일을 받는 자리가 하나도 없다.** 지금 들어오는 바이트는 전부 텍스트이고
(`/api/push`의 JSON, 로케일 파일 내용), 그 경로는 크기·형식·수명을 신경 쓸 필요가 없었다.

`account-settings`가 아바타 업로드를 요구하면서 그 전부가 한꺼번에 필요해진다 — 저장 위치,
형식 검증, 크기 상한, 교체 시 옛 파일 정리, 삭제. **화면보다 이쪽이 크기 때문에 따로 뗀다.**

⚠️ **`User.image` 컬럼은 이미 있다** (Auth.js 표준 · `auth.ts`가 Google `profile.picture`를 넣는다).
만드는 것은 컬럼이 아니라 **우리가 소유하는 바이트의 저장 경로**다.

## 완료 조건

1. Server Action에 2 MB 이하 PNG/JPG를 넘기면 저장되고, **URL이 `User.image`에 들어간다.**
2. **매직 넘버로 형식을 판정한다** — 확장자와 `Content-Type`을 신뢰하지 않는다. `.png`로 이름만
   바꾼 SVG가 거부되는 것을 테스트가 보인다.
3. 2 MB를 넘기면 저장 전에 거부하고, 사유가 값으로 돌아온다(예외로 죽지 않는다 — ARCHITECTURE §6.3).
4. **사진을 교체하면 옛 파일이 지워진다.** 지우기가 실패해도 교체는 성공한다(고아 하나가 남는 것이
   교체 실패보다 싸다) — 그 사실이 서버 로그에 남는다.
5. 삭제하면 `User.image`가 `null`이 되고 파일도 지워진다.
6. `pnpm test`가 green이고, 판정 순수 함수 셋에 단위 테스트가 있다.

## 비목표

- **번역 스크린샷 첨부** — `docs/PRODUCT.md` §4.2 비범위다. 이 능력이 생겨도 그 판정은 안 바뀐다.
- **임의 파일·프로젝트 자산** — 받는 것은 **이미지 하나**이고 소유자는 `User` 하나다.
- **이미지 리사이즈·크롭 UI** — 고른 파일을 그대로 올린다. 2 MB 상한이 그 자리를 대신한다.
- **CDN 캐시 무효화 전략** — 키에 난수를 넣어 교체마다 새 URL이 되게 한다(무효화가 필요 없어진다).
