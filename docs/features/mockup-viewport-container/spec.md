# mockup-viewport-container — 랜딩 목업 그릇을 뷰포트가 고른다

상태: 스펙(2026-10-11, `/feature-review` 반영). [설계](design.md) · [태스크](tasks.md). 브리프 없음(MK1 시안의 틀·프레임을 그대로 쓰고 순환만 걷는다 — M 높이만 바꾼다).

## 사용자 정정 (2026-10-11)

> "아니 사용자 뷰포트에 따라, 컨테이너는 결정됨. PC면 PC씬만 순환. 모바일이면 Mobile씬만 순환" · "계획부터 잘못했네 이거"
> 그릇 경계: **3단 — 뷰포트 ≥1024 데스크톱 · 640~1023 태블릿 · <640 모바일**(사용자 선택).

responsive-mockup(2026-10-11 dev `fb4920b5`, 기능 디렉터리 닫힘)은 D5(2026-10-07 "16:10 데스크톱 → 태블릿 → 모바일 컨테이너를 순서대로")를 **씬마다 D→T→M 순환**으로 풀어 구현했다. **틀린 것은 그 해석 하나다** — 뷰포트가 그릇 하나를 고르고, 그 그릇 안에서 다섯 씬이 순환 이전처럼 교차한다. 그 spec의 비목표 원문 "목업의 뷰포트 `max-lg:` 분기, 기기명·UA로 내부 UI 선택"은 **이 기능에서도 그대로 산다** — 목업 **안**의 배치는 여전히 루트 `@container/mockup`이 정하고(V-06, ARCHITECTURE "뷰포트 토큰 0"), 뷰포트가 고르는 것은 **바깥 그릇의 폭·높이**뿐이다.

## 사용자

랜딩 방문자(공개) — **자기 화면 폭 부류(D·T·M)의 앱 모습**을 본다. 기기가 아니라 폭이 정하므로 가로로 든 폰(812)은 T, 좁힌 데스크톱 창(<640)은 M이다. 그릇 안 루트 폭은 1422·768·375 셋으로 고정이라 실물과 갈리는 구간이 있다(822~1023 실물은 두 판 / T는 한 판 · 1024~1277 실물은 트리 접힘 / D는 펼친 두 판) — 수용한다(DESIGN "목업 루트 컨테이너" 행에 적는다).

### 방문자가 보는 변화 (프로덕션 v1.3.1 대비)

| 뷰포트 | 지금 프로덕션 | 이 기능 뒤 |
|---|---|---|
| <640 | 축소된 D(사실상 못 읽음) | **M**(393×776 — 폭이 배율을 정한다) |
| 640~1023 | 축소된 D | **T**(786×900) |
| ≥1024 | D | D(변화 없음) |

⚠️ **출시 순서**: 순환(9eafafc7..9df288af)은 dev에만 있고 main에 없다. **이 기능이 dev에 들어가기 전에 `/merge`를 돌리지 않는다** — 돌면 순환이 프로덕션에 나간다.

## 비목표

- 기기명·UA 판정 없음 — 폭만 본다. 태블릿 그릇의 세로 비율·틀은 MK1 그대로(높이 900, 같은 Bezel). **M만 높이 776으로 바꾼다**(폭은 393 그대로).
- 목업 내부 레이아웃 변경 없음(K1 결과 유지). 새 화면 문구 없음.
- **`sm`(40rem) 경계는 공개 랜딩 목업의 그릇 선택에만 쓴다** — 앱·공개 셸 배치의 뷰포트 경계는 여전히 `lg` 하나다(PRODUCT §4.1·DESIGN §5에 예외로 등재).
