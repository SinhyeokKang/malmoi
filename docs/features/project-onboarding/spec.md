# project-onboarding — 탐지 온보딩 (SaaS 5단계)

> 정본은 [docs/SAAS.md](../../SAAS.md) §7.3·§7.4·§7.5·§7.8·§8 5단계다. 이 문서는 그 체크박스 여섯
> 개를 "무엇이 되면 끝인가"로 펼친 것이고, 결론은 끝나면 SAAS.md로 올라간다.

## 1. 사용자

**개발자(나)** 가 1차 사용자다. 리포를 말모이에 붙이는 사람이고, 지금은 그 일을 터미널에서 한다.

번역 편집자(비개발자 동료)는 **이 화면을 보지 않는다** — 초대 링크로 들어와 이미 `ready`인
프로젝트의 번역 화면에 착지한다. 다만 그 사람이 보게 되는 것이 여기서 정해진다: 온보딩이 작은
후보를 고르면 편집자에게는 "번역할 게 4개뿐인 프로젝트"로 보이고, 왜 그런지 알 방법이 없다.

## 2. 문제 — 관측된 것

1. **프로젝트를 만드는 경로가 없다.** `Project` 행은 손으로 넣거나 `pnpm push:local`이 만들지
   못한다(그 스크립트는 이미 있는 행을 채운다). 편집 UI는 멀티테넌트인데 **테넌트를 만들 수단이
   없다** — SAAS §5.7의 공격 시나리오 둘("설치되지 않은 리포를 Project로 등록"·"접근할 수 없는
   설치로 생성")이 4단계에서 판정만 서고 닫히지 못한 이유가 이것이다.
2. **탐지가 조용히 작은 쪽을 고른 전례가 있다.** bugshot-2에서 `_locales`(4키, 스토어
   메타데이터)가 `ts-dict`(903키, 앱 UI)를 가렸고 **에러가 나지 않았다** (TASKS §7). 그 판단을
   지금은 `--adapter` 플래그를 아는 사람만 뒤집을 수 있다.
3. **탐지는 처음 보는 리포에서 6.3% 틀린다** (ADAPTER-COVERAGE §0 3차, 홀드아웃 20개). 학습
   코퍼스 0.0%는 과적합이었다 — 자동 확정은 그 6.3%를 조용한 오설정으로 바꾼다.
4. **배포 하나가 프로젝트 하나만 받는다.** `/api/push`·`/api/pull`이 `ACTIVE_PROJECT_SLUG`
   하나를 보므로 두 리포의 CI를 동시에 붙일 수 없고(다른 쪽은 409), 야간 pull도 한 프로젝트만
   돈다. 프로젝트를 만들 수 있게 되는 순간 이 제약이 곧바로 막는다.
5. **연동 실패의 원인을 사람이 못 읽는다.** 지금 실패는 CLI의 exit 1과 `/api/push`의 4xx 본문으로만
   드러나고, 둘 다 터미널·Actions 로그를 여는 사람만 본다.

## 3. 완료 조건 — 검증 가능한 문장으로

**SAAS §8 5단계의 완료 게이트 셋을 그대로 잇고, 검증 방법을 붙였다.**

1. **새 사용자가 문서나 터미널 없이 첫 적재를 완료한다.**
   검증: 로그인 → `/projects/new` → GitHub 연결 → 리포 선택 → 후보 확정 → 번역 화면에 키가
   보인다. 이 경로에 `pnpm`·`.env`·`prisma studio`가 한 번도 등장하지 않는다.
2. **작은 후보가 큰 표면을 조용히 가리지 않는다.**
   검증: bugshot-2를 대상으로 돌리면 `_locales`(4키)가 1순위로 뜨되 **키 수가 화면에 보이고**,
   후보 목록 아래의 수동 지정으로 `ts-dict`(903키)를 고를 수 있다. ⚠️ `ts-dict`는 자동 탐지에
   참여하지 않으므로(`detectCandidates`가 항상 `[]`) **수동 지정이 그 포맷의 유일한 경로다** —
   수동 지정 없이는 이 조건이 절반만 충족된다.
3. **확정하지 않은 추정값으로 `ready`가 되지 않는다.**
   검증: 후보와 기준 로케일을 사용자가 고르기 전에는 `Project` 행이 생기지 않는다. 행이 생겨도
   **첫 적재가 성공하기 전에는 번역 화면에 들어갈 수 없다** (§7.5 불변식 8).
4. **접근할 수 없는 설치·리포로는 프로젝트가 만들어지지 않는다.**
   검증: 남의 리포 `owner/repo`를 직접 POST해도 `planRepoConnect`가
   `installation-forbidden`·`repo-forbidden`·`repo-not-installed`로 거부한다. SAAS §5.7의 미종결
   시나리오 둘이 여기서 닫힌다.
5. **두 리포의 CI를 동시에 받는다.**
   검증: 프로젝트 둘에 각자의 push 토큰을 발급해 양쪽 리포 CI를 돌리면 둘 다 200이고 서로의
   키를 orphan시키지 않는다. `ACTIVE_PROJECT_SLUG`가 리포에서 사라진다
   (`grep -rn ACTIVE_PROJECT_SLUG` 0건 — 문서·스킬 포함).
6. **야간 pull이 모든 준비된 프로젝트를 돈다.**
   검증: 프로젝트 하나가 실패해도 나머지가 계속 돈다(응답에 프로젝트별 결과가 배열로 온다).
7. **실패가 사람이 읽는 한 줄로 화면에 닿는다.**
   검증: 실패 갈래마다 문구가 다르고 `?e=`로 넘긴 사유를 **읽는 쪽이 있다**
   (POSTMORTEM 2026-09-06 — 거부를 쿼리로 넘겨놓고 읽는 쪽을 안 만들면 통째로 무음이다).

## 4. 범위 밖 — 이번에 안 하는 것

- **코드 참조(`refs`) 수집.** 서버는 리포를 체크아웃하지 않으므로 ts-morph를 돌릴 수 없다. 첫
  적재의 `refs`는 **빈 배열**이고, permalink는 CI가 처음 push한 뒤에 채워진다. 온보딩 화면이
  그 사실을 한 줄로 알린다.
- **연동 PR 자동 생성.** 복사용 워크플로 YAML만 낸다 (2026-09-07 결정 — design §7).
  App에 Workflows write를 더하면 **기존 설치 넷이 전부 재승인 대기**가 되고 그동안 pull이 죽는다.
- **프로젝트 삭제·보관.** SAAS §7.9는 "보관까지만"이라고 정했지만 그 화면은 6단계다. 잘못 만든
  프로젝트는 지금처럼 DB에서 지운다.
- **멤버 관리 화면.** 6단계다. 생성자는 `ProjectMember(OWNER)` 한 행으로 시작한다.
- **`SyncRun`·동시 실행 차단·고정 제한 전반.** 7단계다. **예외 하나** — 사용자당 프로젝트 3개
  제한만 여기서 건다(2026-09-07 결정: 자율 가입을 여는 대가다).
- **로케일 추가·삭제 UI.** SAAS §7.2 — 리포가 정본이다.
- **재탐지 자동화.** 로케일 파일이 사라졌을 때의 `needs_configuration`은 7단계다.

## 5. 이 단계가 남기는 빚

- **`ts-dict` 리포는 수동 지정이 필수다.** 온보딩이 그것을 화면에 노출하지만, "왜 안 뜨지"를
  사용자가 겪는다는 사실 자체는 그대로다 (ADAPTER-COVERAGE 판정 ③).
- **한 리포에 표면이 둘이면 프로젝트를 두 번 만든다** (§7.1). 온보딩이 그것을 안내하지 않는다 —
  `features/README.md` 백로그의 "로케일 디렉터리의 네임스페이스 여러 개"와 같은 자리다.
- **push 토큰 원문은 생성 시 한 번만 보인다.** 잃어버리면 재발급이 필요하고, 그 버튼은 설정
  화면에 둔다(초대 토큰과 같은 모델).
- **로케일이 하나뿐인 리포는 붙일 수 없다.** 탐지의 "로케일 2개 이상" 규칙 때문이고 수동 지정도
  같은 규칙을 지난다 — 온보딩은 그것을 `no-candidates`로만 말한다. `features/README.md` 백로그가
  이 판정을 5단계에 배정했는데, **여기서 답하지 않고 진단 문구에 이유를 담는 데까지만 간다**
  (규칙을 바꾸면 어댑터 재측정이 따라오고, 근거가 아직 리포 1건이다 — ADAPTER-COVERAGE §6 순위 4).
