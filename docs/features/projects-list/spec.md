# spec — Projects 목록 재설계 (`/projects`)

**시안 정본**: Claude Design `malmoi` 프로젝트의 `design_handoff_projects_list/`
(`Projects.dc.html` 아트보드 `1a`·`1b`·`1c`·`1e`·`1f`·`1g`·`1h`·`3a`·`3b` + `README.md`).
아트보드 id는 그 캔버스의 배지와 같다.

## 사용자

**둘 다 본다. 그래서 이 화면은 둘의 요구가 정면으로 갈리는 자리다.**

| | 개발자(OWNER) | 번역 편집자(EDITOR) |
|---|---|---|
| 이 화면에 오는 이유 | "지금 막힌 프로젝트가 있나" — 연결 끊김·첫 적재 실패·안 보낸 편집 | "내가 번역할 것이 어디 있나" |
| 할 수 있는 일 | 재연결 · 설정 마무리 · Publish | 번역 · 검토 · Publish(PRODUCT §3) |
| 할 수 **없는** 일 | — | 리포 재연결 · base 변경 · 보관 |

마지막 칸이 **행 아래 띠의 문구를 가르는 축**이다 — EDITOR에게 [Reconnect]를 보여 주면 눌러서
거절당하는 경험이 된다. PRODUCT §3의 권한표가 그 판정의 정본이다.

## 문제

관측된 사실 넷.

1. **필터 탭 여섯이 늘 그려진다** (`PROJECT_FILTERS` = `all` + 상태 다섯,
   `components/projects/project-list.tsx:131`). 생성 제한은 **OWNER의 활성 프로젝트 3개**이며,
   초대·보관을 포함하는 목록 전체의 상한은 아니다. 프로젝트가 적은 목록에서도 모든 탭이 노출돼
   빈 탭을 누른 사용자가 프로젝트를 잃었다고 읽을 수 있다.
   그 빈 화면의 문구(`m.projects.narrowed.byFilter` = "No project in this view.")가 이미
   그 사고를 전제하고 쓰여 있다.
2. **상태가 배지 하나로만 말한다.** 행이 드는 것은 이름 · 리포 URL · 역할 · 멤버 수 · 상태 배지뿐이고
   (`project-list.tsx:275-303`), **"그래서 지금 뭘 하면 되나"에 답하는 자리가 없다.**
   안 보낸 편집 24건도, 검토 대기 88건도, 끊긴 연결의 복구 링크도 이 화면에는 없다 —
   전부 프로젝트를 하나씩 열어야 보인다.
3. **진행률이 없다.** 로케일별 진행률은 `/projects/:slug/locales`에만 있고
   (`localeProgress`, `lib/keys/view.ts:427`), 목록에서는 "어느 프로젝트가 덜 됐나"를 못 본다.
4. **계정 전체의 잔량을 아는 자리가 없다.** 번역할 것이 총 몇 개인지, 검토 대기가 몇 개인지,
   안 보낸 편집이 몇 개인지는 프로젝트를 전부 열어 더해야 안다.

## 완료 조건

검증 수단을 괄호에 적는다. **`pnpm test` green + `/bugshot-qa`**가 게이트다.

1. **필터 탭이 사라지고 검색만 제목 줄에 남는다.** `?filter=`를 받는 코드가 목록 경로에서 0이고
   (`grep -rn "parseProjectFilter\|filterProjects\|PROJECT_FILTERS" app components lib` → 테스트 제외 0건),
   `/projects?filter=active`로 들어와도 **전체 목록**이 뜬다(무시되고 404·리다이렉트가 아니다).
2. **목록이 그룹 셋으로 묶인다** — `Needs attention` · `All set` · `Archived`. 그룹 판정이
   서버의 순수 함수 하나이고(`lib/projects/list.ts`), 헤더마다 카운트 배지가 선다.
   (단위 테스트: 상태표의 유효 행 × 그룹 매트릭스와 사건 중첩 조합)
3. **보관이 목록에서 사라지지 않는다** — 세 번째 그룹으로 남고 이름만 `#737373`로 내려간다.
   (기존 결정 유지 — `project-list.tsx:296` 주석과 PRODUCT §7.9)
4. **머리에 Summary 넷이 선다** — `New from GitHub` · `To translate` · `To review` · `To send`.
   내 멤버십 중 **보관하지 않은 프로젝트 전체**의 값이고 검색·그룹에 흔들리지 않는다.
   보관 행과 Meter는 목록에 유지하되 Summary 네 항목에서는 제외한다.
   보관 프로젝트만 있으면 Summary 네 값은 0이며 프로젝트 0건용 빈 화면으로 바꾸지 않는다.
   누를 수 없다(hover·cursor·테두리 없음).
   `New from GitHub`는 **마지막 pull 이후 추가된 활성 키**다. 마지막 pull이 있으면
   `StringKey.orphaned = false AND createdAt > Project.lastPulledAt`으로 센다.
   첫 pull 전(`lastPulledAt = null`)에는 **활성 키 전체**를 센다.
   (소스 검사: Summary 블록 안에 `<a`·`Link`·`href`가 0)
5. **행이 로케일 Meter를 최대 셋 든다.** 완료 `rgba(10,10,10,0.85)` + 검토 대기 `#f59e0b` 두 구간.
   값이 없는 상태(`setup`·`awaiting_first_sync`)는 0% 바가 아니라 **문장**이 그 자리에 선다.
   문장의 기준 폭은 332px이며 좁은 화면에서는 남은 폭에 맞춰 축소·말줄임한다.
   (실측: 컨테이너 840·680px에서 상태 배지·화살표·행 포커스 링 잘림 없음)
6. **행 아래 띠가 다음 한 수를 말한다.** 겹치면 **하나만** 그리고, 우선순위가 순수 함수다.
   `Reconnect`·`Continue setup`·`View details`만 EDITOR에게 링크 대신 안내 문구를 표시한다.
   `rowBanner`의 우선순위는 순수 함수 테스트, 역할별 링크는 렌더 테스트로 검증한다.
7. **DB 왕복 수가 상수다.** 프로젝트 수에 비례해 **쿼리**가 늘지 않는다
   (멤버십 1회 + 집계 5회, 프로젝트 0건이면 멤버십 1회만. 호출 수 테스트로 N+1 회피).
   ⚠️ **GitHub 조회는 보관 제외 전부 수행한다.** 필요한 식별자가 있는 프로젝트마다 compare·PR 상태를
   조회하고 **동시에 처리하는 프로젝트만 최대 3개**로 제한한다. 하나가 끝나면 다음 것을 시작한다.
   총 조회 수는 프로젝트 수에 비례하며, 토큰 발급·리포 확인 요청도 별도로 센다(design §3.4).
   (검증: 대상 10개 전부 처리, 실행 중 프로젝트 최대 3개, 보관 프로젝트 요청 0)
7.5 **GitHub이 실패해도 목록이 뜬다.** `pr_open`·`repo_ahead` 띠만 빠지고 나머지는 그대로 선다.
8. **빈 상태 둘이 형이 다르다.** 프로젝트 0건은 KV 합성(검색·Summary·머리 [New project]를 그리지 않는다),
   검색 0건은 `EmptyState` 규격 그대로 + 액션 둘.
9. **`?e=` Alert가 제목 줄 아래·Summary 위에 선다.** 목록은 그대로 살아 있다.
10. **스켈레톤이 실물 골격을 따라간다** — 제목 줄 · Summary 넷 · 그룹 헤더 · 행 둘.
    `motion-safe:` 분기 유지.
11. **행의 focus 링이 `ring-inset`으로 남는다.** (`focus-ring.test.ts` 계보)
12. **CI 파싱 실패도 목록에 남는다.** `scripts/push-local.ts`가 `/api/push` 도달 전의
    파싱 실패를 프로젝트 토큰으로 보고하고, 목록과 OWNER 설정 화면에 안전한 실패 문구가 표시된다.
    보고 요청이 실패해도 원래 파싱 오류와 CI exit 1은 유지한다. 최초 적재·재시도의 실패와
    부분 실패도 기록한다. (실패 주입: 정상 보고·보고 타임아웃·오배송·재시도 성공)

## 비목표

- **그룹 접기.** 세 헤더가 이 화면의 목차다. 보관이 5건 이상 쌓이면 그때 다시 본다(design §9의 열린 결정 2).
- **탭 부활.** 되돌아올 조건은 이미 정해져 있다 — `Archived`가 쌓이면 `All / Archived` **둘로만**.
  상태 다섯을 그대로 되살리지 않는다.
- **Summary 칸의 링크.** 계정 단위 큐 화면이 생기기 전까지는 표시 전용(열린 결정 1).
- **정렬·페이지네이션 컨트롤.** 이번 변경은 전체 목록을 `slug asc`로 제공한다. 조회 대상 수를 자르지 않는다.
- **프로젝트 이미지 업로드.** 글리프 자리(28 · `toneFill`)는 그대로 둔다.
- **`?filter=`의 영구 호환.** 옛 링크는 **조용히 무시**한다(리다이렉트를 만들지 않는다).
- **Publish 실행.** 띠의 [Send changes]는 **번역 화면으로 가는 링크**이지 Action이 아니다 —
  Publish는 라우트가 아니라 번역 화면 툴바의 버튼이다(PRODUCT §7.7).
- **알림·이메일.** §4.2 비범위 그대로.
- **Meter의 추가 스크린리더 설명.** 완료율·검토 대기율을 함께 읽는 설명은 이번 범위에서 제외한다(2026-09-13 사용자).

## 스키마 (2026-09-13 결정)

**additive 셋** — `StringKey.createdAt` · `Project.lastImportStartedAt` · `Project.lastImportError`.
기존 키의 `createdAt`은 **`COALESCE(Project.lastPulledAt, Project.createdAt)`으로 backfill**한다.
pull 이력이 있으면 기존 키를 초기 신규 집계에서 제외하고, 없으면 활성 키 전체를 센다. 자세한 것은
`design.md` §8이고, 적용은 `/db`가 받는다 — dev는 `/push` 전, prod는 `/merge` 1단계.

**CI 파싱 실패 포함 결정(2026-09-13):** 외부 진입점 `POST /api/push/failure`를 추가한다.
새 토큰이나 Action input은 만들지 않고 기존 `PUSH_TOKEN`을 사용한다. 서버 계약을 먼저 배포하고
실패 보고를 포함한 Action을 릴리스해야 대상 리포에서 이 경로가 동작한다(`design.md` §3.35).

## 범위 게이트

**PRODUCT §4.2 비범위에 걸리는 항목 없음.** §4.3의 다섯 판정과도 무관하다(로그인·웹훅·provider·
계정 병합·MCP 어느 것도 건드리지 않는다).

기존 결정과의 관계 및 문서 갱신 필요는 아래와 같다.

| 마찰 | 어느 결정 | 판정 |
|---|---|---|
| `?filter=`(값 여섯) 제거 | PRODUCT §7.7 "필터는 쿼리 상태다" 문단이 **목록의 `?filter=`를 명시**한다 | **PRODUCT 갱신 필요** — 그 문장에서 목록 `?filter=`를 빼고 `?q=`만 남긴다 |
| 계정 전체 집계 넷 (DB) | PRODUCT §7.7 IA 결정 5가 **사이드바 카운트**를 거절했다 | **갱신 불필요.** 거절 대상은 "**모든 화면**의 셸이 매 렌더에 세는 것"이고 이건 **이 화면 하나**다. 같은 절의 재정당화 조건 ②가 이 경우를 예견하고 답까지 정해 뒀다 — *"`/projects` 목록의 프로젝트별 카운트가 N+1이 된다(실재하지만 **`GROUP BY` 한 쿼리로 끝난다**)"*. 그 답을 그대로 쓴다. ⚠️ **`loadMemberships`는 넓히지 않는다** |
| 빈 상태 KV · 결과 0건의 액션 **둘** | DESIGN §6.4 "빈 상태 패턴 — 짧은 제목 · 문장 하나 · **버튼 하나**" | **DESIGN 갱신 필요** — 예외 둘을 등재한다. `EmptyState.action`은 `ReactNode` 하나라 구조적으로는 이미 둘을 받는다(`components/ui/empty-state.tsx:31`) |

**코어 설계 원칙(ARCHITECTURE §0)과 충돌 없음** — 실패 보고는 프로젝트의 임포트 상태만 기록한다.
키·번역·소스 커밋 기준점은 바꾸지 않으며 머지·충돌 해소·양방향 동기화를 요구하지 않는다.

⚠️ **"repo moved ahead"가 그 경계에 가장 가깝다.** 리포와 DB를 **비교**하지만 **값을 고르지 않는다** —
화면은 "base가 앞섰고 로케일 파일 n개가 바뀌었다"만 말하고, 다음에 무엇이 이기는지는 여전히 push가
정한다(불변식 1·2: push 시점엔 리포가 DB를 덮는다). **이 띠에 "머지"·"해결" 같은 동작을 붙이는 순간
원칙이 깨진다** — 링크는 GitHub의 compare 화면으로만 나간다.
