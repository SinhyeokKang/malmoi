## 1. 결정과 범위 게이트

- 사용자 확정: **Resend로 멤버 초대 메일 발송**, 본문은 **초대 링크 한 줄**, **다중 초대·사람별 역할**, 전원 발송 접수 성공 시 **모달 종료+토스트**.
- 사용자 확정: 재발급은 이전 링크를 만료시키며, 같은 프로젝트·주소 **60초 간격**, 프로젝트 전체 **최근 1시간 20건** 제한. 발송 실패도 이미 생성한 초대 횟수에 포함한다.
- 사용자 위임: 불필요한 상태·분기를 판단해 줄인다. 이에 따라 **부분 성공 편집 화면·성공자 목록·링크 복사 대안**을 제외하고, 검증 통과한 요청 전체를 발급하는 구조로 단순화한다.
- 추가 사용자 확정: **Pending invitations의 Resend는 유지**한다. 앞서 그 버튼을 제외했던 결정을 대체한다.
- PRODUCT §4.2의 이메일 비범위를 안내한 뒤 사용자가 스펙 작성을 요청했으므로 **멤버 초대 메일만 예외**로 진행한다. 정본 PRODUCT §4.1·§4.2·§4.3 갱신은 구현 태스크에 포함한다. 이메일 로그인·범용 알림은 비범위다.

## 2. 사용자와 문제

개발자 OWNER가 비개발자 동료 여러 명을 초대할 때, 한 명씩 링크를 발급해 메신저로 전달해야 한다. 여러 사람의 이메일·역할을 한 폼에 입력하고 메일로 보내 이 작업을 끝낸다.

초대 수락은 기존 경로를 유지한다. 링크 조회만으로 가입하지 않으며, GitHub/Google 로그인 후 검증된 이메일 대조와 명시적 수락을 거친다.

## 3. 사용자 흐름

1. OWNER가 Email / Role / Remove 행을 추가한다. 사람마다 Editor/Owner를 선택하며 새 행 기본값은 Editor다. 여러 주소 붙여 넣기를 지원한다.
2. 제출 전에 주소 형식·중복을 검사한다. 서버는 전체 대상의 이미 멤버 여부·발급 제한·좌석·설정도 검증한다. **하나라도 거부되면 이번 요청은 아무 초대도 새로 만들거나 발송하지 않는다.** 사용자가 해당 입력을 수정/제거하고 다시 제출한다.
3. 모두 통과하면 초대 전체를 저장한 뒤 Resend에 개인별 메시지의 배치 요청을 한 번 보낸다. 각 메일의 수신자는 한 명이다.
4. 전체 접수 확인 시 모달을 닫고 `Invitations sent to N people` 토스트를 보인다. 입력은 초기화하고 Pending 목록을 갱신한다. 성공 화면·링크·Done 단계는 없다.
5. 실패나 결과 미확인은 **같은 폼에서 입력을 유지하고 안내 한 곳**에 보인다. 성공자/실패자 목록을 나누지 않는다. 자동 재시도하지 않으며 제한이 풀린 뒤 수동 재시도한다.
6. Pending의 **Resend**는 저장된 주소·역할로 새 초대와 메일을 만든다. 별도 모달/확인창 없이 그 행만 처리 중으로 표시한다. 성공 토스트 후 목록을 갱신하고, 오류는 대상 라벨을 포함한 안내로 보인다.

메일 제목 기본안은 `You're invited to malmoi`, 발신자 제안은 `malmoi <invite@notify.mal-moi.com>`이다. 발신 주소는 DNS 인증 가능한 주소로 운영 설정 때 확정한다. 본문은 `https://mal-moi.com/invite/<token>` 형태의 plain-text URL 하나다. HTML·서명·프로젝트명·역할·추적 요소는 넣지 않는다.

## 4. 실패 계약과 수용하는 비용

| 상황 | 표시와 처리 |
|---|---|
| 주소·역할·중복·이미 멤버 | 문제 행에 오류. 요청 전체 쓰기·발송 없음 |
| 인가·좌석·설정·발급 제한 | 폼 오류 또는 Resend 오류. 쓰기·발송 없음. 제한이면 서버의 재시도 가능 시각 안내 |
| DB 실패 | 생성 실패. 트랜잭션 전체 롤백, 외부 발송 없음 |
| 메일 명시적 거부 | 초대는 생성됐지만 메일 요청 실패. 입력 유지, 제한 후 재시도 |
| 타임아웃·통신 오류·불완전 응답 | 발송 결과를 확인하지 못했다고 안내. 성공 수·실패 수를 추정하지 않음 |
| 전체 접수 확인 | 모달 종료 또는 Resend 토스트. 수신·열람·가입 완료로 표시하지 않음 |

**DB의 일괄 저장과 실제 메일 배달의 원자성은 다르다.** 일부 메일이 이미 접수/배달됐는데 응답을 잃을 수 있다. 다시 보내면 중복 메일이 갈 수 있고 이전 링크는 만료된다. unknown 안내는 이를 짧게 알린다. 실제 도착 인원별 상태를 복원하는 기능은 만들지 않는다.

메일 장애 동안 초대가 지연된다. 수동 링크 발급·복사 대안은 제거한다. 발급 후 프로세스가 종료되면 미발송 초대가 Pending에 남을 수 있으며 OWNER가 Resend로 복구한다. 이미 생성된 초대를 메일 실패 때문에 롤백하거나 이전 토큰으로 되돌리지 않는다.

좌석 제한은 기존 정책대로 **발급 시점의 현재 멤버 수가 10명 미만인지** 판정한다. 대기 초대나 이번 입력 인원을 예약 좌석으로 세지 않으므로, 현재 9명일 때 3명을 초대하고 모두 수락하면 12명이 될 수 있다. 수락 후 인원 상한을 새로 강제하지 않는다.

## 5. 완료 조건

- [ ] 여러 주소에 서로 다른 역할을 지정하고 전체 접수 성공 시 링크 화면 없이 닫힌다.
- [ ] 사전 검증 하나라도 실패하면 전체 초대 생성·기존 토큰 회전·발송이 0회다.
- [ ] 각 메일에는 자기 링크 하나만 있고 다른 수신 주소가 없다.
- [ ] Pending Resend는 OWNER만 가능하며 저장된 주소·역할을 사용한다. 재발급 시 만료 7일·초대한 사람을 갱신하고 이전 링크는 무효다.
- [ ] Resend와 모달이 같은 60초/시간당 20건 제한을 공유한다. 3명 발급은 3건이고 철회·동시 요청으로 우회되지 않는다.
- [ ] 명시적 거부와 결과 미확인을 구분하되, 별도 결과 화면이나 주소별 발송 상태 모델은 없다.
- [ ] 초대 토큰 원문은 DB·앱 로그에 저장하지 않으며, 발급·Resend Action 응답과 OWNER 관리 UI의 클라이언트 상태에 노출하지 않는다. 발급 측에서는 서버 메모리와 메일 전달에만 사용하고, 수신자의 기존 토큰 URL·로그인 복귀·명시적 수락 경로는 유지한다.
- [ ] 미가입·다른 프로젝트·EDITOR의 초대/Resend가 거부되고, 만료·철회·수락된 행을 Resend로 되살리지 않는다.
- [ ] 기존 이메일 대조·단일 사용·만료 판정을 유지하며 GET/HEAD는 토큰을 소비하지 않는다.
- [ ] 단위·DOM·동시성 검증 및 지정 수신자의 dev/prod 실제 왕복을 완료한다.

## 6. 비목표

부분 성공 전용 화면, Already sent 블록, 주소별 발송 결과/선택 재시도, 수동 링크 발급·복사, 발송 이력/배달/열람 추적, 자동 재시도·작업 큐, 범용 알림, SMTP 서버 운영, CSV·캠페인 발송, 이메일 로그인은 만들지 않는다. Pending의 Resend와 기존 Revoke는 범위에 포함한다.
