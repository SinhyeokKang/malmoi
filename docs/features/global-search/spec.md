# global-search — 스펙

## 범위 게이트 (2026-10-01 사용자 확인)

이 기능은 **옛 판정 둘을 뒤집는다** — 사용자가 재확인했다("뒤집고 진행").

1. **DESIGN §6.5 · §9.2 "헤더의 검색·`+`·카운터는 넣지 않는다 — PRODUCT §4.2가 기능 밀도를 막는다"** → 헤더 중앙에 검색 트리거 하나를 넣는다.
   `+`(`New project`)는 2026-09-30에 이미 헤더로 들어왔고, 카운터는 여전히 넣지 않는다.
   **왜 기능 밀도 비범위와 충돌하지 않나**: 새 목적지·새 데이터·새 권한을 만들지 않는다 — 이미 있는 목적지(프로젝트·메뉴·가이드·릴리스 노트)로 가는 **입구 하나**다. 사이드바 항목은 늘지 않는다.
2. **PRODUCT §7.7 `/changelog` 비범위 "검색·필터·페이지네이션"** → 그중 **검색만** 글로벌 검색으로 연다. `/changelog` 페이지 자체에는 검색창을 넣지 않는다(필터·페이지네이션도 여전히 없다).

PRODUCT §4.2 목록에 직접 걸리는 항목은 없고, 코어 설계 원칙(병합 없음 · export 결정성)과 닿는 곳이 없다 — DB를 **읽기만** 한다(키·번역값 검색).

**키·번역값 검색은 범위 안이다** (2026-10-01 사용자 — 처음엔 "내비게이션만"을 골랐다가 성능 판단을 듣고 넣었다). 조건: 트라이그램 인덱스 없이 시작하고, 실측이 기준을 넘을 때만 additive 마이그레이션으로 인덱스를 넣는다(완료 조건 20).

## 사용자

**셋이다** — 이 도구의 두 사용자에 공개 셸 방문자가 더해진다.

- **번역 편집자(비개발자)**: 가이드에서 "어떻게 하지"를 찾는다(예: Publish · Revert · 초대 수락). 지금은 `/docs`의 문서 내비 29쪽을 눈으로 훑는 길뿐이다. 그리고 동료가 말한 문구("결제 버튼 문구 바꿔 주세요")가 **어느 프로젝트·어느 소스의 어느 키인지**를 찾는다.
- **개발자(OWNER)**: 프로젝트 여럿을 오가며 특정 화면(Settings · Sources · Logs)으로 간다. 지금은 사이드바 스위처로 프로젝트를 바꾼 뒤 사이드바 항목을 한 번 더 누른다.
- **비로그인 방문자**(공개 셸 — 랜딩 · `/docs` · `/changelog` · `/privacy`): 가이드·릴리스 노트만 찾는다.

⚠️ **결과 집합은 라우트(어느 셸인가)가 아니라 로그인 세션으로 갈린다** (2026-10-01 사용자) — 로그인 사용자는 `/docs`를 읽다가도 자기 프로젝트·키로 바로 간다. 셸이 정하는 것은 트리거의 자리뿐이다.

**상충**: 없다. 결과 집합이 역할·로그인 여부로 좁혀질 뿐 서로의 동작을 바꾸지 않는다.

## 문제 (관측된 사실)

1. **`/docs`에 검색이 없다.** 원고 29쪽(`guide/SUMMARY.md`)을 트리 내비와 페이지 목차(H2)로만 찾는다 — 본문에만 있는 낱말(`PUSH_TOKEN`, `base-locale`, `stale-commit`)은 어느 페이지에 있는지 알 수단이 없다.
2. **`/changelog`에 검색이 없다** — 최대 100판(`RELEASES_PAGE_SIZE`)이 한 페이지에 쌓이고, 브라우저 찾기(⌘F) 말고는 "그 변경이 몇 판에 들어갔나"를 답할 수단이 없다. PRODUCT §7.7이 일부러 뺀 것이다.
3. **프로젝트 이동과 메뉴 이동이 두 단계다.** 스위처(`components/shell/project-switcher.tsx`)는 프로젝트 이름만 찾고 Home에 착지한다 — 다른 프로젝트의 Settings로 가려면 스위처 → Home → 사이드바 Settings 세 번을 누른다.
4. **번역 화면 검색은 한 프로젝트 안이다** — `lib/keys/translation-list.ts`의 `?q=`는 `projectId` 하나로 좁혀 키·원문·번역값을 `ILIKE`로 찾는다. 문구가 어느 프로젝트에 있는지 모르면 프로젝트마다 번역 화면을 열어 같은 낱말을 다시 친다.
5. **검색창이 화면마다 따로다** — `/projects`(이름) · 번역 화면(키) · Logs(사건)의 `SearchInput`은 그 화면 안을 좁히는 도구이고, 화면을 가로지르는 입구는 없다.

## 완료 조건

트리거:

1. **앱 셸 헤더**(`components/shell/header.tsx`)와 **공개 셸 헤더**(`components/public-shell/header.tsx`)의 **가로 중앙**에 캡슐 모양 버튼이 선다 — 검색 글리프 + placeholder 문구 `Search…` + 단축키 칩. 좌·우 묶음의 폭이 달라도 뷰포트 중앙에 있다(좌우 너비 차이로 밀리지 않는다 — DOM 테스트가 구조로, `/runtime-test`가 실측으로 확인).
2. 버튼을 누르거나 **⌘K(macOS) / Ctrl+K(그 밖)**를 누르면 검색 Dialog가 열리고 포커스가 입력에 있다. 한글 조합 중의 키 입력은 단축키로 읽지 않는다.
3. 버튼은 접근 이름 `Search`(말줄임 없음 — DESIGN §10), `aria-haspopup="dialog"`, `aria-keyshortcuts`를 가진다.

Dialog:

4. 입력이 비어 있으면 **최근 검색어**(최대 5개, 최신 먼저)가 보인다. 항목을 고르면 그 낱말이 입력에 채워진다. 그룹 머리의 `Clear`가 전부 지운다 — **항목별 지우기는 없다**(`role="option"` 안에 버튼을 두면 중첩 상호작용이 되고, 5개 상한이라 밀려나며 사라진다). 최근 검색어가 없으면 안내 문장 한 줄이다.
5. 입력하면 결과가 **그룹**으로 선다 — 순서 `Projects · Pages · Keys · Docs · Changelog`, 그룹당 최대 5행, 빈 그룹은 그리지 않는다. 결과 0건이면 `No results for “{q}”`(곡선 따옴표 — DESIGN §6.63).
6. 결과를 고르면(클릭 또는 Enter) 그 목적지로 이동하고 Dialog가 닫히며, 그때의 입력값이 최근 검색어 맨 앞에 저장된다(대소문자 무시 중복 제거). **입력하는 동안에는 저장하지 않는다.**
7. 키보드: ↑↓로 활성 행이 이동하고(끝에서 반대편으로 순환), Enter가 활성 행을 연다. 포커스는 입력에 남는다(`aria-activedescendant`). 조합 중 Enter·Esc는 조합 확정·취소이고 이동·닫기가 아니다. Esc는 닫는다. 마우스 hover는 활성 행을 바꾸되 포커스를 입력에서 빼앗지 않는다(스위처와 같은 이유 — 한글 첫 글자 유실).
8. 결과 행의 일치 구간이 `<mark>`로 칠해진다(`/projects` 검색 강조와 같은 형). `İ`처럼 소문자화로 길이가 바뀌는 글자에서 강조가 어긋나지 않는다(POSTMORTEM 2026-09-13 재발 방지 테스트).

결과 집합:

9. **Projects** (로그인이면 어느 셸이든): 내 멤버십 전부 — 보관 포함(`Archived` 배지) · 썸네일 · 이름 일치. 고르면 그 프로젝트 Home. 앱 셸은 레이아웃이 이미 받은 멤버십을 쓰고(**새 DB 조회 0**), 공개 셸은 로그인일 때 **Dialog를 처음 열 때 한 번** 멤버십을 받는다(공개 페이지 렌더에 조회를 더하지 않는다).
10. **Pages**: 로그인이면 ① 사용자 메뉴(`Projects` · `New project` · `MCP connector` · `Account`) ② 멤버십마다 프로젝트 메뉴(`projectSections(role)` — `Project settings`는 `project:settings` 역할만) ③ 하단 전역(`Changelog` · `Docs`). 프로젝트 메뉴 행은 "메뉴 이름 · 프로젝트 이름"이고 두 필드를 가로질러 맞춘다(`settings demo` → demo의 Project settings). **지금 보고 있는 프로젝트의 메뉴가 먼저**다(공개 셸에는 '지금 프로젝트'가 없다). 비로그인이면 ③만이다.
11. **Docs**: 서빙되는 가이드 페이지(SUMMARY 등재 — AUTHORING·SHOOTING 제외)의 **절 단위** 항목 — 페이지 첫 절(제목 아래 도입부)과 표식 있는 H2 절마다 하나. 제목·절 제목·본문 텍스트를 맞추고, 본문 일치면 일치 주변 한 줄을 보인다. 고르면 `routes.docs(page, anchor)`.
11a. **Keys** (로그인이면 어느 셸이든): 내가 멤버인 **보관 안 된** 프로젝트의 **보관 안 된** 소스에서 orphaned 아닌 키 중, 키 이름 · 원문(`sourceText`) · 번역값 어느 하나가 **질의 전체를 부분 문자열로** 품는 것(대소문자 무시 — 번역 화면 `?q=`와 같은 규칙이라 클릭해 간 화면과 판정이 같다). 행은 키 이름(강조) · `프로젝트 · 소스` · 일치한 필드 한 줄(원문이면 원문, 번역값이면 `ja  값`). 순위는 키 이름 일치 > 원문 일치 > 번역값 일치, 같은 급이면 지금 프로젝트 먼저 → 키 이름 오름차순. 고르면 그 키가 선택된 번역 화면(`?ns=` · `?key=` · `?keySurface=` — Logs의 `Open this translation`과 같은 착지, 필터는 켜지 않는다).
11b. Keys 조회는 **trim 뒤 2자 이상**에서만, 마지막 입력 뒤 250ms에 한 번 나간다. 늦게 돌아온 응답이 새 질의의 결과를 덮지 않는다. 조회 중에는 Keys 자리에 로딩 한 줄, 실패하면 `Keys can't be searched right now.` 한 줄이고 다른 그룹은 그대로다.
11c. **다른 사용자의 프로젝트 키가 결과에 절대 서지 않는다** — 조회는 서버가 세션의 `userId`로 `ProjectMember`를 조인해 좁히고, 클라이언트가 보낸 프로젝트 목록을 믿지 않는다(격리 postgres 통합 테스트).
12. **Changelog**: 앱 버전 릴리스(`parseReleases`가 거른 것)마다 하나 — 버전·날짜·본문 텍스트를 맞추고 본문 일치면 그 줄을 보인다. 고르면 `/changelog#v<x.y.z>`.
13. Docs·Changelog 색인은 **Dialog를 처음 열 때 한 번** 받는다(같은 탭의 이후 열기는 재요청 0). 받는 동안 Projects·Pages 결과는 즉시 서고 Docs·Changelog 자리에 로딩 한 줄이 선다. 릴리스를 못 받았으면(GitHub 장애) Changelog 그룹 대신 안내 한 줄이고 나머지 결과는 그대로다.

경계:

14. 검색어는 URL·서버 로그·분석 이벤트 어디에도 실리지 않는다 — Dialog는 라우트가 아니고(PRODUCT §7.7 "모달도 라우트가 아니다"), 색인 요청은 질의 없는 GET 하나다. Keys 조회는 질의를 Server Action 본문으로 보내고 서버는 그것을 기록하지 않는다(`console.*`에 싣지 않는다).
15. 최근 검색어는 **이 브라우저의 `localStorage`에만** 있다. 저장소가 막힌 브라우저(사생활 모드 등)에서는 최근 검색어가 비고 검색은 그대로 된다 — 오류 문구를 띄우지 않는다.
15a. 최근 검색어는 로그아웃해도 남는다 — 같은 브라우저의 다른 계정이 그 목록을 본다(2026-10-01 사용자 수용).
16. `/privacy`가 "브라우저에 남기는 것"으로 최근 검색어를 공표한다(개정 이력 · 시행일 — `policy-gate.test.tsx`).
16a. **UI는 프리미티브 조립이다** (2026-10-01 사용자) — `components/search/*`에 raw 태그·색 리터럴·치수 임의값이 0이고, 새로 만든 `Kbd`·`Highlight`로 기존 손 사본 둘(스위처 `<kbd>` · `/projects` `<mark>`)이 옮겨져 소스에 손 `<kbd>`·`<mark>`가 `components/ui/` 밖에 0이다(소스 스캔 테스트).
17. `pnpm gate` green(typecheck · test · build · 미러 · 트리거 시 격리 postgres).

성능:

18. Keys 조회는 **왕복 최대 둘**이다 — ① 키 이름·원문 일치(상한 5) ② ①이 5건 미만일 때만 번역값 일치(남은 수만큼). 번역값 순차 스캔이 필요 없는 질의에서 돌지 않는다.
19. 조회가 인덱스 선두 `projectId`로 먼저 좁혀진다(`EXPLAIN`에 멤버십 밖 프로젝트의 행을 훑는 단계가 없다).
20. **실측 기준**: 격리 postgres에 합성 한 프로젝트 **20,000키 × 10로케일(번역 200,000행 — push 행 상한)**을 넣고, 어느 키에도 없는 질의(최악 — ②까지 끝까지 훑는다)로 서버 조회 시간을 잰다. **중앙값 300ms 이하면 인덱스를 넣지 않는다.** 넘으면 `pg_trgm` GIN 인덱스(`StringKey.key`·`sourceText`, `Translation.value`) additive 마이그레이션을 이 기능 안에서 넣고 같은 측정으로 기준 통과를 확인한다. 측정값은 design.md에 남긴다.

## 비목표

- **멤버 · 로그 사건 · 소스 파일 경로 검색** — 프로젝트 데이터 조회가 키 하나를 넘어 늘어난다. 키 검색의 실측이 선 뒤 다시 본다.
- **보관 프로젝트·보관 소스의 키** — 번역 화면이 보관 프로젝트를 열지 않으므로 결과가 갈 곳이 없다.
- **번역 화면 검색의 판정 변경** — 같은 `ILIKE` 규칙을 따를 뿐 그 화면의 조회는 고치지 않는다.
- **서버 측 최근 검색어** — 기기 간 동기화 없음(스키마·개인정보 수집 항목 증가, 2026-10-01 사용자).
- **동작(Action) 실행** — `Sign out` · `Publish` · `Sync` 같은 명령을 결과에 넣지 않는다. 목적지로 가는 것만 한다(명령 팔레트가 아니다).
- **그룹별 "더 보기" · 결과 페이지** — 그룹당 5행을 넘는 결과는 검색어를 좁혀 찾는다.
- **퍼지 매칭 · 오타 교정 · 동의어**(`i18n` → Translations 등) — 부분 일치(공백으로 나눈 낱말 전부)만.
- **`/changelog`·`/docs` 페이지 안의 전용 검색창** — 입구는 헤더 하나다.
- **프로젝트 스위처를 `Command`로 옮기는 것** — 같은 "입력으로 목록 거르기" 형이지만 형이 메뉴이고 사용자가 고른 것이다(2026-09-27). 이 기능 뒤 따로 판정한다.
- **검색 분석(어떤 낱말이 검색됐나)** — 수집하지 않는다.
