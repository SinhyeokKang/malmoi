# global-search — 스펙

## 범위 게이트 (2026-10-01 사용자 확인)

이 기능은 **옛 판정 하나를 뒤집는다** — 사용자가 재확인했다("뒤집고 진행").

1. **DESIGN §6.5 · §9.2 "헤더의 검색·`+`·카운터는 넣지 않는다 — PRODUCT §4.2가 기능 밀도를 막는다"** → 헤더 중앙에 검색 트리거 하나를 넣는다.
   `+`(`New project`)는 2026-09-30에 이미 헤더로 들어왔고, 카운터는 여전히 넣지 않는다.
   **왜 기능 밀도 비범위와 충돌하지 않나**: 새 목적지·새 데이터·새 권한을 만들지 않는다 — 이미 있는 목적지(프로젝트·메뉴·키·가이드)로 가는 **입구 하나**다. 사이드바 항목은 늘지 않는다.
2. **DESIGN §6.5 스위처 행 "새 Popover·combobox 프리미티브 없음 — 사용자"(2026-09-27)** → 이 기능이 `Command*` combobox 프리미티브를 세운다. 스위처는 옮기지 않는다(비목표) — 판정 문장만 "스위처는 `DropdownMenu`를 쓰고, combobox 프리미티브는 검색 Dialog가 소유한다"로 갱신한다.

**PRODUCT §7.7 `/changelog` 비범위("검색·필터·페이지네이션")는 뒤집지 않는다** — 릴리스 노트는 검색 대상이 아니다(2026-10-01 리뷰, 비목표).

PRODUCT §4.2 목록에 직접 걸리는 항목은 없고, 코어 설계 원칙(병합 없음 · export 결정성)과 닿는 곳이 없다 — DB를 **읽기만** 한다(키·번역값 검색).

**키·번역값 검색은 범위 안이다** (2026-10-01 사용자 — 처음엔 "내비게이션만"을 골랐다가 성능 판단을 듣고 넣었다). 조건: 트라이그램 인덱스 없이 시작하고, 실측이 기준을 넘을 때만 additive 마이그레이션으로 인덱스를 넣는다(완료 조건 20).

**component-unify와의 관계**: 착수 순서는 독립이고, 새 프리미티브의 **prop·슬롯 어휘는 component-unify 규약**(`docs/features/component-unify/design.md` 축 표 — 슬롯 `icon`·`description`·`action`, `...rest` 전달)을 따른다.

## 사용자

**셋이다** — 이 도구의 두 사용자에 공개 셸 방문자가 더해진다.

- **번역 편집자(비개발자)**: 가이드에서 "어떻게 하지"를 찾는다(예: Publish · Revert · 초대 수락). 지금은 `/docs`의 문서 내비 28쪽을 눈으로 훑는 길뿐이다. 그리고 동료가 말한 문구("결제 버튼 문구 바꿔 주세요")가 **어느 프로젝트·어느 소스의 어느 키인지**를 찾는다.
- **개발자(OWNER)**: 프로젝트 여럿을 오가며 특정 화면(Settings · Sources · Logs)으로 간다.
- **비로그인 방문자**(공개 셸 — 랜딩 · `/docs` · `/changelog` · `/privacy`): 가이드만 찾는다.

⚠️ **결과 집합은 라우트(어느 셸인가)가 아니라 로그인 세션으로 갈린다** (2026-10-01 사용자) — 로그인 사용자는 `/docs`를 읽다가도 자기 프로젝트·키로 바로 간다. 셸이 정하는 것은 트리거의 자리뿐이다.

**상충**: 없다. 결과 집합이 역할·로그인 여부로 좁혀질 뿐 서로의 동작을 바꾸지 않는다.

## 문제 (관측된 사실)

1. **`/docs`에 검색이 없다.** 원고 28쪽(`guide/SUMMARY.md` 등재 — AUTHORING·SHOOTING·SUMMARY는 서빙 안 됨, `lib/guide/summary.ts`)을 트리 내비와 페이지 목차(H2)로만 찾는다 — 본문에만 있는 낱말(`PUSH_TOKEN`, `base-locale`, `stale-commit`)은 어느 페이지에 있는지 알 수단이 없다.
2. **번역 화면 검색은 한 프로젝트 안이다** — `lib/keys/translation-list.ts`의 `?q=`는 `projectId` 하나로 좁혀 키·원문·번역값을 `ILIKE`로 찾는다. 문구가 어느 프로젝트에 있는지 모르면 프로젝트마다 번역 화면을 열어 같은 낱말을 다시 친다.
3. **검색창이 화면마다 따로다** — `/projects`(이름) · 번역 화면(키) · Logs(사건)의 `SearchInput`, 스위처의 `Find project…`, 온보딩 리포 검색, 네임스페이스 트리 필터는 모두 그 화면 안을 좁히는 도구이고, 화면을 가로지르는 입구는 없다.
4. (부수) **다른 프로젝트의 하위 화면으로 가는 길이 스위처 → Home → 사이드바 항목이다** — 스위처(`components/shell/project-switcher.tsx`)는 Home에 착지한다. 검색도 ⌘K → 타이핑 → Enter 세 동작이라 클릭 수가 줄지는 않는다 — 이 기능의 가치는 1·2이고 이것은 부수 효과다.

## 완료 조건

트리거:

1. **앱 셸 헤더**(`components/shell/header.tsx`)와 **공개 셸 헤더**(`components/public-shell/header.tsx`)의 **가로 중앙**에 캡슐 모양 버튼이 선다 — 검색 글리프 + placeholder 문구 `Search…` + 단축키 칩. 면은 콘텐츠 패널과 같다(`bg-background` · `border-border-subtle` · `shadow-low`), 높이 36 · `rounded-full` · 폭 320(2026-10-01 사용자). 좌·우 묶음의 폭이 달라도 뷰포트 중앙에 있다 — DOM 테스트가 구조(3칸 grid · 가운데 슬롯 `justify-self-center`)로, `/runtime-test`가 computed rect로 확인한다.
2. 버튼을 누르거나 **macOS에서 ⌘K, 그 밖에서 Ctrl+K**를 누르면 검색 Dialog가 열리고 포커스가 입력에 있다. 다른 플랫폼의 조합(macOS Ctrl+K — 텍스트 필드의 줄 끝 지우기)은 가로채지 않는다. 다음 경우 단축키를 읽지 않는다: 한글 조합 중 · 포커스가 텍스트 입력(`input`·`textarea`·`contenteditable`) 안 · 열린 Dialog·메뉴(`[role="dialog"]`·`[role="menu"]`)가 있음(검색 Dialog 자신 포함 — 토글하지 않는다).
3. 버튼은 접근 이름 `Search`(말줄임 없음 — DESIGN §10), `aria-haspopup="dialog"`, 플랫폼별 `aria-keyshortcuts`(`Meta+K` 또는 `Control+K`, 수화 전에는 없음)를 가진다.

Dialog (레이아웃은 GitLab 검색 패널을 따른다 — 2026-10-01 사용자 참고 이미지):

3a. **자리·크기** (2026-10-01 사용자): **폭·높이·면·dim은 대형 모달(`components/ui/modal.tsx` `OnboardingModal`)과 같고, 다른 것은 위치 하나다** — 가로 중앙(트리거와 같은 축), **위 16**(`top-4` — 헤더를 덮는다, 세로 가운데 정렬이 아니다). 폭 `w-[calc(100%-96px)] max-w-[1024px]`, 높이 `min(80svh,800px,calc(100svh-96px))` ~ `min(800px,calc(100svh-96px))`, `rounded-xl` · `shadow-medium` · dim `bg-foreground/32` + `backdrop-blur-[6px]`. 입력 줄이 맨 위이고 그 아래 전폭 구분선, 그 아래 결과 목록이 남은 높이 안에서 스크롤한다. 바닥 줄·닫기 버튼은 없다(Esc·배경 클릭으로 닫는다).
3b. **목록 모양**: 그룹마다 굵은 머리(`Projects` 등)와 그룹 사이 전폭 구분선. 행은 **한 줄** `제목 · 맥락`(맥락은 muted 작은 글자 — 예: 프로젝트 행의 slug, 메뉴 행의 프로젝트 이름)이고, 엔터티 행(Projects)만 앞 글리프(썸네일)를 든다. Keys·Docs 행은 일치한 필드 한 줄을 둘째 줄로 든다. **활성 행**은 면(`bg-accent`) + 포커스 링과 같은 테두리이고 오른쪽 끝에 `Go to` + `Kbd` `↵` 힌트가 선다(활성 행에만).
4. 입력이 비어 있으면 **미리보기**가 선다(2026-10-01 사용자) — 로그인·프로젝트 있음: Projects 앞 3(지금 프로젝트 먼저 → 멤버십 순서) + 끝 행 `View all projects`(→ `/projects`) · Menus 앞 3(지금 프로젝트, 없으면 첫 프로젝트의 메뉴 — `navZones` 순서) · Docs 앞 3(SUMMARY 순서의 페이지 도입부) + 끝 행 `Browse all docs`(→ `/docs`). 로그인·프로젝트 0: Menus(사용자 메뉴·하단) 앞 3 · Docs 앞 3 + `Browse all docs`. 비로그인: Menus(하단) · Docs 앞 3 + `Browse all docs`. Keys는 미리보기에 없다. `View all …` 행은 글리프를 들고 3개 상한에 세지 않으며, 질의가 있으면 서지 않는다.
5. 입력하면 결과가 **그룹**으로 선다 — 순서 `Projects · Menus · Keys · Docs`, 그룹당 최대 5행, 빈 그룹은 그리지 않는다. 결과 0건이고 **대기 중인 조회가 없으면** `EmptyState` `No results for “{q}”`(곡선 따옴표 — DESIGN §6.63, 액션 없음 — 입력이 바로 위다). 대기 중인 조회(Keys·색인)가 있으면 `EmptyState` 대신 상태 줄만 선다.
6. 결과를 고르면(클릭 또는 Enter) 그 목적지로 이동하고 Dialog가 닫힌다. **Enter는 활성 option 안 링크의 `.click()`이다** — 마우스 클릭과 같은 경로라 번역 화면 이탈 가드(`use-leave-guard.ts`)·navigation-dim·`Link`가 한 벌이다. 가드가 이탈 확인을 띄우면 검색 Dialog는 닫혀 있다(두 Dialog가 겹치지 않는다).
7. 키보드: ↑↓로 활성 행이 이동하고(끝에서 반대편으로 순환), Enter가 활성 행을 연다. 포커스는 입력에 남는다(`aria-activedescendant` — 가리키는 id의 요소가 실재한다). **활성 행은 항목 id로 잡는다** — 질의가 바뀌면 첫 행이 활성, 결과만 늘면(늦게 온 Keys·Docs 그룹) 활성 id가 그대로이고, 그 id가 사라지면 첫 행이다. 조합 중 Enter·Esc는 조합 확정·취소이고 이동·닫기가 아니다. Esc는 닫는다. 마우스 hover는 활성 행을 바꾸되 포커스를 입력에서 빼앗지 않는다(스위처와 같은 이유 — 한글 첫 글자 유실).
8. 결과 행의 **일치한 필드**가 `<mark>`로 칠해진다 — 제목뿐 아니라 Keys의 원문·번역값 줄, Docs 본문 스니펫까지(§6.63 "칠한 곳 = 찾은 곳"). `/projects` 검색 강조와 같은 형이다. `İ`처럼 소문자화로 길이가 바뀌는 글자에서 강조가 어긋나지 않는다(POSTMORTEM 2026-09-13 재발 방지 테스트).
8a. 상태 줄(로딩·부분 실패)은 **listbox 밖**(입력 아래)에 `aria-live="polite"`로 선다 — listbox의 자식은 option·group뿐이다. 결과 수는 sr-only 공지 `{n} results`로 디바운스해 알린다.

결과 집합:

9. **Projects** (로그인이면 어느 셸이든): 내 멤버십 전부 — 보관 포함(`Archived` 배지) · 썸네일 · 이름 일치. 고르면 그 프로젝트 Home. 앱 셸은 레이아웃이 이미 받은 멤버십을 쓰고(**새 DB 조회 0**), 공개 셸은 로그인일 때 **탭 수명에 한 번**(첫 열기, 모듈 수준 Promise — 공개 셸은 페이지마다 다시 렌더된다) 멤버십을 받는다(공개 페이지 렌더에 조회를 더하지 않는다).
10. **Menus**: 로그인이면 ① 사용자 메뉴(`navWorkItems()` — `Projects` · `MCP connector` · `Account` — 와 헤더 버튼의 `New project`) ② 멤버십마다 프로젝트 메뉴(`navZones`의 프로젝트 구역 — `Settings`는 `project:settings` 역할만) ③ 하단 전역(`navFooterItems()` — `Changelog` · `Docs`). 프로젝트 메뉴 행은 "메뉴 이름 · 프로젝트 이름"이고 두 필드를 가로질러 맞춘다(`settings demo` → demo의 Settings). **지금 보고 있는 프로젝트의 메뉴가 먼저**다(공개 셸에는 '지금 프로젝트'가 없다). 비로그인이면 ③만이다.
11. **Docs**: 서빙되는 가이드 페이지(SUMMARY 등재)의 **절 단위** 항목 — 페이지 첫 절(제목 아래 도입부)과 표식 있는 H2 절마다 하나. 제목·절 제목·본문 텍스트를 맞추고, 본문 일치면 일치 주변 한 줄을 보인다. 고르면 `routes.docs(page, anchor)`.
11a. **Keys** (로그인이면 어느 셸이든): 내가 멤버인 **보관 안 된** 프로젝트의 **보관 안 되고 첫 적재가 끝난**(`lastCommitSha` 있음 — 번역 화면이 `ProjectNotReady`를 그리지 않는) 소스에서 orphaned 아닌 키 중, 키 이름 · 원문(`sourceText`) · **orphaned 아닌 로케일의** 번역값 어느 하나가 **질의 전체를 부분 문자열로** 품는 것(대소문자 무시 — 번역 화면 `?q=`와 같은 규칙이라 클릭해 간 화면과 판정이 같다). ⚠️ Projects·Menus·Docs의 토큰 AND 판정과 **다르다**(`settings demo`는 Keys에선 그 문자열 전체). 행은 키 이름 · `프로젝트 · 소스 slug` · 일치한 필드 한 줄(원문이면 원문, 번역값이면 로케일 코드와 값 — 따로 렌더). 순위는 키 이름 일치 > 원문 일치 > 번역값 일치, 같은 급이면 지금 프로젝트 먼저 → 키 이름 오름차순(`COLLATE "C"`). 같은 이름의 키가 다른 소스·프로젝트에 있으면 각각 선다(중복 제거는 키 id). 고르면 그 키가 선택된 번역 화면(`?ns=` · `?key=` · `?keySurface=` — Logs의 `Open this translation`과 같은 착지, 필터는 켜지 않는다).
11b. Keys 조회는 **trim 뒤 2자 이상**(`String.length`)에서만, 마지막 입력 뒤 250ms에 한 번 나간다. 200자(`Q_MAX_LENGTH`)를 넘으면 번역 화면처럼 앞 200자로 자른다. 1자에는 안내를 띄우지 않는다(2026-10-01 사용자). 늦게 돌아온 응답이 새 질의의 결과를 덮지 않는다(A→B→A 순서 포함). 조회 중에는 상태 줄에 로딩 한 줄, 실패(세션 만료 포함)하면 `Keys can't be searched right now.` 한 줄이고 다른 그룹은 그대로다.
11c. **다른 사용자의 프로젝트 키가 결과에 절대 서지 않는다** — 조회는 서버가 세션의 `userId`로 `ProjectMember`를 조인해 좁히고, 클라이언트가 보낸 프로젝트 목록을 받지 않는다(격리 postgres 통합 테스트).
12. Docs 색인은 **탭 수명에 한 번**(첫 열기) 받는다(같은 탭의 이후 열기는 재요청 0). 받는 동안 Projects·Menus 결과는 즉시 서고 상태 줄에 로딩 한 줄이 선다. 못 받았으면 상태 줄에 안내 한 줄이고 나머지 결과는 그대로다(다음 열기에 다시 받는다).

착지:

13. **같은 가이드 페이지 안 해시 이동**(`/docs/x` → `/docs/x#y`)은 목차 클릭과 같은 형이다 — 대상 제목으로 스크롤(48 오프셋)하고 그 제목에 포커스한다(`public-doc-toc.tsx`와 같은 규칙).
13a. **지금 보고 있는 번역 화면(같은 소스)에서 Keys 결과를 고르면** 목록이 선택된 키의 행으로 스크롤한다 — 다른 화면에서 착지했을 때와 결과가 같다.

경계:

14. 검색어는 URL·서버 로그·분석 이벤트·브라우저 저장소 어디에도 실리지 않는다 — Dialog는 라우트가 아니고(PRODUCT §7.7 "모달도 라우트가 아니다"), 색인 요청은 질의 없는 GET 하나다. Keys 조회는 질의를 Server Action 본문으로 보내고 서버는 그것을 기록하지 않는다(`console.*`에 싣지 않는다).
15. `/privacy`는 **고치지 않는다** — 새 수집·새 브라우저 저장·새 전송처가 없다. 그것이 여전히 참인지 `/push` 4단계가 대조한다.
16. **UI는 프리미티브 조립이다** (2026-10-01 사용자) — `components/search/*`에 raw 상호작용·표식 태그(`button`·`input`·`a`·`kbd`·`mark`)·hex 색·`[Npx]` 임의값이 0이고, 새로 만든 `Kbd`·`Highlight`로 기존 손 사본 둘(스위처 `<kbd>` · `/projects` `<mark>`)이 옮겨져 소스에 손 `<kbd>`·`<mark>`가 `components/ui/` 밖에 0이다(소스 스캔 테스트 — 주석 제거 · 대상 파일 수 > 0 · 심은 위반 탐지).
17. **정본 문서가 판정을 따라간다** — PRODUCT §4.1(글로벌 검색) · IA("검색은 라우트가 아니다"), DESIGN §6.5 헤더 행·스위처 행 · §6.8 헤더 행 · §9.2 · §6.4 프리미티브 행 · §6.2 강조 색 위치 · `EmptyState` 액션 없음 예외 · 아이콘 표, ARCHITECTURE §6 인증 경계 표(`/api/search-index` · Keys 조회의 멤버십 조인)와 §1.96(pg_trgm 판정과의 관계), CLAUDE.md 데이터 경로 표, DIRECTORY, README.
17a. `pnpm gate` green(typecheck · test · build · 미러 · 트리거 시 격리 postgres).

성능:

18. Keys 조회는 **왕복 최대 둘**이다 — ① 키 이름·원문 일치(상한 5) ② ①이 5건 미만일 때만 번역값 일치(남은 수만큼). 번역값 순차 스캔이 필요 없는 질의에서 돌지 않는다.
19. 조회가 **멤버 프로젝트 id를 먼저 확정한 뒤** 인덱스 선두 `projectId`로 좁혀진다 — 멤버가 아닌 대형 테넌트가 있는 DB에서 `EXPLAIN ANALYZE`의 `Translation` 방문 행이 그 테넌트의 행을 포함하지 않는다(통계 없음·`ANALYZE` 뒤 둘 다).
20. **실측 기준**: 커밋된 격리 postgres 성능 테스트(`lib/keys/__tests__/search-performance.integration.ts` — `translation-list-performance.integration.ts`의 형)에서 멤버 프로젝트 둘(하나는 **20,000키 × 10로케일 = 번역 200,000행** — push 행 상한) + 비멤버 대형 테넌트 하나를 넣고, 통계 없음·`ANALYZE` 뒤 각각 네 질의(어느 키에도 없음 — ②까지 끝까지 훑는 최악 · 키 이름 일치 · 번역값만 일치 · 흔한 단어)를 잰다. 기준은 로컬 PG의 `EXPLAIN ANALYZE` Execution Time(**`hnd1`↔도쿄 왕복 제외**)이고, **최악 질의 중앙값 300ms 이하면 인덱스를 넣지 않는다.** 넘으면 `pg_trgm` GIN 인덱스(`StringKey.key`·`sourceText`, `Translation.value`) additive 마이그레이션을 이 기능 안에서 넣고 같은 테스트로 기준 통과를 확인한다. 측정값은 design.md에 남긴다.

## 비목표

- **최근 검색어** — 검색어가 곧 번역 문자열이라 ARCHITECTURE "번역 문자열은 URL·`localStorage`·로그에 싣지 않는다 · 사용자별이다"(§ draft 복구 절)와 충돌한다(2026-10-01 리뷰, 사용자 제외). 서버 측 저장도 하지 않는다.
- **릴리스 노트(Changelog) 검색** — 앱 릴리스 11판이라 `/changelog` 안 ⌘F로 충분하다. PRODUCT §7.7 비범위를 그대로 둔다(2026-10-01 리뷰, 사용자 제외). `Changelog` **페이지로 가는 메뉴 행**은 Menus에 있다.
- **멤버 · 로그 사건 · 소스 파일 경로 검색** — 프로젝트 데이터 조회가 키 하나를 넘어 늘어난다. 키 검색의 실측이 선 뒤 다시 본다.
- **보관 프로젝트·보관 소스·첫 적재 전 소스의 키** — 번역 화면이 그 자리를 열지 않으므로 결과가 갈 곳이 없다.
- **번역 화면 검색의 판정 변경** — 같은 `ILIKE` 규칙을 따를 뿐 그 화면의 조회는 고치지 않는다.
- **Keys 1자 조회·1자 안내** — 2자 하한을 그대로 두고 안내도 띄우지 않는다(2026-10-01 사용자).
- **동작(Action) 실행** — `Sign out` · `Publish` · `Sync` 같은 명령을 결과에 넣지 않는다. 목적지로 가는 것만 한다(명령 팔레트가 아니다).
- **그룹별 "더 보기" · 결과 페이지** — 그룹당 5행을 넘는 결과는 검색어를 좁혀 찾는다.
- **퍼지 매칭 · 오타 교정 · 동의어**(`i18n` → Translations 등) — 부분 일치(공백으로 나눈 낱말 전부)만.
- **`/changelog`·`/docs` 페이지 안의 전용 검색창** — 입구는 헤더 하나다.
- **프로젝트 스위처를 `Command`로 옮기는 것** — 같은 "입력으로 목록 거르기" 형이지만 형이 메뉴이고 사용자가 고른 것이다(2026-09-27). 이 기능 뒤 따로 판정한다.
- **검색 분석(어떤 낱말이 검색됐나)** — 수집하지 않는다.
