## detect 확장 — 층위가 둘이다 (2026-09-02 확정)

오탐에는 두 클래스가 있고, 측정하려면 둘 다 후보로 나와야 한다:

| 클래스 | 전례 | 측정 위치 |
|---|---|---|
| **어댑터 내** — 같은 어댑터의 후보 중 순위가 틀림 | bugshot-web `public/search/{locale}.json` | `Adapter.detectCandidates` (프로덕션, 병존 추가) |
| **어댑터 간** — 딴 어댑터의 후보가 정답을 가림 | bugshot-2 `_locales` 4키 vs `ts-dict` 903키 (MVP §5.1) | **실험 쪽 순수 함수 `mergeCandidates`** (`lib/survey/`) |

- **프로덕션 변경은 어댑터 메서드까지다**: `detectCandidates(paths, probe): DetectedFormat[]`(순위순, 빈 배열 = 못 찾음)를 병존 추가하고, 기존 `detect`는 내부에서 `[0]`을 쓴다. `detectFormat`·`detectFormatWith`(첫 매치 승)는 그대로다.
- **어댑터 간 병합은 프로덕션에 넣지 않는다.** 지금 소비자가 이 실험뿐이라, 병합·글로벌 순위(`ADAPTERS` 순서 → 어댑터 내 순위)는 `lib/survey/`의 순수 함수가 담당한다. 이 순위 규칙에서 **병합 목록의 `[0]` = 현재 `detectFormat` 결과**가 구조적으로 보장된다 — 현 `detectFormat`이 정확히 "ADAPTERS 순서의 첫 매치"이기 때문이다. 온보딩 UI 같은 프로덕션 소비자가 생기면 그때 `lib/adapters/`로 승격한다.

## 순수 함수로 분리 가능한 부분 (= `/tdd` 대상, 전부 `lib/survey/`)

| 함수 | 입력 → 출력 | 왜 순수여야 하나 |
|---|---|---|
| `detectCandidates(paths, probe)` | 경로 목록 → `DetectedFormat[]` (순위순) | 기존 `detect`의 확장. 이미 순수다 (`lib/adapters/` — 유일한 프로덕션 변경) |
| `mergeCandidates(perAdapter)` | 어댑터별 후보 목록 → 글로벌 순위 목록 | 어댑터 간 오탐 측정의 근거. `[0]` = 현 `detectFormat` 결과 불변식을 테스트로 박는다 |
| `selectSurveyFiles(paths)` | 리포 전체 경로 목록 → 물리화할 파일 경로 목록 | **껍데기에 스밀 뻔한 로직이다** — 후보 카탈로그 파일 + 설정 파일(`i18next-parser.config.*` 등)만 읽고, `.git`·바이너리·대용량은 여기서 걸러진다. 리포 전체 내용을 메모리에 올리지 않는 이유가 이 함수다 |
| `roundtripDiffRatio(original, written)` | 두 문자열 → 변경 줄 비율 | **첫 pull PR diff 크기의 대리 지표.** 원본 vs **1차 write** 기준. 실제 git diff를 부르지 않고 줄 단위로 센다 |
| `surveyOne(input)` | `{repo, paths, files, verdict?}` → `RepoSurvey` | 리포 하나의 판정 전체. **파일 내용을 인자로 받으므로 네트워크·디스크가 없다** — 픽스처로 완전히 테스트된다 |
| `summarize(surveys, verdicts)` | `RepoSurvey[]` + 정답 경로 목록 → 지표 4개 + 마크다운 표 | 표 생성이 로직이라 테스트 대상이다. **verdicts를 입력으로 받는다** — 오탐률은 정답 경로와 후보 목록의 대조로 계산되고, 판정이 코드 밖 파일에 있어 재실행이 판정을 파괴하지 않는다 |

I/O 껍데기는 `scripts/adapter-survey.ts` 하나다: clone → 파일 트리 나열 → `selectSurveyFiles`가 고른 파일만 읽기 → 순수 함수 호출 → 출력. 껍데기에 남는 결정도 명시해둔다 — **경로는 git 트리와 같은 리포 상대 POSIX 형식으로 정규화**하고(어댑터 `detect`가 그 형식을 전제한다), ts-dict `probe`는 디렉터리당 최대 4파일 ts-morph 파싱이라 대형 리포에서 디렉터리 수에 비례하는 비용이 든다(이것도 측정에 남긴다 — 리포당 소요 시간).

**여기가 비면 설계를 다시 본다** — 이 실험은 "돌려보고 눈으로 본다"로 흐르기 쉽고, 그러면 재현이 안 되고 숫자가 남지 않는다.

## 불변식 영향

**측정만 하는 동안은 없다. 다만 결과가 두 불변식을 흔들 수 있다** — 흔드는 것까지가 이 실험의 목적이고, 실제 개정은 다음 기능이다.

### MVP §4.1 "키 정렬" — 흔들릴 가능성이 가장 높은 지점

재생성 writer는 `usableEntries`(`lib/adapters/shared.ts`)에서 **항상 키를 재정렬한다.** 원본이 정렬돼 있지 않으면 **첫 pull PR이 로케일 파일 전체 diff로 나온다.** skillflo 1446키 파일이 통째로 재정렬된 PR은 리뷰어가 머지하지 않는다.

MVP §4.1과 ARCHITECTURE §1.2는 JSON 재정렬을 인지하고 "첫 pull에서 한 번 정규화, 이후 안정"으로 **수용**했다 — 논점은 "다루지 않았다"가 아니라 **그 수용이 skillflo 1446키 규모, 그리고 남의 리포에서 성립하느냐**다 (2026-09-02 표현 정정). `ts-dict`에 수술적 치환을 도입한 이유(빈 줄 120개·주석 23개 파괴)와 같은 문제가 JSON에서도 규모에 따라 발생한다.

해결이 가능하다는 점까지만 적어둔다: **원본을 입력에 포함시키면 "원본 키 순서 보존"과 결정성이 양립한다** (같은 `DB 상태 + 원본` → 같은 바이트). `ts-dict`가 이미 그 구조이고 계약에 자리도 있다(`DetectedFormat.currentFiles`). 원본에서 가져오는 것은 **구조(순서)뿐이고 값은 전부 DB다** — 병합 없음 원칙 안이다. 대가는 pull이 blob SHA만이 아니라 내용을 받는 것인데, MVP §3.3의 1층(DB 측 스킵)이 "편집 없는 날엔 GitHub을 한 번도 안 부른다"를 보장하므로 추가 비용이 편집 있는 날로 한정된다. *주의: 보존 모드라도 DB에만 있는 신규 키의 삽입 위치는 diff를 만든다 — 지표 ④를 읽을 때 전제할 것 (이 실험의 왕복은 read→write라 신규 키가 없어 측정엔 안 걸린다).*

**이 실험은 지표 ④로 그 개정이 필요한지만 판정한다.**

### ARCHITECTURE §1.1 결정성 3규칙 — 계약 테스트의 공백

`adapters.test.ts`의 "writer 결정성" describe 블록(라인 번호는 썩으므로 이름으로 참조)이 `chromeLocales`·`jsonCatalog`를 **손으로 열거한다** — it 9개 중 6개는 jsonCatalog 단독이다. 즉 **4번째 어댑터를 추가하면 결정성 규칙을 하나도 안 지켜도 CI가 green이다.**

이 실험이 새 어댑터를 만들지는 않지만, 결과가 "포맷 N개를 지원해야 한다"로 나오면 그 직후에 어댑터가 여럿 붙는다. **`ADAPTERS`를 순회하는 구조로 바꾸는 것을 태스크에 넣는다** — 단 규칙은 전 어댑터 공통이 아니다. **적용 매트릭스가 layout으로 갈린다** (2026-09-02 정정 — "공통 규칙 전부 적용"이라 쓰면 ARCHITECTURE §1.4와 모순: ts-dict는 orphaned를 파일에 남기고 빈 값 필터는 호출부 책임이다):

| 규칙 | 재생성 (`per-locale`) | 수술적 치환 (`multi-locale`) |
|---|---|---|
| 정렬·2칸·끝 개행 1개 | 검사 | 비적용 (원본 보존이 요지) |
| orphaned | 출력에서 제외 | **원본 값이 남는다** — 공통 단언은 "orphaned의 **DB 값**이 출력에 나타나지 않는다"까지 |
| 빈 값 | 어댑터가 제외 | **호출부 계약** — 여기서 검사하지 않는다 (§1.4) |
| 입력 순서 무관 (결정성) | 검사 | 검사 |

### 2026-08-31 — `process.exit()`이 파이프 stdout을 잘라먹었다

**이 하네스가 정확히 그 형태다**: 리포 50개의 결과를 `--json`으로 파이프에 흘린다. skillflo 하나(8676행)가 73KB에서 잘렸으니 50개 리포는 확실히 넘는다.

- **규칙**: `process.exit()`을 쓰지 않는다. `process.exitCode`만 세우고 자연 종료를 기다린다.
- **그리고 그 `exit`이 제어 흐름을 겸하는지 본다** — 그때 바꾸면서 조기 종료가 사라져 JSON 문서가 둘 나왔다. `--json` 분기는 early return으로 명시한다.
- **검증에 파이프를 포함하되, 출력이 파이프 버퍼(64KB)를 넘는 조건에서 한다.** POSTMORTEM 원문이 "bugshot-2(작은 출력)에서는 재현되지 않았다"고 적었다 — 리포 3개 스모크의 통과는 아무것도 증명하지 않을 수 있으므로, 태스크 7 전체 실행(50개+)에서 `--json | jq . > /dev/null`을 반복한다.

## 예상되는 함정 (측정 항목에 넣는다)

- **로케일 코드를 정규화하지 않는다.** `zh_CN.json` vs `zh-CN.json` vs `zh-Hans.json`. 지금 `pathTemplate` 치환이 파일명 원본을 쓰므로 **우연히 맞다** — 어디선가 정규화하는 순간 write가 경로를 못 만든다. **"파일명 그대로가 로케일 코드의 진실"을 `lib/adapters/types.ts` 계약 주석에 박는다** (이 실험의 부수 산출물 — spec §프로덕션 변경 ②).
- **`flatten` 키 충돌.** 원본에 `"a.b": "x"`와 `"a": {"b": "x"}`가 함께 있으면 하나가 조용히 사라진다. `lib/adapters/json-catalog.ts`의 `flatten`이 중복 검사를 하지 않는다 (부수 관측: write 쪽 `setDeep`도 문자열 자리를 빈 객체로 조용히 교체한다). **지표 ③의 유형으로 센다** — 실제 빈도를 모르는 채로 고치지 않는다.
- **`ts-dict`의 파싱 실패는 `ReadResult.errors`로 오지 않는다.** `read`·`write` 모두 `createSourceFile`을 try 없이 불러 throw가 그대로 전파된다. 지표 ③에 "파싱 실패"를 세려면 **`surveyOne`이 어댑터 호출을 감싸서 유형화**해야 한다 — 계약 공백을 실험 쪽에서 흡수한다. 부수 관측: `ts-dict.write`가 내부 `errors` 배열을 만들고 버린다(반환 안 함) — 이 실험이 고치지는 않지만 왕복 측정 중 마주칠 수 있다.
- **`ts-dict`의 무증상 skip → orphaned 오인.** spec.md에 적은 경로다. spread·shorthand·computed는 **에러 없이** 건너뛰므로 지표 ③의 에러 건수로는 안 잡힌다 — **"읽힌 키 수 vs 파일의 문자열 리터럴 수"가 유일한 그물이고**, 무증상 skip 건수를 별도 유형으로 센다 (spec 완료 조건 ③). 이 숫자가 자동 탐지에서 `ts-dict`를 뺄지의 근거다.
- **`nested: boolean`이 좁다.** 실제로 필요한 건 구분자다 — i18next는 키 구분자 `.`에 namespace 구분자 `:`를 쓴다. 이 실험은 **구분자가 `.` 아닌 리포가 몇 개인지만 센다.** 계약을 넓히는 것(`tree: {style, separator}`)은 결과를 보고 판정한다.
- **리포 선정 편향.** i18n 라이브러리 스타터만 모으면 실제 프로덕션 리포의 지저분함을 놓친다 — 그게 바로 자기 리포 4개로 판단한 것과 같은 실수의 반복이다. **스타 수 구간을 3개로 나눠 뽑고, 스타터·템플릿 리포를 절반 이하로 제한한다.**
- **설정 파일이 추론보다 정확하다.** `i18next-parser.config.*`·`lingui.config.*`·`crowdin.yml`·`.i18nrc`·next-intl 설정. **이 실험에서는 구현하지 않고, 몇 개 리포가 그런 파일을 갖고 있는지만 센다** — 있으면 다음 기능의 우선순위가 확정된다.

## 이 실험이 답하지 않는 것

`detect`·`read`가 다 통과해도 남는 질문 둘이 있고, 둘 다 6·7단계 왕복 검증에서 관측된다:

- 첫 pull PR을 개발자가 실제로 머지하는가 (지표 ④가 대리 지표일 뿐이다)
- 번역자가 `refs` permalink를 클릭하는가

그리고 판정 ③이 "제외"로 나올 때의 온보딩 변화(`--adapter ts-dict` 명시가 공식 경로가 되는 것 — spec §사용자)는 이 실험이 아니라 다음 기능이 다룬다.
