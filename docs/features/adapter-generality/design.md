## 영향 받는 흐름

**없다.** push·편집 UI·pull 어디에도 붙지 않는다. 읽기 전용이고, 산출물은 스크립트 하나(`scripts/adapter-survey.ts`)와 문서(`docs/ADAPTER-COVERAGE.md`)다.

## 순수 함수로 분리 가능한 부분 (= `/tdd` 대상)

| 함수 | 입력 → 출력 | 왜 순수여야 하나 |
|---|---|---|
| `detectCandidates(paths, probe)` | 경로 목록 → `DetectedFormat[]` (순위순) | 기존 `detect`의 확장. 이미 순수다 |
| `roundtripDiffRatio(original, written)` | 두 문자열 → 변경 줄 비율 | **첫 pull PR diff 크기의 대리 지표.** 실제 git diff를 부르지 않고 줄 단위로 센다 |
| `surveyOne(input)` | `{repo, paths, files}` → `RepoSurvey` | 리포 하나의 판정 전체. **파일 내용을 인자로 받으므로 네트워크·디스크가 없다** — 픽스처로 완전히 테스트된다 |
| `summarize(surveys)` | `RepoSurvey[]` → 지표 4개 + 마크다운 표 | 표 생성이 로직이라 테스트 대상이다 |

I/O 껍데기는 둘뿐이다: 리포를 받아 파일 트리를 만드는 것, 결과를 stdout·파일로 내는 것.

**여기가 비면 설계를 다시 본다** — 이 실험은 "돌려보고 눈으로 본다"로 흐르기 쉽고, 그러면 재현이 안 되고 숫자가 남지 않는다.

## 불변식 영향

**측정만 하는 동안은 없다. 다만 결과가 두 불변식을 흔들 수 있다** — 흔드는 것까지가 이 실험의 목적이고, 실제 개정은 다음 기능이다.

### MVP §4.1 "키 정렬" — 흔들릴 가능성이 가장 높은 지점

재생성 writer는 `usableEntries`(`lib/adapters/shared.ts`)에서 **항상 키를 재정렬한다.** 원본이 정렬돼 있지 않으면 **첫 pull PR이 로케일 파일 전체 diff로 나온다.** skillflo 1446키 파일이 통째로 재정렬된 PR은 리뷰어가 머지하지 않는다.

이건 `ts-dict`에 수술적 치환을 도입한 이유(빈 줄 120개·주석 23개 파괴)와 **같은 문제인데, MVP §4.1은 이 위험을 TS 전용으로 다루고 있다.** JSON에서도 발생한다.

해결이 가능하다는 점까지만 적어둔다: **원본을 입력에 포함시키면 "원본 키 순서 보존"과 결정성이 양립한다** (같은 `DB 상태 + 원본` → 같은 바이트). `ts-dict`가 이미 그 구조이고 계약에 자리도 있다(`DetectedFormat.currentFiles`). 대가는 pull이 blob SHA만이 아니라 내용을 받는 것인데, MVP §3.3의 1층(DB 측 스킵)이 "편집 없는 날엔 GitHub을 한 번도 안 부른다"를 보장하므로 추가 비용이 편집 있는 날로 한정된다.

**이 실험은 지표 ④로 그 개정이 필요한지만 판정한다.**

### ARCHITECTURE §1.1 결정성 3규칙 — 계약 테스트의 공백

`lib/adapters/__tests__/adapters.test.ts:296`의 "writer 결정성" 블록이 `chromeLocales`·`jsonCatalog`를 **손으로 열거한다.** 즉 **4번째 어댑터를 추가하면 결정성 규칙을 하나도 안 지켜도 CI가 green이다.**

이 실험이 새 어댑터를 만들지는 않지만, 결과가 "포맷 N개를 지원해야 한다"로 나오면 그 직후에 어댑터가 여럿 붙는다. **`ADAPTERS`를 순회하는 `describe.each`로 바꾸는 것을 태스크에 넣는다** — 어댑터 추가 비용을 상수로 고정하는 장치이고, 지금 하면 5줄이다.

## `docs/POSTMORTEM.md`에서 소환한 함정

### 2026-08-31 — `process.exit()`이 파이프 stdout을 잘라먹었다

**이 하네스가 정확히 그 형태다**: 리포 30~50개의 결과를 `--json`으로 파이프에 흘린다. skillflo 하나(8676행)가 73KB에서 잘렸으니 30개 리포는 확실히 넘는다.

- **규칙**: `process.exit()`을 쓰지 않는다. `process.exitCode`만 세우고 자연 종료를 기다린다.
- **그리고 그 `exit`이 제어 흐름을 겸하는지 본다** — 그때 바꾸면서 조기 종료가 사라져 JSON 문서가 둘 나왔다. `--json` 분기는 early return으로 명시한다.
- **검증에 파이프를 포함한다.** TTY로는 재현되지 않는다: `pnpm adapter-survey ... --json | jq . > /dev/null`이 통과해야 한다.

### 2026-08-31 — 외부 계약 페이로드를 리터럴로 조립해 필수 필드가 늘어도 컴파일러가 침묵했다

이 하네스의 결과 객체(`RepoSurvey`)를 리터럴로 조립하면 지표를 하나 추가할 때 `summarize`가 조용히 `undefined`를 센다. **생산자에 타입을 명시한다** (`const survey: RepoSurvey = { ... }`).

### 2026-08-31 — 작은 픽스처가 원리적으로 못 잡는 결함 계열

이 실험의 존재 이유 자체다. spec.md 문제 절에 인용했다.

## 예상되는 함정 (측정 항목에 넣는다)

- **로케일 코드를 정규화하지 않는다.** `zh_CN.json` vs `zh-CN.json` vs `zh-Hans.json`. 지금 `pathTemplate` 치환이 파일명 원본을 쓰므로 **우연히 맞다** — 어디선가 정규화하는 순간 write가 경로를 못 만든다. **"파일명 그대로가 로케일 코드의 진실"을 `lib/adapters/types.ts` 계약 주석에 박는다** (이 실험의 부수 산출물).
- **`flatten` 키 충돌.** 원본에 `"a.b": "x"`와 `"a": {"b": "x"}`가 함께 있으면 하나가 조용히 사라진다. `lib/adapters/json-catalog.ts`의 `flatten`이 중복 검사를 하지 않는다. **지표 ③의 유형으로 센다** — 실제 빈도를 모르는 채로 고치지 않는다.
- **`nested: boolean`이 좁다.** 실제로 필요한 건 구분자다 — i18next는 키 구분자 `.`에 namespace 구분자 `:`를 쓴다. 이 실험은 **구분자가 `.` 아닌 리포가 몇 개인지만 센다.** 계약을 넓히는 것(`tree: {style, separator}`)은 결과를 보고 판정한다.
- **`ts-dict`의 부분 읽기 → orphaned 오인.** spec.md에 적은 경로다. **코드 파일 어댑터가 잡힌 리포에서 "읽힌 키 수 vs 파일의 문자열 리터럴 수"를 따로 센다** — 이 숫자가 자동 탐지에서 `ts-dict`를 뺄지의 유일한 근거다.
- **리포 선정 편향.** i18n 라이브러리 스타터만 모으면 실제 프로덕션 리포의 지저분함을 놓친다 — 그게 바로 자기 리포 4개로 판단한 것과 같은 실수의 반복이다. **스타 수 구간을 3개로 나눠 뽑고, 스타터·템플릿 리포를 절반 이하로 제한한다.**
- **설정 파일이 추론보다 정확하다.** `i18next-parser.config.*`·`lingui.config.*`·`crowdin.yml`·`.i18nrc`·next-intl 설정. **이 실험에서는 구현하지 않고, 몇 개 리포가 그런 파일을 갖고 있는지만 센다** — 있으면 다음 기능의 우선순위가 확정된다.

## 이 실험이 답하지 않는 것

`detect`·`read`가 다 통과해도 남는 질문 둘이 있고, 둘 다 6·7단계 왕복 검증에서 관측된다:

- 첫 pull PR을 개발자가 실제로 머지하는가 (지표 ④가 대리 지표일 뿐이다)
- 번역자가 `refs` permalink를 클릭하는가
