상태: 구현 전 설계. 2026-10-07 정적 코드 대조·4인 검수 반영 완료, 2026-10-10 대표 프레임 수령·판정 반영([브리프](design-brief.md#시안-수령-판정-2026-10-10)), 브라우저 실측·구현·배포 미실행.
관련 문서: [기술 설계](design.md) · [태스크](tasks.md) · [시각 브리프](design-brief.md) · [앱 설계](../responsive-app/spec.md).

## 사용자와 문제

개발자는 작은 창에서 제품·가이드·로그인을 확인하고, 번역 편집자는 초대 링크·로그인·OAuth 동의를 좁은 화면에서도 완료해야 한다. 같은 역할·상태의 기능은 폭 때문에 없어지지 않는다.

문제의 근거는 **2026-10-07 사용자 결정**이다(원문: "할거면 풀스펙. 모든 기능을 지원하는 게 맞는 것 같아. 괜히 분기 만들지 말고, UI로 전부 해결"). 소스에서 확인한 현재 제약은 공개/Auth 셸의 `min-w-shell-min`(`--spacing-shell-min` 1280), Docs 내비264·TOC200, Auth 폼320·OAuth480, Inbox360, 대형 모달 총 거터96이다. 랜딩은 1440×900 캔버스와 한 줄 캡션을 가정한다. **P0 실측(2026-10-10, 로컬 dev · 375×812 · 터치 에뮬레이션 · 라이트 · en)**: 측정한 모든 화면(`/`·`/docs`·`/docs/self-hosting`·`/changelog`·`/privacy`·`/signin`·로그인 `/docs`)이 루트 `scrollWidth` 1280 / `clientWidth` 375다 — 1280 하한 때문에 데스크톱 폭으로 배치된다. 헤더의 검색 [480,800]·GitHub·Get started, 로그인 시 Inbox [1192,1224]·계정 [1236,1268]이 화면 밖이다. 검색 다이얼로그 [128,1152]·Inbox 메뉴 [832,1192]·사용자 메뉴 [996,1236]는 열려도 행·닫기가 전부 375 밖이다. `/signin`은 폼 열이 [8,636]이라 provider 버튼 오른쪽이 잘리고 장식 판과 푸터 스위처가 밖이다. 헤더 겹침은 0(재배치 없이 밀려날 뿐). `/invite/<token>`·`/oauth/authorize`는 유효 토큰이 없어 미측정이다.

## 범위 게이트와 확정 사항

PRODUCT §4.2·§4.3에 반응형 웹은 비범위가 아니다. ARCHITECTURE §0의 병합 없음·단일 판정·인가 불변식은 보존한다.

**이 기능은 기존 사용자 판정 두 건을 뒤집는다**(2026-10-07 사용자, 위 원문):
- `docs/PRODUCT.md:824` — "폭은 셸의 1280이고 폰에서는 가로 스크롤을 수용했다 · 사용자 판정"
- `docs/DESIGN.md:340` §5 — "최소 대응 너비는 1280px다 … 모바일 분기를 만들지 않는다"(2026-09-10 사용자)

갱신은 P6의 독립 정본 태스크가 든다. 공개 단계는 앱 단계와 **프로덕션에 함께** 나가므로(아래 출시 절) 정본은 공개/앱 과도기 문장을 쓰지 않고 최종 상태 하나로 갱신한다.

브리프에 기록된 사용자 확정 D4~D6을 유지한다: 최소375px, 공개 단계는 기존 5씬 축소+줄바꿈 캡션, 좁은 로그인은 장식 숨김·폼 우선, 가이드 이미지는 en 데스크톱 공유. 앱 완성 후 목업 내부 반응형은 responsive-app A2e 소유다.

## 범위와 완료 조건

모든 ID의 판정 기준은 아래 **측정 판정**과 "해당 상태의 마지막 동작 도달"이다. "도달·조작"은 그 두 판정을 통과했다는 뜻이다.

| ID | 범위 / 완료 판정 | 대표 프레임 |
|---|---|---|
| P-01 | 공개 헤더·푸터의 비로그인/로그인 상태 모두 검색·Docs·Changelog·GitHub·계정(사용자 메뉴의 프로젝트 그룹 ≤5 포함 — user-menu-projects, 2026-10-09)·언어·테마·로그인 시 Inbox에 도달한다. 좁은 내비는 서랍, 데스크톱 내비는 기존 자리다. | PT1 |
| P-02 | 랜딩 히어로·CTA·5씬·마지막 CTA가 모두 보인다. 캡션은 축소하지 않고 줄바꿈하며 목업·진행 표시와 겹치지 않는다. reduced-motion·역방향 스크럽을 유지한다. | PT6 |

| P-06 | **검색·Inbox 컴포넌트 자체**의 빈/로딩/결과/실패와 로그인별 검색 범위를 유지한다. 메뉴 이동·폭 변경으로 중복 조회나 읽음 기록이 생기지 않는다 — **사용자 메뉴 프로젝트 그룹의 열기 직전 조회도 대상이다**(user-menu-projects, 2026-10-09: 트리거 hover·focus·열기 중 첫 신호에 한 번, 닫히면 버린다. 서랍으로 옮겨 다시 마운트되면 회차가 새로 선다 — 열지 않은 재마운트가 조회를 시작하지 않는지 본다). 앱 헤더 안의 배치는 A-01이 갖는다. | PT4·PT5 |

지원 검증 뷰포트: 375×812·768×1024·1024×768·1280×800.

**샘플링 규칙**(2026-10-07 검수 합의): 4폭 × 라이트 × en은 모든 페이지 유형의 기본 상태. 다크·ko·es는 375·1280 양끝만. 24조합 전수는 P-01 헤더·서랍과 P-05 초대 수락만. 오류/빈/진행 상태는 375·1280. System은 OS light/dark를 각각 따라가는지 한 번 확인한다. 화면 언어가 es여도 Privacy 본문 en, Changelog 원문·가이드 스크린샷 en인 기존 정책은 그대로다.

측정 판정: 루트 `scrollWidth <= clientWidth`, 제목·입력·닫기·마지막 동작 도달, 헤더 겹침0, 포커스가 숨은 노드에 남는 경우0. 루트 overflow를 감춰 통과시키지 않고 자식 rect의 잘림까지 확인한다. 표/코드 내부 overflow만 예외다. 200% 확대는 유효 CSS 폭375 이상에서 같은 계약을 확인하며 그 미만은 지원 보증 범위 밖이다.

터치 검증은 ego-browser 터치 에뮬레이션(`pointer:coarse`·touch 이벤트·뷰포트)으로 판정한다(2026-10-07 사용자 — 실기기 대체).

## 출시와 앱 연결

**프로덕션은 앱과 동시 출시한다**(2026-10-07 사용자). `/merge`는 dev 전체를 squash하므로 공개만 따로 내보낼 수 없다. 공개 단계(P2~P7)는 dev(preview)에 먼저 쌓이고, `/merge`는 responsive-app 완료 뒤 한 번 한다. 그래서 프로덕션 사용자가 "초대 수락 직후 1280 앱에 떨어지는" 반쪽 기간은 없다.

preview 과도기에는 앱이 1280 하한을 유지한다. 공유 Dialog·LargeModal·CommandDialog·검색·Inbox는 body 포털이라 앱 하한과 무관하게 뷰포트 기준으로 크기가 정해지므로, **앱 1280 이상과 1280 미만(가로 스크롤 구간) 모두 회귀 금지**다(P2·P7 검증).

## 비목표

앱 편집/관리 레이아웃, 앱 완성 후 목업 A18, 새 승인 흐름·권한·서버 API·DB·쿠키·환경변수, 새 UI 라이브러리·토큰 체계, 네이티브 앱·별도 모바일 URL, PWA·manifest·홈 화면 설치, `<meta name="theme-color">`(PRODUCT §4.2 테마 확장), 화면 방향 고정, 스와이프 등 모바일 전용 제스처, Tooltip 프리미티브, 가이드 원고 기능 확장·언어별/모바일 스크린샷은 제외한다. 이 문서 작성은 구현·커밋·배포를 포함하지 않는다.

## 확정 전 시각 값

1024(`lg` = 64rem) 셸 내비 경계·960 본문 TOC 경계는 소스 폭 예산에 근거한 설계값이다. 대표 프레임(2026-10-10 수령)이 두 값을 그대로 썼다. 남은 확정은 긴 문구 및 경계 양쪽 실측이며, 변경 시 두 기능의 설계와 브리프를 함께 맞춘다. 새로운 제품 선택지는 없다.
