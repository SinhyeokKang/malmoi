# Claude Design 요청 — Publish 모달 핸드오프 갱신 (2026-09-16)

> 이 파일은 **Claude Design 캔버스에 붙일 프롬프트**다. 리포 문서가 아니라 전달용이고,
> 기능이 끝나면 `docs/features/publish-modal/`과 함께 지운다.

---

`design_handoff_publish_modal`을 스펙 단계의 판정에 맞춰 갱신해 주세요. 아래는 리포 코드를 읽고
확정한 결정이고, **다섯 가지가 지금 캔버스에 자리가 없습니다.**

## 0. 먼저 — 배송 분할이 사라졌습니다

README §1의 **A(360 확인 Dialog) / B(736 목록·결과 모달) 둘로 쪼갠 배송을 폐기**했습니다.
배송은 하나이고 **360 확인 Dialog는 만들지 않습니다.**

근거: `1a`가 같은 질문("열린 PR을 덮어쓴다")을 **더 잘** 묻습니다 — 경고 한 줄이 아니라 목록까지
듭니다. 둘을 연달아 세우면 되돌릴 수 없는 동작 앞에 물음이 둘이 되고, 그러면 둘째를 안 읽습니다.
이것은 캔버스가 `1a`에 확인 체크박스를 두지 않은 근거("필요한 것은 동의 장치가 아니라 읽을 수
있는 목록이다")와 같은 축입니다.

**그리고 `1a`가 우회 없는 필수 관문이 됐습니다** — `[Publish]`는 언제나 목록을 먼저 보이고
"바로 보내기" 경로가 없습니다. 이 사실이 아래 1·2를 만듭니다.

⚠️ 이에 따라 **README §1의 A/B 문단 · §13-6 · §10-1의 "B 배송" 표현**이 전부 낡았습니다.

## 1. `1a`에 **열린 PR 줄**이 필요합니다 (삼상태)

A 배송이 말하기로 했던 "열려 있는 PR을 덮어씁니다"가 갈 곳을 잃었습니다. `1a`가 그 자리입니다.

지금 `1a`의 설명문은 `A pull request opens on {owner}/{repo}. …` 하나이고, **이미 열린 PR이 있는
경우를 말하지 않습니다.** 그런데 그때 일어나는 일은 새 PR을 여는 것이 아니라 **기존 PR의 내용을
force로 교체하는 것**입니다(`1e`가 사후에 말하는 바로 그 사실).

값은 서버가 삼상태로 줍니다 — 리포의 `OpenImportPr` 타입 그대로입니다:

| 값 | 뜻 | 화면 |
|---|---|---|
| `{ number, url }` | 열린 PR이 있다 | "#128을 덮어씁니다" |
| `null` | 없다 | 새로 열린다는 기존 문장 |
| `undefined` | **조회 전 또는 조회 실패** | "미확인" 줄 |

⚠️ **삼상태를 `null`로 접지 마세요.** "없다"와 "모른다"가 화면에서 다른 줄입니다 — Sync 확인
Dialog(`design_handoff_sync_repository`의 `4a`~`4d`)가 이미 그 구별 위에 서 있고, 같은 사실을
같은 제품에서 두 모양으로 말하면 안 됩니다.

⚠️ **그 Dialog의 amber 블록을 그대로 가져올지는 판단해 주세요.** 이쪽은 736이고 저쪽은 360이라
치수 규칙이 다르고(저쪽은 radius 10 · padding 12 · 글자 13 · 글리프 14로 **한 단계 줄인** 형입니다),
`1a`에는 이미 무거운 표가 있어 amber 블록이 둘째 무게 중심이 될 수 있습니다.

**요청**: `1a`의 변주 셋(`{number,url}` · `null` · `undefined`). 조회가 돌아오면 그 줄이 **바뀌므로**
live 처리도 함께 봐 주세요 — Sync Dialog가 `aria-live="polite"`로 그 교체를 알립니다.

## 2. 신규 아트보드 — `1k` 목록을 못 읽었을 때

`1a`가 필수 관문이 되면서 **base 트리 조회가 실패했을 때**의 화면이 필요해졌습니다.
(설치 취소 · 브랜치 부재 · GitHub 장애 · 타임아웃)

**판정: 막습니다.** 모달은 열리고 표 자리가 실패를 말하며 **보내기 버튼이 서지 않습니다.**
근거 둘 —
1. "무조건 목록을 확인하고 보낸다"가 규칙이면, 확인할 수 없는 순간은 그 규칙이 **미치지 않는**
   순간이 아닙니다. 예외를 두면 규칙이 "보통은"이 됩니다.
2. **같은 조회가 실행 중에 또 돕니다.** `runPull`이 base ref를 못 읽으면 `base-unreadable`로
   던집니다 — 지금 못 읽었으면 보내도 `1h`로 죽을 확률이 높습니다. 막는 것이 헛걸음을 줄입니다.

⚠️ **실패로 말하지 않습니다.** 보낼 수 있었는데 안 보낸 것이 아니라 **아직 읽지 못한** 것입니다.
`1h`의 danger를 쓰면 끝난 일처럼 읽힙니다.

| 자리 | 값 |
|---|---|
| 제목 | `Couldn't read what would go out` (제안 — 문구는 검토해 주세요) |
| 본문 | **무색 블록** — `1e`·`1f`와 같은 급(`border #e5e5e5` · `bg #fff` · 글리프 `#737373`) |
| 바닥 보조문 | `Nothing was sent. Your edits are safe.` — **`1h`·`1i`와 같은 문장** |
| 버튼 | `Try again` **하나**. 보내기 버튼 없음 |
| 폭·높이 | 목록이 없으므로 `1a`(736 · 560~620)보다 작아야 할 텐데 값은 판단해 주세요 |

⚠️ **`1j`(시작 거부)와 다릅니다** — `1j`는 서버가 "지금은 안 된다"고 **판정한** 것이고,
이쪽은 **판단할 재료를 못 얻은** 것입니다. 그래서 `1j`는 `Close`, 이쪽은 `Try again`입니다.

## 3. `1h`가 하나의 틀이고 **사유가 제목·본문·바닥 버튼을 듭니다**

캔버스의 `1h`는 `Couldn't reach the repository` + 사실 표(`Repository` · `Base branch` ·
`Failed at` · `Reference`) + `[Open project settings]`로 **리포 접근 실패 전용**입니다.

그런데 코드를 읽어 보니 **`1h`로 가야 할 사유가 넷 더 있습니다.** Publish는 실행에 들어가기 전에
여섯 사유로 거부되고(`invalid input` · `unavailable` · `unauthorized` · `not-found` · `archived` ·
`not-ready`), 이들은 오류 코드 체계(`SYNC_ERROR_CODES`)를 **지나지 않습니다** — 코드도
재시도 가능 여부도 없습니다. 가르는 기준을 **"사람이 다시 해서 통하나"** 하나로 유지하면
`unavailable`만 `1i`이고 나머지는 `1h`입니다.

**그대로 쓰면 제목이 거짓말이 됩니다** — 세션이 끝난 사람에게 "리포에 닿지 못했다"고 말하고
누를 수 없는 `[Open project settings]`를 줍니다. 이것은 README §4가 `1e`에서 경계한 것과 같은
부류입니다(*"관측할 수 없는 것을 단정하면 문장이 더 구체적이라 거짓이 된다"*).

**요청**: `1h`를 **한 틀 + 사유별 변주**로 그려 주세요.

| 사유 | 제목 | 바닥 버튼 | 사실 표 · `Reference` |
|---|---|---|---|
| `base-unreadable` · `not-installed` · `glob-matched-nothing` | `Couldn't reach the repository` (현행) | `Open project settings` | **선다** |
| `unauthorized` (세션 만료) | 세션 문구 | `Sign in` | **없다** |
| `not-found` · `archived` | 접근 사유 문장 | **없음** | **없다** |
| `not-ready` (첫 적재 전) | 온보딩 사유 문장 | **없음** | **없다** |
| `invalid input` | 폴백 문장 | **없음** | **없다** |

⚠️ **리뷰 5번 보류**: OWNER/EDITOR별 버튼 분기는 추가하지 않습니다. 위 설정 버튼을 제거하고
공통으로 프로젝트 소유자에게 오류 코드를 전달하도록 안내하는 대안은 아직 미확정입니다.
EDITOR는 설정 화면에 접근할 수 없으므로 이 표의 버튼을 확정된 복구 경로로 보지 마세요.

**실행 전 명시적 거부 여섯이 공유하는 것**: danger `Alert` 규격 · 바닥
`Nothing was sent. Your edits are safe.`

✅ **리뷰 1번 확정(2026-09-16)**: 실행 중 오류·응답 유실에는 이 바닥 문구를 쓰지 않습니다.
PR 작성 뒤 DB 기록이 실패할 수도 있으므로, 기존 `1h`/`1i` 안에서
`We couldn't confirm whether your changes were sent.`로 표시해 주세요.
재시도 가능 여부와 전송 여부는 별개입니다. 응답 유실에는 Reference를 만들어 붙이거나
Logs에 기록됐다고 단정하지 않습니다.

⚠️ **`Reference`를 뺄 때 바닥의 "it is in Logs too"도 함께 빼야 합니다** — 그 코드는
`SyncRun.errorCode`로 Logs에 남는 값인데, **이 다섯은 실행 행 자체가 안 생깁니다.**
(같은 이유로 `1j`도 Logs에 안 남고, 캔버스가 이미 그 사실을 적었습니다.)

`1i`가 이미 "사람이 할 일이 같으면 화면도 같다 · 제목 한 줄과 `Reference`만 갈린다"는 형이라,
같은 형을 `1h`로 넓히는 것입니다.

## 4. `1g`에서 **브랜치 교체 경고가 사라집니다**

`1g`(버려진 값이 있는 성공)는 `pr: "created"`와 `"updated"` **둘 다** 받는데, 캔버스는 PR 줄을
축약형 하나로 그렸습니다. 그러면 `1e`가 존재하는 근거 — **브랜치를 덮었고 PR이 든 것이 이번
실행의 분량이 아니다** — 가 `1g`에서만 사라집니다. `warnings`가 있는지와 **무관하게 참인
사실**인데요.

**판정: `1e`의 무색 경고 블록을 `1g`에서 그대로 재사용합니다.** 규칙은 한 줄입니다 —
**`pr === "updated"`면 그 블록은 항상 선다.** 조건이 `warnings`가 아니라 `pr` 하나이므로 예외를
기억할 것이 없고, 무색이라 `Not written` 목록과 급이 안 섞이며, 문구도 안 늘어납니다.

**요청**: `1g`의 변주 둘(`created` · `updated`). `updated` 쪽에서 무색 블록과 `Not written` 목록의
**순서와 간격**을 정해 주세요 — 둘 다 블록이라 붙으면 한 덩어리로 읽힙니다.

## 5. 값이 없어 자리를 지워야 하는 것 둘 (확인 요청)

코드를 읽어 보니 캔버스가 그린 값 중 둘이 **지금 얻을 수 없습니다.** 제안은 "그린 자리를
지운다"인데, 그 판단을 확인해 주세요.

1. **`1d`의 reviewer** — `PullResult`에 없고, 내려면 GitHub 호출이 **한 번 더** 붙습니다.
   README §10-6이 이미 "없으면 그린 자리를 지운다"고 적어 두셨습니다.
2. **`1e`의 총 건수 `62`** — README §10-7이 *"값은 `runPull`의 렌더 결과에 이미 있다"*고
   적었는데, **파일 수준까지입니다.** `changed`는 경로 배열이고 **셀 단위 총 건수는 아무도 세지
   않습니다**(값을 비교하지 않으므로). 세려면 base 파일을 파싱해 DB와 대조하는 경로를 성공
   경로에서도 돌려야 합니다.
   제안: **수 없이 사실만** 말합니다 — "이번 24가 아니라 미발송 전부가 들어 있다"는 수 없이도
   성립하고, 없는 수를 만들면 PR을 열어 본 사람이 또 다른 수를 봅니다.

## 6. 진행·결과 재열기 (리뷰 4번 확정)

번역 화면과 Home 모두 실행 중 모달을 닫아도 `[Publish]`가 `Publishing…` 상태를 유지합니다.
버튼은 클릭 가능하며 현재 진행 모달을 다시 엽니다. **재실행하는 버튼이 아닙니다.**

완료되면 진행 표시를 끝내고 별도 `[View result]`로 마지막 결과를 열게 해 주세요.
미발송 수가 0이라 Publish가 비활성화돼도 이 진입점은 남습니다. PR 링크·경고·실패 결과 모두
다시 볼 수 있어야 합니다. 닫힌 동안 완료돼도 모달을 자동으로 열지는 않습니다.
단순 미리보기 열기·닫기는 직전 결과를 지우지 않고, 새 실행이 완료되면 그 결과로 교체합니다.

## 7. 버튼 영역·접근성 (리뷰 6번 확정)

바닥 오른쪽 버튼 영역은 갈래별로 전달하고, 버튼 없는 갈래에는 온보딩의 Next가 나오지
않게 합니다. 온보딩의 기존 기본값은 유지합니다.

최초 열기·재열기 포커스는 시안의 모달 컨테이너를 따릅니다. 열린 모달에서 진행·결과로
전환되면 본문 시작으로 옮기고, 닫으면 호출 버튼으로 복귀합니다. 버튼이 비활성화되거나
사라졌다면 Home·번역 화면 각각의 제목으로 돌아갑니다. 닫힌 동안 완료돼도 포커스를
빼앗지 않습니다.

danger는 기존 Alert의 `role="alert"`를 유지하고, 같은 오류를 모달 live 영역에서 반복하지
않습니다. 나머지는 껍데기의 polite live 영역 한 곳으로만 전이를 알립니다. 시안의 danger
`role="status"` 요구는 이 규칙으로 정정합니다. 실제 중복 낭독 여부는 수동 검증합니다.

## 8. 상태 구분 (리뷰 7번 확정)

아트보드 번호는 유지합니다. `1a`의 조회 중/성공, `1k`의 조회 실패, `1c`의 실행 중은 모달
상태이고, `1d`~`1j`는 실행 결과 8갈래가 그리는 본문입니다(`1j`에 시작 거부 둘).
`1b`는 모달 본문이 아니라 비활성 Publish 버튼입니다. 실행 결과와 모달 상태를 별도 계약으로
정의하며, 이 구분 때문에 새 화면을 추가하지 않습니다.

## 9. 재시도는 매번 새 목록으로 확인 (리뷰 8번 확정)

`1i`·`1k`의 `Try again`과 미리보기 재열기는 모두 `1a`의 스켈레톤부터 시작해 목록을
새로 읽습니다. 로딩 중 보내기 버튼은 없으며, 새 목록이 도착한 뒤 확인해야 발송합니다.
이전 목록이나 늦게 도착한 이전 요청의 응답으로 보내기를 허용하지 않습니다.

`Publishing…`로 진행을 다시 보거나 `View result`로 완료 결과를 다시 보는 것은 새 발송이
아니므로 기존 상태를 그대로 엽니다. 닫힌 동안 진행 결과를 버리지 않습니다.

## 10. 그대로 두는 것 (재확인)

아래는 코드와 대조했고 **캔버스가 옳습니다** — 바꾸지 마세요.

- `1a`의 행 단위가 셀(`@@unique([keyId, localeCode])`)이고 키가 같으면 칸이 병합되는 것
- `1a`에 확인 체크박스가 없는 것
- `1b`가 새 미리보기를 열지 않는 것 · 자리를 지키고 배지만 없애는 것(진행·결과 재열기는 §6)
- `1c`에 취소가 없고 완료 표시가 **무색**인 것(진행 이벤트를 내는 API를 만들지 않기로 했습니다 —
  단계 셋은 시간 기반으로 그리고 사실을 주장하지 않습니다)
- `1f`가 `1b`와 다른 상태인 것 · danger가 아닌 것 · 버튼이 `Close`인 것
  - 리뷰 2번 확정: `no-edits`와 `no-changes` 모두 `No changes to send.`로 표시합니다.
    미리보기 이후 다른 사람이 발송한 경우도 여기에 속하며 새 화면을 만들지 않습니다.
- `1g`가 버려진 값을 펼치는 것 · 제목이 건수를 말하지 않는 것 · 목록의 단위가 파일인 것
- `1e`가 승인 상태를 말하지 않는 것
- `1j`가 둘이고 `too-soon`의 초가 버튼 라벨인 것 · `already-running`이 먼저인 것
- 껍데기가 온보딩 모달(최대 800)이고 앱 `Dialog`(360)가 아닌 것

⚠️ **`1j` 왼쪽의 `Started by Jiwon · 12 seconds ago`는 지금 API에 없습니다**(README §10-3).
값 자체는 `SyncRun.requestedBy` + `startedAt`에 있어 실을 수 있습니다 — 다만 cron이 돌린 실행은
`requestedBy`가 비어 문구가 두 벌("Someone" / 이름)이 됩니다. 살릴지 판단해 주세요.
