# operator-account — 스펙

## 사용자

**개발자(나, 운영자)**. 번역 편집자에게는 보이는 변화가 없다.

## 개념

**운영자(operator)** = 정적 allowlist로 지정된 **플랫폼 계정**. 프로젝트 역할(OWNER/EDITOR)이 아니다 — 어느 프로젝트의 무엇을 볼 수 있나는 지금처럼 `ProjectMember`가 정한다. 운영자 여부는 "이 사람이 Malmoi를 운영하는가"만 말한다.

운영자에게 붙는 권한은 소비자가 생길 때마다 하나씩 더한다(사용자 2026-10-03 — "리밋 제한 해제는 권한 중 하나일 뿐. 나중에 백오피스 같은 곳 자격증명 계정으로도 사용"). **이번 기능의 소비자는 하나다: 프로젝트 상한 면제.** 백오피스는 그 기능이 올 때 같은 판정(`isOperator`)을 쓴다.

## 문제 (관측된 사실)

- 사용자당 프로젝트 상한 `PROJECT_LIMIT = 3`(`lib/onboarding/create-plan.ts:16`)이 운영자 본인에게도 걸린다. 셈 조건은 `ownedActiveProjects`(`lib/onboarding-run/repos.ts:19` — OWNER 행 · 비보관).
- dev에서 상주 QA·검증 프로젝트(`bugshot-i18n-test-qa` · `i18n-order-check` · `bugshot-i18n-test-qa3`)가 이미 3을 채워, 상주 촬영 프로젝트(`Acme web`, 2026-10-03 search-ux-polish O7)를 두려면 다른 프로젝트를 영구 보관해야 했다. 스크린샷·런타임 검증·roundtrip이 늘 이 자리를 놓고 다툰다(`guide/SHOOTING.md` 진행 상태의 "보관 → 복원" 기록들).
- 운영자를 가리키는 개념이 코드에 없다 — 나중의 백오피스가 기댈 판정이 없다.

## 범위 게이트 (PRODUCT 판정 변경)

- **§3 "역할은 둘뿐이다. Viewer·Admin·Billing은 만들지 않는다"** — 운영자는 **프로젝트 역할이 아니라 플랫폼 계정 축**이다. 역할 표는 그대로 두고, §3에 "운영자"를 별도 축으로 정의하는 단락을 둔다(무엇이 아니고 무엇인지 — 프로젝트 권한을 늘리지 않는다).
- **§4.2 "자원 상한은 전부 고정값"** — 상한 값은 그대로 3이고, **운영자는 계정 축 프로젝트 상한에서 면제**된다는 예외를 등재한다. 플랜·과금이 아니므로 "플랜으로 갈리지 않는다"는 원칙은 유지된다.
- 사용자 확인: 2026-10-03("allowList로 관리할 듯. 정적 운영" · "리밋 제한 해제는 권한 중 하나일 뿐").

## 완료 조건

- C1. 환경변수 `OPERATOR_GITHUB_IDS`(쉼표로 구분한 **GitHub 숫자 사용자 id**)에 든 GitHub 로그인 계정이 연결된 사용자가 운영자다. 판정은 한 함수(`isOperatorUser`)다.
- C2. 환경변수가 비었거나 없으면 운영자는 0명이다(fail-closed — 지금과 같다). 형식이 틀린 항목(숫자 아님·빈 조각)은 무시하고 나머지는 적용한다.
- C3. 판정은 **GitHub 로그인 `Account` 행**(`provider = "github"`, `providerAccountId`)으로만 한다. 이메일·이름·`User.id`로 하지 않는다 — `User.id`는 DB마다 다르고 dev 리셋마다 바뀌며, 이메일은 봉투 암호화 대상이다. 계정 연결용 `APP_ACCOUNT_PROVIDER` 행은 판정에 쓰지 않는다.
- C4. **운영자는 프로젝트 상한에 걸리지 않는다.** 생성 선조회(①의 리포 목록 `listConnectableRepos`) · 생성 판정(`planProjectCreate`) · 트랜잭션 안 재집계(`createProject`)의 세 자리가 같은 값을 쓴다. MCP `create_project`(같은 코어)도 같다.
- C5. 운영자가 아닌 사용자의 동작·문구(`limit-reached`, ①의 상한 안내)는 그대로다.
- C6. 운영자 여부는 화면에 표시하지 않는다(배지·문구·메뉴 없음). 프로젝트 권한(`ProjectMember` 인가)은 운영자라고 늘지 않는다 — 남의 프로젝트를 보거나 고칠 수 없다.
- C7. `.env.example`에 변수·형식·fail-closed·"프로젝트 역할이 아니다" 주석. dev(로컬·Preview)와 Production 값 넣기 절차가 OPERATIONS에 있다.
- C8. PRODUCT §3·§4.2, ARCHITECTURE(생성 판정 §3.1 + 운영자 판정의 자리), CLAUDE.md(필요하면 환경변수·자격 축 언급)와 일치한다. `pnpm gate` green.

## 비목표

- **백오피스·운영 화면** — 운영자의 다음 소비자다. 이번에는 판정만 두고 소비자는 상한 면제 하나다.
- **권한 표·capability 플래그·관리 UI** — 소비자가 하나뿐인데 권한 목록을 만들면 확장 선반영이다. 두 번째 소비자가 생길 때 `isOperator`를 그대로 부르거나, 그때 권한을 가른다.
- **운영자에게 프로젝트 접근을 더 주는 것**(남의 프로젝트 열람·수정) — 인가는 `ProjectMember` 하나다.
- **다른 상한의 면제**(프로젝트당 멤버 10 · 첫 적재 예산 · push 상한) — 필요해지면 그때.
- **Google 로그인 계정의 운영자 지정** — 운영자 계정은 GitHub 로그인이다.
- **DB 저장 allowlist·스키마 변경** — 정적 운영이다.
