# spec — multi-surface projects, 2라운드 (다중 후보 선택)

1라운드(`multi-surface-projects`)가 스키마·격리·단일 PR·표면 선택기·**후보 하나짜리** Add surface까지
끝냈다. 이 문서는 그 spec §0이 2라운드로 미뤄 둔 축 **둘 중 하나**만 받는다.

**2026-09-14 리뷰 확정: 신규 프로젝트 생성과 첫 적재는 All-or-Nothing이다.**
표면 하나의 실패뿐 아니라 일부 파일 실패도 전체 생성을 취소한다. 이전의 “생성 후 표면별 독립 적재”
결정과 1라운드의 신규 생성 경로에 대한 부분 실패 허용은 이 결정으로 대체한다.

| 2라운드의 축 | 이 문서 |
|---|---|
| Checkbox 다중 후보 선택으로 표면 여럿을 **한 번에** 만들기 | **범위** |
| 표면 비활성화/재활성화 UI (`planSurfaceArchive`, 1라운드 design §4.3) | **비목표** — §6 |

⚠️ **1라운드 spec §5.7이 이 기능의 UI를 이미 정해 뒀다.** 이 문서는 그것을 옮겨 적지 않고 **그 절이
답하지 않은 것**(적재 의미론·결과 화면·충돌 시점)만 정한다. 행 구조·접근 이름·초기 체크는 그쪽이 정본이다.

## 1. 사용자

**개발자(나)** 하나다. 번역 편집자는 이 화면을 보지 않는다 — 프로젝트 생성은 OWNER만 하고, 편집자에게
표면은 이미 선택기로만 보인다(1라운드 완료 조건 6).

## 2. 문제

**리포에 로케일 파일 갈래가 둘 이상이면, 지금은 프로젝트를 만든 뒤 Settings로 한 번 더 들어가야 한다.**

관측된 사실 — 2026-09-14 prod 실물 왕복(`SinhyeokKang/bugshot-i18n-test`)이 그 순서를 그대로 밟았다:
프로젝트 생성(`namespaces` 903키) → Settings → Add surface(`_locales` 4키). 두 갈래가 **탐지 화면 ②에
동시에 후보로 서 있었는데도** 한 번에 고를 수 없어서다.

비용은 클릭 수가 아니라 **판단의 분리**다:

- ②는 후보를 **나란히 놓고 비교하는** 유일한 화면이다(좌측 목록 + 우측 키·값 표). 거기서 "둘 다 필요하다"를
  알고도 하나만 고르면, 나머지는 화면을 떠난 뒤 **기억으로** 다시 찾아야 한다.
- Add surface는 후보를 다시 탐지한다 — `i18n-many-locales`류 리포에서 그 탐지가 **30초를 넘는다**
  (CLAUDE.md). 같은 스냅샷을 두 번 읽는다.
- 온보딩 ④가 주는 workflow YAML은 그 시점의 표면만 싣는다. 표면을 나중에 더하면 **대상 리포의 워크플로를
  두 번 고쳐야 한다.**

## 3. 목표

②에서 후보를 **여럿 체크해** 프로젝트 생성 한 번으로 표면 N개를 만들고, ④가 그 N개 전부의 적재 결과와
**step N개가 든 워크플로 YAML 하나**를 낸다.

## 4. 완료 조건

1. ②에서 후보를 둘 이상 체크하고 ③④를 지나면 **체크한 수만큼 `TranslationSurface` 행이 생긴다.**
   기본 표면은 체크된 후보 중 탐지 순서가 가장 앞선 표면(`selectDefaultSurface`)이고 `Project.defaultSurfaceId`가 그것을 가리킨다.
2. **생성·첫 적재 전부가 All-or-Nothing이다.** 모든 표면의 포맷 확정·파일 읽기·파싱이 성공하고,
   키·번역 저장까지 끝나야 프로젝트가 생긴다. 한 표면이라도 실패하면 ③에 입력을 유지하고 실패 경로와
   사유를 보여 준다. Project·OWNER·Surface·Locale·StringKey·Translation·refs·토큰 해시는 남지 않는다.
   일부 파일 실패, 다운로드 누락, 중복 키(`failed > 0`), 0키, 예산 초과, DB 쓰기 실패도 전체 거부다.
3. **표면 하나도 같은 All-or-Nothing 규칙을 따른다.** 단일 표면의 선택 UI와 성공 후 YAML은 유지하되,
   생성과 첫 적재를 기다리는 위치는 ③으로 바뀐다. 기존의 “④에서 첫 적재 중” 화면은 신규 생성에서 없어진다.

4. 체크한 후보 둘이 **같은 출력 경로를 소유하면** 생성 전에 fail-closed로 거부하고 어느 경로가 겹쳤는지
   보인다(1라운드 완료 조건 5를 생성 경로로 연장).
5. ④의 워크플로 YAML이 **활성 표면마다 step 하나**를 담는다 — Settings의 블록과 **같은 함수**가 낸다.
6. 후보 목록의 체크박스와 상세 트리거가 **형제**이고, 중첩 인터랙티브가 없다. 체크박스 접근 이름은
   `Include {path}`, 상세 트리거는 `Preview {path}`다(1라운드 spec §5.7).
7. 생성·적재가 도는 동안 ③에 머무르고 중복 제출을 막는다. **모든 저장이 커밋된 뒤에만** ④에서
   합산 적재 결과·토큰·YAML·[Start translating]을 제공한다. 실패 후 재시도는 전체 선택을 다시 처리한다.

8. ③에서 **체크한 표면마다 베이스 언어를 선택한다** (2026-09-14 리뷰 확정). 각 표면의 탐지 제안으로
   초기화하고, 해당 표면의 언어 중에서 변경한다. 생성·첫 적재는 각 표면에서 선택한 언어를 사용한다.
   체크하지 않은 표면의 미리보기를 열어도 이 선택은 바뀌지 않는다. 표면 하나일 때는 기존 선택 UI를 유지한다.

## 5. 사용자 흐름 — 1라운드 spec §5.7이 답하지 않은 것

### 5.1 한 번의 생성 요청에서 준비하고 원자적으로 저장한다

`createProject`가 하나의 리포 스냅샷에서 체크한 모든 표면의 파일을 읽고 적재 데이터를 준비한다.
GitHub 읽기·포맷 확정·파싱·예산 검사는 DB 트랜잭션 밖이다. 한 표면이라도 불완전하면 저장을 시작하지 않는다.

준비가 모두 끝나면 **한 DB 트랜잭션**에서 프로젝트·OWNER·표면·키·번역을 저장한다.
중간 표면의 DB 쓰기가 실패하면 먼저 저장한 표면까지 롤백한다. 생성 뒤 별도 `runFirstIngest`를 호출하지 않는다.
기존 프로젝트의 Settings 재시도와 Add surface의 정책은 이번 결정의 범위가 아니다.

### 5.2 ③은 대기·실패, ④는 완료다

- ③에서 생성 버튼과 입력을 잠그고 처리 중임을 `role="status"`로 알린다. 실제 서버 진행을 알 수 없는
  “남은 표면 수”를 클라이언트가 추정해서 표시하지 않는다.
- 서버가 생성 거부를 확정해 반환하면 ③에서 **아무것도 생성되지 않았음**과 실패 표면의 경로·사유를 표시한다.
  사용자는 입력을 고치거나 전체 생성을 다시 시도한다. 실패 진단은 `errors.length`뿐 아니라 `failed`를 따른다.
- ④는 모든 표면이 준비된 성공 상태다. 설명 줄에 `Imported N keys.`를 표시하고 성공 Alert는 추가하지 않는다.
  토큰·활성 표면 전체의 YAML·[Start translating]은 이때 제공한다.
- **응답 유실은 생성 거부와 다르다.** DB 커밋 뒤 네트워크가 끊길 수 있으므로 네트워크 오류·클라이언트
  타임아웃만으로 “생성되지 않았다”고 단정하지 않는다. 자동 재제출하지 않고 프로젝트 목록 확인을 안내한다.
  이미 생성됐다면 기존 Settings의 토큰 재발급 경로를 사용한다. 모달을 닫는 동작도 서버 취소를 보장하지 않는다.

### 5.3 충돌은 체크 시점에 말하고 생성 시점에 막는다

두 층이다. 체크 시점 경고는 **되돌리기 쉬운 자리**에서 알려 주기 위한 것이고, 생성 시점 거부가 방어선이다.

- **서버 후보 응답**: 탐지 스냅샷과 확정 포맷으로 계산한 후보별 출력 경로 목록 `outputPaths`를 담는다
  (2026-09-14 리뷰 확정). 표본 미리보기 파일만이 아니라 해당 후보가 소유하는 출력 경로를 제공한다.
- **클라이언트**: 체크된 후보들의 `outputPaths`가 겹치면 그 자리에서 겹친 경로를 표시하고 [Next]를 막는다.
  체크를 해제해 겹침이 없어지면 경고도 사라진다. 화면이 경로 템플릿이나 어댑터로 경로를 다시 계산하지 않는다.
- **서버**: `createProject`가 `surfaceOwnership`으로 재판정한다. 클라이언트 판정을 신뢰하지 않는다 —
  탐지와 생성 사이에 스냅샷이 바뀔 수 있고, 무엇보다 **클라이언트 입력이 경로를 정하게 두지 않는다**(불변식 10).
  `outputPaths`는 사전 안내용이며 생성 입력의 신뢰 근거가 아니다. 조작·누락돼도 서버 재판정은 생략하지 않는다.

수동 지정은 탐지 후보와 함께 제출하지 않는다(§5.5). 수동·탐지 혼합을 충돌 검사의 근거로 삼지 않는다.

### 5.4 ③의 베이스 언어는 표면별이다

- 프로젝트 이름·주소는 하나이고, 베이스 언어 선택은 **체크한 표면의 경로별로** 표시한다.
- A의 베이스 언어를 바꿔도 B는 그대로다. 모든 선택이 각 표면의 언어 목록에 속해야 생성할 수 있다.
- 같은 후보 목록에서 ②로 돌아가 체크를 해제했다가 다시 체크하면 그 표면의 언어 선택을 유지한다.
  리포·브랜치 변경이나 후보 재탐지로 목록이 바뀌면 이전 선택을 버리고 새 탐지 제안으로 초기화한다.

### 5.5 수동 지정은 후보 하나를 만드는 별도 경로다

**2026-09-14 리뷰 확정: 수동 후보 하나만 생성하고 탐지 후보와 섞지 않는다.**
기존 수동 입력·검증 흐름을 유지한다. 탐지 선택은 체크가 하나 이상이어야 진행하지만, 수동 지정은
체크 수가 아니라 현재 입력의 검증 성공 여부로 진행을 판정한다.

③에서는 그 수동 표면의 베이스 언어를 선택하고, 생성 요청에는 수동 포맷 하나만 넣는다.
이전에 체크했던 탐지 후보는 함께 보내지 않는다. 수동 입력을 바꾸면 기존 검증을 무효화한다.
수동 표면 하나도 생성·첫 적재 All-or-Nothing 규칙을 따른다.

## 6. 비목표

- **표면 비활성화·재활성화 UI** — 2라운드의 다른 축이다. 화면이 Settings로 다르고 순수 함수도 다르다
  (`planSurfaceArchive`). 같이 묶으면 한 번에 검증할 면적이 두 배가 된다.
- **Add surface 화면의 다중 선택.** 그 화면은 후보 하나를 유지한다 — 이미 있는 프로젝트에 표면을 더하는
  자리라 "나란히 비교"라는 ②의 성질이 없다.
- **수동 후보 여러 개 추가와 탐지·수동 후보 혼합 선택.** 수동 지정은 기존 단일 포맷 경로만 유지한다.
- **표면별 워크플로 step을 사용자가 고르기.** 활성 표면 전부가 step을 갖는다.
- **체크된 후보 여럿의 미리보기를 동시에 띄우기.** 미리보기는 현재 상세 하나만 lazy load한다
  (1라운드 spec §5.7).
- **새 합산 파일·바이트 예산.** 기존 표면별 예산을 유지한다. 단, 생성 요청 전체의 실행 시간과
  DB 트랜잭션 시간 제한은 별도 제약이며 실측 검증한다. 표면별 예산 통과를 전체 시간 통과로 간주하지 않는다.
- **표면 개수 상한을 새로 두기.** 상한은 이미 탐지 후보 상한(`PROBE_LIMITS`, 7 이하)이 정한다.
- 1라운드 §6의 비목표 전부는 그대로 유효하다.
